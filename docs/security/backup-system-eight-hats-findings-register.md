# `dune db backup-system` — Requirement 20 Eight Hats Findings Register

**Feature:** `dune db backup-system` (issue #269, PR #270 / upstream #159)
**Date:** 2026-08-15
**Status:** Layer 2 + Layer 3 (2 internal rounds + 1 external upstream-maintainer round) audits complete for the current design. Layer 1 (design) was conducted informally via direct user consultation rather than a written pre-code design doc — see "Layer 1" section below for why, and what was actually decided.

This document is the evidence artifact Requirement 20 requires: every layer's findings, their severity, and their resolution status, committed under version control rather than left in chat history alone.

## Layer 1 — Design

No standalone L1 design document was written before code was first drafted. This is a process gap relative to Requirement 20's stated preference ("dispatch all eight hats against the design document... before implementation begins"), acknowledged here rather than silently glossed over. In practice, design decisions were made through direct, explicit user consultation at two points:

1. **Initial design** (two-mode `backup-full`/`backup-world`, redact/exclude secrets for the "world" scope) — implemented first, audited second (Layer 3, retroactively). This ordering is exactly what Requirement 20 warns against ("a single review at the end of weeks of work is destructive") and is the root cause of the CRITICAL/HIGH findings in the first Layer 3 audit below — findings that a design-stage review of "redact secrets from an archive using field-level sed patterns" would very plausibly have caught (redaction-completeness and correctness are exactly the kind of thing a design review interrogates before any code exists).
2. **Redesign** (single-command, retain-everything, encrypt-the-whole-archive) — this time the design decision *was* made before code was written, via explicit back-and-forth with the user:
   - User: *"we need to retain all credentials, we should consider compressing the final archive and encrypting it."*
   - Considered and explicitly rejected: routing the passphrase/DEK through the unmerged age-based KEK library (PR #257/upstream #153) — rejected because `age`/`age-keygen` aren't installed anywhere in this deployment yet, the library is designed for small secret values (not bulk archive data), and coupling a shippable feature to an unmerged, unreviewed dependency violates this project's own scoping discipline. Filed as a deferred follow-up (#272) instead of silently dropped.
   - User: *"lets not engage with age just yet... continue with storing the secret in an env var for cron purposes."* — confirmed the passphrase-based design, deferring age integration explicitly.

**Lesson applied going forward:** the second redesign was still followed by a full Layer 2/3 audit (below) *before* being merged, catching a new CRITICAL and a HIGH that the design conversation alone did not surface (filename-collision cross-contamination; passphrase argv exposure) — confirming Requirement 20's core claim that no single layer substitutes for the others.

## Layer 2/3 Audit — Round 2 (against the redesigned single-command implementation)

**Dispatched:** 8 independent Task-tool agents (same eight hats) against PR #270's diff at commit `ca2f4003`, after Round 1's findings were resolved and the PR was moved to draft pending this audit.

### Findings and resolution

| # | Hat | Severity | Finding | Resolution |
|---|---|---|---|---|
| 1 | Software Architect | **CRITICAL** | `backup_db()` (pre-existing, unmodified, shared by every other backup path in `db.sh`) names its output using only second-resolution timestamps. Two `backup-system` invocations landing in the same wall-clock second computed the identical destination path for the *inner* database dump and silently overwrote each other before `backup_system()` read the result back. Independently reproduced 10/10 times: two concurrent invocations produced two distinct, correctly-unique encrypted archives that **both silently contained the same database dump content** — a real, novel failure mode for the encrypted-backup feature specifically, not just the pre-existing "one plaintext file gets overwritten" behavior that already existed on `main`. | **Resolved.** `backup_db()` is now given a private, per-invocation staging directory (`$out_dir/.dune-db-dump-$archive_id`, named after the archive's own already-unique PID+`$RANDOM` nonce) instead of writing directly into the shared `out_dir`. Collision is now structurally impossible regardless of what filename `backup_db()` computes inside that directory. Verified via a new regression test (`concurrent-invocations-no-cross-contamination`) that runs two real concurrent invocations with per-run content markers baked into the mocked `pg_dump` output, decrypts both resulting archives, and asserts each one's dump matches its own run's marker. Verified via mutation testing (reverting the fix) that this test actually fails when the regression is reintroduced. |
| 2 | Security Architect, Network Engineer, Cloud Security (independently, 3 hats) | **HIGH** | Passphrase passed via `-pass "pass:$passphrase"` — visible in the `openssl` subprocess's own argv (`ps aux`/`/proc/<pid>/cmdline`) for that process's lifetime. Same exposure class as GHSA-fc89-h24v-6j3x, already flagged and fixed elsewhere in this account's security history. Independently reproduced by three separate hats via direct `ps`/`/proc` inspection during a real `openssl` invocation. | **Resolved.** Encryption now uses `-pass fd:N` (passphrase piped through a dedicated file descriptor, verified never to appear in argv). Every operator-facing decrypt instruction (`usage()` text, sidecar YAML's `decrypt_command` field, success-path stdout) rewritten to show the safe `-pass stdin` pattern with an interactive prompt, so operators are not taught to reintroduce the same exposure themselves when restoring. Verified via direct reproduction (background `openssl` process, `ps auxww` inspection) that the passphrase no longer appears in argv, and via a full decrypt round-trip that the new pattern still works correctly. |
| 3 | Security Architect, Cloud Security | MEDIUM | `DUNE_SYSTEM_BACKUP_PASSPHRASE` (when set for cron/automation) is visible via `/proc/<pid>/environ` for the parent process's full lifetime — a real, distinct, narrower-blast-radius exposure than the argv issue (finding 2), inherent to the env-var design and not something this fix eliminates. | **Documented, not eliminated.** This is an accepted, disclosed tradeoff of the "no age dependency yet, use an env var" decision made in Layer 1. Added to `docs/security/secrets-management.md` §1.2a as an explicit, named limitation with its tracking issue (#272, which would eliminate the need for a raw passphrase at all once age integration lands). |
| 4 | Network Engineer | **HIGH** | The "`DUNE_SYSTEM_BACKUP_PASSPHRASE` for cron/automation" documentation claim has no actual automation wiring in this diff — unlike plain `dune db backup`, which has a first-class `dune db auto enable` companion generating a systemd `.service`+`.timer`+`EnvironmentFile`, `backup-system` has no equivalent. An operator who copies that sibling pattern verbatim would get a `644`-permissioned file for a passphrase that gates every credential in the archive. | **Resolved via disclosure, not code.** Filed as its own tracked issue (#274) rather than left implicit — the claim itself ("the env var works for non-interactive use") remains true and tested; the gap is the *lack of a companion automation command*, which is a legitimate, separate feature request, not a defect in what's shipped. |
| 5 | Software Architect | LOW/INFO | Nested function definition (`backup_system_cleanup_on_failure`, defined inside `backup_system()`) leaks into the shell's global function table in bash and persists after the parent returns — a real, non-obvious bash scoping surprise, confirmed via direct testing. | **Accepted, not fixed.** Confirmed not exploitable in this codebase: `db.sh` is always invoked as a fresh subprocess, never sourced/re-entered in the same shell anywhere in this repo, and even a hypothetical same-shell re-call would not reference stale variables (bash functions don't capture by closure). Documented as a known, inert structural quirk rather than refactored under time pressure. |
| 6 | Software Architect | MEDIUM | Code duplication between `backup_db()` and `backup_system()` (carried forward from Round 1, Finding 6) — still open. | **Still open**, tracked as ongoing structural debt. Directly relevant context for Finding 1 above: the two functions' filename strategies diverged specifically because this duplication was never resolved. |
| 7 | GRC | **HIGH** | The PR body's claim that the leaked-token finding was "being tracked/remediated separately" was, at the time of the Round 2 audit, unsubstantiated — no GitHub issue existed anywhere documenting it. | **Partially resolved.** PR body corrected to state plainly that the token has *not* yet been remediated and requires direct operator action, rather than repeating an unverified "being handled" claim. The token itself remains live — see "Outstanding, Unresolved Items" below. |
| 8 | GRC | MEDIUM | PR title and issue #269's title still described the abandoned `backup-full`/`backup-world` two-mode design. | **Resolved** — both renamed to reflect the current `dune db backup-system` design. |
| 9 | UI Design/Architect | MEDIUM | No tracking issue existed for the (disclosed-but-not-formally-tracked) lack of web-console visibility for `backup-system` archives. | **Partially resolved** — explicitly called out in the PR body's "Known gaps" section as not yet tracked, with a commitment to file before merge if not addressed sooner. Not yet filed as of this document's writing. |
| — | DBA | LOW | `DB_BACKUP_PRUNE_AFTER_SUCCESS` pruning, when globally enabled, scopes to whatever `out_dir` it's given — for a `backup_system()`-originated call this is now the private per-invocation `db_dump_dir`, not the top-level system-backup directory (confirmed correct and harmless: pruning only ever matches `*.dump`/`*.sql`/`*.backup` glob patterns, never `.tar.gz.enc`, and the private directory is deleted immediately after use regardless). | No action needed — re-verified as a non-issue after the Finding 1 fix; flagged only for completeness. |
| — | DBA, UI, QA/Test | — | Both previously-fixed Round 1 HIGH bugs (`output-dir` ignored; orphaned plaintext file in web console) independently re-verified as genuinely fixed via fresh empirical testing, not just re-reading the diff. | Confirmed, no further action. |

## Layer 3 Audit — Round 3 (upstream maintainer review of PR #159)

**Source:** live review comment from the upstream maintainer (`Red-Blink`) on `Red-Blink/dune-awakening-selfhost-docker#159`, 2026-08-15, after Round 1/2's fixes were already merged and CI was green. Not a dispatched eight-hats round — an external, independent review, which is itself exactly the kind of independent verification Requirement 20 exists to eventually be checked against.

### Findings and resolution

| # | Severity | Finding | Resolution |
|---|---|---|---|
| 1 | **CRITICAL** | The archive used AES-256-CBC without authentication — confidentiality only, no integrity/tamper detection. A corrupted or maliciously modified archive would silently decrypt to garbage (or worse) with no error. | **Resolved.** Switched to gpg's AES-256-OCB (AEAD), verified against Ubuntu 22.04's shipped GnuPG 2.2.27 (AEAD/OCB support since 2.1.13, 2016) and 24.04's 2.4.4. Passphrase via `--passphrase-fd` (never argv), a private per-invocation `GNUPGHOME` (never the operator's own `~/.gnupg`). Verified directly: a single flipped byte anywhere in the ciphertext is rejected outright (nonzero exit, "WARNING: encrypted message has been manipulated!", zero bytes of output written). New regression test `tampered-archive-rejected`. |
| 2 | **HIGH** (blocking) | `rsync` was required by the implementation but not installed by `install.sh` or in the console container image (confirmed directly against both) — tests only passed because the GitHub Actions runner happens to ship it, masking a real deployment gap. | **Resolved.** Both `rsync` calls replaced with a `tar`-to-`tar` pipe (`tar` is already a hard dependency of this same function, used a few lines below to build the plaintext archive itself) — reuses an existing dependency instead of adding a new untracked one. `gnupg` (needed for Finding 1's fix) added explicitly to `install.sh` (every supported package manager: apt/dnf/yum/zypper/pacman/apk/xbps) and the console `Dockerfile`. |
| 3 | MEDIUM | A broad, permanent Gitleaks allowlist entry existed for 4 literal test-fixture strings, unscoped to any path — "construct fixtures dynamically or scope the allowlist to the test path." | **Resolved by removal, not scoping.** Investigated the maintainer's suggested `paths`-based scoping first; empirically confirmed (via direct `gitleaks detect --log-level debug` testing against gitleaks v8.30.1) that a global `[[allowlists]]` entry with `paths` set causes gitleaks to skip the **entire file** at the filesystem-walk stage (`sources/files.go`'s `shouldSkipPath`), not just the specific allowlisted secret within it — a broader, not narrower, exemption than either the original global regex or the maintainer's request. Verified instead that these 4 fixture strings were never actually necessary in the first place: `gitleaks detect` against the real test file, using only the built-in default ruleset with **no** fixture-specific allowlist entry at all, already produces zero findings (the fixtures' variable names, e.g. `SECRET_ADMIN_PASSWORD=`, don't match any built-in rule's keyword+pattern requirements). Removed the entries entirely rather than keeping an unverified "just in case" allowlist. Also migrated the pre-existing `[allowlist]` (singular) to `[[allowlists]]`, required because gitleaks v8.25+ rejects a config containing both forms. |
| 4 | Suggestion | Test low-disk/interrupted backups, since the implementation duplicates the database and generated state through `/tmp` before encrypting. | **Addressed.** New regression test `disk-full-during-encryption-cleans-up`: wraps `gpg` to simulate an ENOSPC-style failure partway through encryption, confirms zero artifacts (including the private per-invocation `GNUPGHOME` staging directory) survive the failure. |

**Note on Finding 3's investigation:** this is a concrete instance of the same principle already established elsewhere in this project (the secrets-library findings register's Finding 6, and the meta-repo README's #121-123 severity-rating correction) — a plausible-sounding fix (`paths`-scoped allowlist) was tested directly against the real tool's real behavior before being shipped, rather than assumed correct because it matched the reviewer's literal suggestion. The direct test revealed the suggested approach would have been *actively worse* (whole-file exemption) than the thing it was meant to replace, which a solo read of gitleaks' documentation alone did not make obvious — confirmed only by reading `config/config.go`/`detect/detect.go`/`sources/files.go`'s actual source and reproducing the behavior in isolation.

Testing for this round: `tests/db-system-backup-test.sh` 10/10 pass (8 pre-existing + 2 new), `shellcheck -S warning` clean on both changed files, `tests/security-pr-checks.sh` (gitleaks + shellcheck + trivy) clean, `tests/db-backup-validation-test.sh` (unrelated, unaffected) 4/4 pass.
