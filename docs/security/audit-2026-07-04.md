## Executive Summary

This audit identified **13 security findings** across the codebase: **3 Critical**, **5 High**, and **5 Medium**. The most severe issues stem from the architecture choice to mount the Docker socket into the web administration container combined with host networking mode, which effectively grants any authenticated web admin user root-level control over the host system. Additional concerns include hardcoded database credentials, plaintext HTTP for administrative authentication, and unsafe command execution patterns in shell scripts.

The project has a good baseline with input validation, audit logging, rate limiting, and security headers already in place. The findings focus on architectural and configuration weaknesses that would allow an attacker who compromises the web interface or a network path to escalate to full host compromise.

### CRIT-01: Docker Socket Exposed to Web Container with Host Networking

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#121`

**Severity:** CRITICAL
**CWE:** CWE-250 (Execution with Unnecessary Privileges), CWE-284 (Improper Access Control)

**Affected Files:**
- `docker-compose.web.yml:33-34` -- Docker socket volume mount
- `docker-compose.web.yml:17` -- `network_mode: host`
- `docker-compose.yml:12` -- `network_mode: host` on orchestrator

**Description:**

The web administration console container (`redblink-dune-docker-console`) mounts the host's Docker socket (`/var/run/docker.sock`) as a volume and uses `network_mode: host`. This configuration means:

1. The web container runs on the host network stack, bypassing Docker network isolation.
2. The Docker socket provides API access to the Docker daemon, which runs as root.
3. Any process inside the container that can write to the socket can create, start, and execute arbitrary containers -- including privileged containers that have full host root access.

The README itself acknowledges this risk with the comment in `docker-compose.web.yml`:
> "WARNING: mounting the Docker socket gives this container broad control over the host Docker daemon. Expose the web admin only to trusted admins."

However, the web admin interface is explicitly designed to be exposed on port 8088 for browser access, and the default bind address is `0.0.0.0` (all interfaces). Combined with the lack of HTTPS (see HIGH-01), this means any attacker who can reach port 8088 and obtain admin credentials can execute arbitrary commands on the host.

**Exploit Scenario:**

1. Attacker obtains admin password through network sniffing (plaintext HTTP) or brute force.
2. Attacker authenticates to the web API at `http://<host>:8088/api/auth/login`.
3. The web console uses Docker commands internally (via `runner.js` and `tasks.js`) to manage the game server stack.
4. An attacker can craft API calls that leverage the Docker socket to run a privileged container, escape to the host, and gain root access.

**Remediation:**

1. **Remove `network_mode: host`** from `docker-compose.web.yml`. Use a Docker bridge network and expose only the admin port:
   ```yaml
   ports:
     - "${ADMIN_BIND_HOST:-127.0.0.1}:${ADMIN_BIND_PORT:-8088}:8088"
   ```

2. **Avoid mounting the Docker socket** directly. Instead, run a small sidecar service or use a Unix-domain-socket proxy that restricts which Docker API calls are permitted (e.g., only `docker ps`, `docker logs`, `docker compose up/down` for specific services).

3. **At minimum**, bind the admin interface to `127.0.0.1` by default and require a reverse proxy (nginx, Caddy) with TLS termination for remote access.

4. **Implement Docker API access controls** -- restrict the mounted socket access to a non-root Docker context or use the Docker TLS API with client certificates that limit permissions.

**Verification:**

```bash
# Check current network mode
docker inspect redblink-dune-docker-console --format '{{.HostConfig.NetworkMode}}'

# Confirm Docker socket is mounted
docker inspect redblink-dune-docker-console --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' | grep docker.sock
```

### CRIT-02: Hardcoded Default Database Password

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#122`

**Severity:** CRITICAL
**CWE:** CWE-798 (Use of Hard-coded Credentials), CWE-259 (Use of Hard-coded Password)

**Affected Files:**
- `console/api/src/db.js:15` -- Default password `"dune"`
- `console/api/src/duneDb.js:46` -- `usesDefaultPassword` detection
- `docker-compose.metrics.yml:69` -- `DATA_SOURCE_PASS: ${DUNE_DB_PASSWORD:-dune}`
- `.env.example:53` -- `# DUNE_DB_PASSWORD=dune`

**Description:**

The database connection module (`db.js`) falls back to a hardcoded password of `"dune"` when no environment variable is set:

```javascript
password: env.DUNE_DB_PASSWORD || env.PGPASSWORD || "dune",
```

The PostgreSQL instance runs on `127.0.0.1:15432` with this well-known default credential. The `duneDb.js` module even detects this condition:

```javascript
usesDefaultPassword: process.env.DUNE_DB_PASSWORD ? process.env.DUNE_DB_PASSWORD === "dune" : true
```

The metrics stack (`docker-compose.metrics.yml`) also uses `dune` as the default password for the Postgres exporter connection. The `.env.example` file documents this password in comments.

Combined with `network_mode: host`, any process running on the host (or a compromised container) can connect to PostgreSQL at `localhost:15432` with username `dune` and password `dune`, gaining full read/write access to the game database -- including player data, inventory, progression, and server configuration.

**Exploit Scenario:**

1. An attacker compromises any service on the host or a container with network access to `localhost:15432`.
2. Connects to PostgreSQL: `psql -h 127.0.0.1 -p 15432 -U dune -d dune` with password `dune`.
3. Gains full read/write access to all game data including player inventories, currencies, progression.

**Remediation:**

1. **Generate a strong random password at install time** and write it to the `.env` file:
   ```bash
   # In install.sh or init.sh
   DB_PASSWORD=$(openssl rand -base64 32)
   echo "DUNE_DB_PASSWORD=$DB_PASSWORD" >> .env
   ```

2. **Remove the hardcoded fallback** in `db.js`:
   ```javascript
   const password = env.DUNE_DB_PASSWORD || env.PGPASSWORD;
   if (!password) throw new Error("DUNE_DB_PASSWORD is required");
   ```

3. **Update `docker-compose.metrics.yml`** to require an explicit password:
   ```yaml
   DATA_SOURCE_PASS: ${DUNE_DB_PASSWORD:?DUNE_DB_PASSWORD is required}
   ```

4. **Firewall PostgreSQL port** -- ensure PostgreSQL binds only to `127.0.0.1` (not `0.0.0.0`) and use `iptables` to restrict access to the postgres port from non-whitelisted containers.

**Verification:**

```bash
# Check if default password is in use
grep -r "dune" .env | grep DUNE_DB_PASSWORD

# Test connection with default password
PGPASSWORD=dune psql -h 127.0.0.1 -p 15432 -U dune -d dune -c "SELECT 1"
```

### CRIT-03: Privileged cAdvisor Container with Host Filesystem Mounts

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#123`

**Severity:** CRITICAL
**CWE:** CWE-250 (Execution with Unnecessary Privileges)

**Affected Files:**
- `docker-compose.metrics.yml:51-61` -- cAdvisor service definition

**Description:**

The metrics stack runs cAdvisor with `privileged: true` and mounts multiple host paths:

```yaml
privileged: true
volumes:
  - /:/rootfs:ro
  - /var/run:/var/run:ro
  - /sys:/sys:ro
  - /var/lib/docker:/var/lib/docker:ro
  - /dev/disk:/dev/disk:ro
```

While the volumes are mounted read-only (`:ro`), the `privileged: true` flag disables all security restrictions -- it grants access to all host devices, disables seccomp/AppArmor/SELinux profiles, and allows loading kernel modules. A vulnerability in cAdvisor or a misconfiguration could allow container escape to the host with root privileges.

**Exploit Scenario:**

1. An attacker compromises the cAdvisor container through a known CVE or exposed endpoint.
2. Because the container runs in privileged mode, the attacker can mount host filesystems read-write, access host devices, or exploit kernel vulnerabilities to escape to the host.

**Remediation:**

1. **Remove `privileged: true`** and use targeted Linux capabilities:
   ```yaml
   security_opt:
     - no-new-privileges:true
   cap_add:
     - SYS_PTRACE
   cap_drop:
     - ALL
   ```

2. **Run cAdvisor as non-root** if the image supports it, or use the `--disable_metrics` flags to reduce the attack surface.

3. **Restrict cAdvisor metrics endpoint** to localhost only if not needed externally:
   ```yaml
   ports:
     - "127.0.0.1:8080:8080"
   ```

4. **Consider alternatives** like running node_exporter on the host directly (via systemd) rather than in a privileged container.

**Verification:**

```bash
# Check cAdvisor privileges
docker inspect dune-cadvisor --format '{{.HostConfig.Privileged}}'

# Check mounted volumes
docker inspect dune-cadvisor --format '{{range .Mounts}}{{.Source}} -> {{.Destination}} ({{.Mode}}){{"\n"}}{{end}}'
```

### HIGH-01: No HTTPS/TLS on Web Admin Panel

**Severity:** HIGH
**CWE:** CWE-319 (Cleartext Transmission of Sensitive Information), CWE-311 (Missing Encryption of Sensitive Data)

**Affected Files:**
- `docker-compose.web.yml:21-22` -- `ADMIN_BIND_HOST: 0.0.0.0`, plain HTTP
- `.env.example:39-40` -- `ADMIN_SECURE_COOKIES=0`, `ADMIN_BIND_PORT=8088`
- `console/api/src/auth.js:88` -- `setSessionCookie` uses `Secure` only when config.secureCookies is true
- `console/api/src/server.js` -- Entire API over HTTP

**Description:**

The web administration panel serves all traffic over plain HTTP (port 8088). This means:

1. Admin login credentials (`POST /api/auth/login` with JSON body containing `password`) are transmitted in cleartext.
2. Session cookies (`asc_session`) are transmitted without the `Secure` flag (default `ADMIN_SECURE_COOKIES=0`), making them vulnerable to network interception.
3. The entire admin interface -- including game server management, database queries, player data, and Funcom token management -- is exposed over unencrypted HTTP.

The `ADMIN_SECURE_COOKIES` configuration defaults to `0`. The `config.js` code only enables secure cookies if explicitly set or if `NODE_ENV=production`, but even then, there is no TLS termination in the stack.

**Exploit Scenario:**

1. Attacker on the same network performs ARP spoofing or passive sniffing.
2. Attacker captures the admin password during login or the session cookie in subsequent requests.
3. Attacker authenticates to the admin panel and gains full control over the game server and host (via CRIT-01).

**Remediation:**

1. **Implement TLS termination** using one of:
   - Reverse proxy (nginx/Caddy) with Let's Encrypt in front of the admin panel.
   - Built-in HTTPS in the Node.js server with auto-generated or user-provided certificates.
   - Caddy sidecar container that handles automatic TLS.

2. **Enable `ADMIN_SECURE_COOKIES=1`** as the default and require it when TLS is active:
   ```bash
   ADMIN_SECURE_COOKIES=1
   ```

3. **Set HSTS header** when TLS is active:
   ```javascript
   "strict-transport-security": "max-age=31536000; includeSubDomains"
   ```

4. **Redirect HTTP to HTTPS** at the reverse proxy level.

5. **Example nginx reverse proxy configuration:**
   ```nginx
   server {
       listen 443 ssl http2;
       server_name dune-admin.example.com;
       ssl_certificate /etc/letsencrypt/live/.../fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/.../privkey.pem;
       location / {
           proxy_pass http://127.0.0.1:8088;
           proxy_set_header X-Forwarded-Proto https;
       }
   }
   ```

**Verification:**

```bash
# Check if HTTP (not HTTPS) is serving the admin panel
curl -sI http://127.0.0.1:8088/api/health

# Verify secure cookies are not set by default
curl -sI http://127.0.0.1:8088/api/health | grep -i set-cookie
```

### HIGH-02: `curl | sh` Anti-Pattern in Install Script

**Severity:** HIGH
**CWE:** CWE-494 (Download of Code Without Integrity Check)

**Affected Files:**
- `install.sh:86` -- `curl -fsSL https://get.docker.com | need_sudo sh`
- `dune_orchestrator.py:218` -- `curl https://steamcdn-a.akamaihd.net/client/installer/steamcmd_linux.tar.gz | tar`
- `runtime/scripts/init.sh:14-17` -- One-liner install instructions with `curl | sudo tee`

**Description:**

The installer script pipes the output of `curl` directly into a shell running as root:

```bash
curl -fsSL https://get.docker.com | need_sudo sh
```

This is a well-known security anti-pattern because:
1. If the connection is interrupted mid-stream, the shell executes a partial script.
2. If the server is compromised, the attacker can serve a malicious script.
3. No integrity verification (checksum, signature) is performed on the downloaded content.

The same pattern exists in the Python orchestrator (`dune_orchestrator.py`), which downloads SteamCMD from `steamcdn-a.akamaihd.net` and the README's install instructions, which use `curl | sudo tee` for Docker repository setup.

**Remediation:**

1. **Download first, verify, then execute:**
   ```bash
   curl -fsSL https://get.docker.com -o /tmp/get-docker.sh
   # Verify with a known checksum if available, or at minimum check the file is non-empty
   if [ -s /tmp/get-docker.sh ]; then
       need_sudo sh /tmp/get-docker.sh
       rm /tmp/get-docker.sh
   else
       echo "Failed to download Docker install script"
       exit 1
   fi
   ```

2. **Bundle the Docker repository setup** into the installer rather than downloading it at runtime.

3. **Verify SteamCMD checksums** against known good values after download.

4. **Pin Docker GPG key fingerprints** in the repository setup rather than downloading them dynamically.

**Verification:**

```bash
# Check for curl piped to shell patterns
grep -rn 'curl.*|.*sh\|curl.*|.*sudo\|curl.*|.*bash' -- '*.sh' '*.py' 'README.md'
```

### HIGH-03: Self-Update Spawns Privileged Docker Containers

**Severity:** HIGH
**CWE:** CWE-250 (Execution with Unnecessary Privileges), CWE-94 (Code Injection)

**Affected Files:**
- `console/api/src/tasks.js:126-140` -- `buildSelfUpdateHelperDockerArgs()`
- `runtime/scripts/self-update.sh:667-677` -- `rebuild_web_console_with_helper()`
- `runtime/scripts/update.sh:185-201` -- `install_auto_units_via_docker_host()`

**Description:**

The self-update mechanism spawns ephemeral Docker containers with elevated privileges:

```javascript
// tasks.js
["run", "--rm", "-d", "--name", helperName,
 "--network", "host",
 "-v", `${hostRepoRoot}:/repo`,
 "-v", "/var/run/docker.sock:/var/run/docker.sock",
 "-w", "/repo",
 helperImage,
 "sh", "-lc", command]
```

And in shell scripts:
```bash
# self-update.sh
docker run --rm -d \
    --name "$helper_name" \
    --network host \
    -v "$HOST_ROOT_DIR:/repo" \
    -v /var/run/docker.sock:/var/run/docker.sock \
    "$helper_image" \
    sh -lc "sleep 2; runtime/scripts/self-update.sh rebuild-web-console '$service' ..."
```

The update process:
1. Downloads a tarball from GitHub releases.
2. Extracts it over the current installation.
3. Spawns a privileged helper container to rebuild and restart the web console.
4. The helper has Docker socket access AND host networking -- full host control.

If the GitHub release tarball were compromised or the download was intercepted, the attacker's code would execute with Docker socket access.

**Remediation:**

1. **Verify tarball integrity** using GitHub release artifact attestations or a hardcoded public key signature check.

2. **Eliminate the helper container** approach. The web console rebuild can be triggered by writing a flag file and having a host-level systemd service or cron job detect it and perform the rebuild locally.

3. **If the helper pattern is necessary**, use a minimal dedicated image (e.g., `docker:cli` or `alpine` with only the docker binary) and restrict it to the specific compose operations needed:
   ```bash
   docker run --rm \
       -v /var/run/docker.sock:/var/run/docker.sock \
       docker:cli \
       docker compose -f /repo/docker-compose.web.yml up -d --force-recreate
   ```

4. **Pin the helper image digest**, not just a tag:
   ```bash
   helper_image="redblink-dune-docker-console@sha256:..."
   ```

**Verification:**

```bash
# Check for privileged update containers
grep -rn 'docker run.*docker\.sock\|docker run.*privileged\|docker run.*network.*host.*docker\.sock' -- '*.sh' '*.js'
```

### HIGH-04: In-Memory Session Store with No Revocation

**Severity:** HIGH
**CWE:** CWE-613 (Insufficient Session Expiration), CWE-384 (Session Fixation)

**Affected Files:**
- `console/api/src/auth.js:3` -- `const sessions = new Map()`
- `console/api/src/auth.js:33-44` -- `makeSession()` with 12-hour expiry
- `console/api/src/auth.js:46-55` -- `readSession()` with no additional validation

**Description:**

Sessions are stored exclusively in a JavaScript `Map` in memory:

```javascript
const sessions = new Map();
```

This has several security weaknesses:
1. **No session persistence** -- restarting the Node.js process invalidates all sessions, but this is not a security control.
2. **No individual session revocation** -- there is no way to log out a specific session or invalidate all sessions for a user.
3. **No user-agent or IP binding** -- a stolen session cookie can be used from any client.
4. **Session fixation possible** -- `makeSession()` generates a new session ID on each login, but the old session remains valid.
5. **No absolute session timeout** -- sessions have a 12-hour sliding window (set at creation time only).

**Remediation:**

1. **Implement session revocation** by storing sessions in a persistent store (SQLite, file-based, or the existing PostgreSQL instance) with an `invalidated` flag.

2. **Bind sessions to client characteristics:**
   ```javascript
   function makeSession(req) {
       const fingerprint = createHash("sha256")
           .update(req.headers["user-agent"] || "")
           .update(req.socket.remoteAddress || "")
           .digest("base64url");
       return { id, csrf, expiresAt, fingerprint };
   }
   ```

3. **Implement sliding expiration** with an absolute maximum (e.g., 24 hours absolute, 1 hour idle).

4. **Invalidate old sessions on password change.**

5. **Implement logout-all-sessions endpoint.**

**Verification:**

```bash
# Check that sessions are in-memory only
grep -n "sessions\s*=" console/api/src/auth.js
```

### HIGH-05: Funcom Token Exposed via Process Environment

**Severity:** HIGH
**CWE:** CWE-214 (Information Exposure Through Process Environment)

**Affected Files:**
- `runtime/scripts/init.sh:212-232` -- `TOKEN="$FUNCOM_TOKEN" python3 ...`
- `runtime/scripts/db.sh:54-73` -- `TOKEN="$token" TOKEN_KEY="$key" python3 ...`
- `console/api/src/config.js:26` -- Token stored in `runtime/secrets/funcom-token.txt`

**Description:**

The Funcom JWT token (used to authenticate the game server to Funcom's backend) is passed to Python scripts via environment variables:

```bash
TOKEN="$FUNCOM_TOKEN" python3 - <<'PY'
...
token = os.environ["TOKEN"].strip()
```

Environment variables of a running process are visible in `/proc/<pid>/environ` (readable by the same user and root). This means:
1. Any process running as the same user can read the token.
2. The token appears in process listings and audit logs if process accounting is enabled.
3. The token persists in shell history when passed in command lines.

Additionally, `config.js` stores the token in a plain text file at `runtime/secrets/funcom-token.txt` with permissions `0o644` (world-readable).

**Remediation:**

1. **Pass the token via stdin or a file descriptor** instead of environment variables:
   ```bash
   python3 - "$FUNCOM_TOKEN" <<'PY'
   import sys
   token = sys.argv[1]
   ```

2. **Use file descriptor passing** for sensitive data:
   ```bash
   python3 /dev/fd/3 3<<<"$FUNCOM_TOKEN"
   ```

3. **Set restrictive permissions** on the token file:
   ```bash
   chmod 600 runtime/secrets/funcom-token.txt
   ```

4. **Use in-memory only passing** where possible, or use a dedicated secrets management approach (e.g., Docker secrets).

**Verification:**

```bash
# Check file permissions on token file
ls -la runtime/secrets/funcom-token.txt

# Check for TOKEN= patterns in shell scripts
grep -rn 'TOKEN=.*python3\|TOKEN=.*python' -- '*.sh'
```

### MED-01: Admin Password Printed to stdout

**Severity:** MEDIUM
**CWE:** CWE-532 (Insertion of Sensitive Information into Log File), CWE-359 (Exposure of Private Information)

**Affected Files:**
- `install.sh:356-378` -- `show_finish()` function

**Description:**

The installer generates an admin password and prints it to the terminal:

```bash
admin_password="$(read_admin_password "$password_file")"
echo "Use this password to sign in:"
echo "  $admin_password"
```

This password ends up in:
1. Terminal scrollback buffers
2. Shell history files (`.bash_history`)
3. Terminal emulator log files
4. SSH session logs if session recording is enabled
5. `script` / `screen` / `tmux` session logs

**Remediation:**

1. **Do not print the password to stdout.** Instead, write it to a file and instruct the user to read it:
   ```bash
   echo "Your admin password has been saved to:"
   echo "  $password_file"
   echo "To view it: cat $password_file"
   ```

2. **Force password change on first login** through the web interface.

3. **Display password via a secure one-time mechanism** such as a QR code displayed once or an expiring link.

**Verification:**

```bash
# Check if password is printed
grep -n 'echo.*\$.*password\|echo.*\$admin_password\|echo.*ADMIN_PASSWORD' install.sh
```

### MED-02: Default Bind to All Interfaces (0.0.0.0)

**Severity:** MEDIUM
**CWE:** CWE-1327 (Binding to an Unrestricted IP Address)

**Affected Files:**
- `console/api/src/config.js:24` -- `resolveAdminBindHost("auto")` resolves to `0.0.0.0` by default
- `docker-compose.web.yml:21` -- `ADMIN_BIND_HOST: "0.0.0.0"`

**Description:**

The web admin binds to `0.0.0.0` (all network interfaces) by default. While the `resolveAdminBindHost` function attempts to detect a private IP, it falls back to `0.0.0.0` when automatic detection fails:

```javascript
function resolveAdminBindHost(value) {
    const raw = String(value || "0.0.0.0").trim();
    if (raw && raw !== "auto") return raw;
    return detectPrivateIpv4() || "127.0.0.1";
}
```

And the compose file explicitly sets `0.0.0.0`:
```yaml
ADMIN_BIND_HOST: "${ADMIN_BIND_HOST:-0.0.0.0}"
```

This exposes the admin panel on all network interfaces, including public-facing ones, increasing the attack surface.

**Remediation:**

1. **Default to `127.0.0.1`** in the Docker Compose file:
   ```yaml
   ADMIN_BIND_HOST: "${ADMIN_BIND_HOST:-127.0.0.1}"
   ```

2. **Only allow `0.0.0.0` when explicitly configured** by the user with a clear warning.

3. **Document the security implications** in the README and setup wizard when binding to all interfaces.

**Verification:**

```bash
# Check bind address
ss -ltnp | grep 8088
```

### MED-03: Database Connection Without TLS (sslmode=disable)

**Severity:** MEDIUM
**CWE:** CWE-311 (Missing Encryption of Sensitive Data)

**Affected Files:**
- `docker-compose.metrics.yml:68` -- `sslmode=disable`
- `console/api/src/db.js:12-17` -- No SSL options in connection config

**Description:**

The Postgres exporter in the metrics stack connects to PostgreSQL with TLS disabled:

```yaml
DATA_SOURCE_URI: dune-postgres:5432/dune?sslmode=disable
```

Similarly, the web admin's database connection (`db.js`) does not specify any SSL/TLS configuration. While PostgreSQL and the exporter run on the same Docker network, defense-in-depth principles require encrypting database connections to prevent packet sniffing if network isolation is compromised.

**Remediation:**

1. **Enable TLS for PostgreSQL** connections:
   ```yaml
   DATA_SOURCE_URI: dune-postgres:5432/dune?sslmode=require
   ```

2. **Configure PostgreSQL with TLS certificates** in the server startup scripts.

3. **Add SSL configuration to `db.js`**:
   ```javascript
   const pool = new Pool({
       ...dbConfig,
       ssl: env.DUNE_DB_SSL === "1" ? { rejectUnauthorized: true } : false,
   });
   ```

4. **At minimum, use `sslmode=prefer`** to attempt encryption when available.

**Verification:**

```bash
# Check for sslmode=disable
grep -rn 'sslmode=disable' -- '*.yml' '*.sh' '*.js'
```

### MED-04: CSRF Token Bypass on GET Requests

**Severity:** MEDIUM
**CWE:** CWE-352 (Cross-Site Request Forgery)

**Affected Files:**
- `console/api/src/auth.js:73-81` -- `requireAuth()` CSRF check

**Description:**

The CSRF token check is only enforced for non-GET methods:

```javascript
if (!["GET", "HEAD", "OPTIONS"].includes(req.method || "")) {
    const csrf = req.headers["x-csrf-token"];
    if (!config.authDisabled && csrf !== session.csrf) {
        json(res, 403, { error: "..." });
        return null;
    }
}
```

While the API currently uses POST for all mutating operations, this is a fragile security boundary. If any state-changing endpoint were accidentally or intentionally implemented as GET, it would be vulnerable to CSRF attacks. GET-based state changes are explicitly forbidden by RFC 7231 and the OWASP ASVS.

**Remediation:**

1. **Enforce CSRF on all methods unconditionally** (except OPTIONS for CORS preflight):
   ```javascript
   if (req.method !== "OPTIONS" && !config.authDisabled && csrf !== session.csrf) {
       json(res, 403, { error: "CSRF token missing or invalid" });
       return null;
   }
   ```

2. **Add `SameSite=Strict` to cookies** for additional protection:
   ```javascript
   res.setHeader("Set-Cookie", `asc_session=...; HttpOnly; SameSite=Strict; Path=/`);
   ```

3. **Implement a Content-Security-Policy header** with `script-src 'self'`.

**Verification:**

```bash
# Verify GET endpoints don't modify state
grep -n "req.method.*GET\|path.*===.*&&.*req.method" console/api/src/server.js | grep -v "auth\|health\|static"
```

### MED-05: Sensitive Values Passed via Shell Command Arguments

**Severity:** MEDIUM
**CWE:** CWE-214 (Information Exposure Through Process Environment)

**Affected Files:**
- `install.sh:356` -- Password passed to `echo` and `printf`
- `runtime/scripts/config.sh:72-88` -- `sed -i "s/^${key}=.*/${key}=${value}/"` with secrets
- `runtime/scripts/ensure-public-ip.sh:20-27` -- `awk -v key="$key" -v value="$value"`
- `console/api/src/tasks.js:139` -- `shellQuote(command)` in Docker exec

**Description:**

Multiple shell scripts handle secrets in ways that can expose them:

1. **`sed` in-place editing** of `.env` can leak values via temporary files.
2. **`awk -v`** passes values that appear in `/proc/<pid>/cmdline`.
3. **`docker exec` commands** pass environment variables that appear in Docker logs and `docker inspect`.

While individual instances may seem low-risk, the cumulative effect is a pattern where secrets routinely pass through mechanisms visible to other processes.

**Remediation:**

1. **Use atomic file writes** with restricted permissions instead of `sed -i`:
   ```bash
   tmp=$(mktemp)
   awk ... "$file" > "$tmp"
   mv "$tmp" "$file"
   chmod 600 "$file"
   ```

2. **Pass secrets via stdin or file descriptors** instead of command arguments.

3. **Use `DOCKER_SECRETS` or file-based configuration** for Docker containers rather than environment variables.

4. **Set restricted `umask 077`** before handling secrets in scripts.

**Verification:**

```bash
# Check for sed -i with sensitive patterns
grep -rn 'sed -i.*password\|sed -i.*token\|sed -i.*secret' -- '*.sh'
```

## Positive Security Observations

The project demonstrates several good security practices:
1. **Input validation** -- All user-supplied parameters are validated with strict regex patterns in `runner.js`.
2. **Audit logging** -- All admin actions are recorded to `web-admin-audit.jsonl` via `audit.js`.
3. **Rate limiting** -- Login attempts are rate-limited (8 attempts per 15-minute window) via `rateLimit.js`.
4. **Security headers** -- `nosniff`, `DENY` framing, `no-referrer`, restrictive permissions policy.
5. **Secret redaction** -- stdout/stderr output is sanitized via `redact.js`.
6. **SQL injection protection** -- Parameterized queries throughout `duneDb.js`.
7. **Path traversal protection** -- `safeAddonRelativePath()` and `installedAddonContentPath()` validate paths.
8. **Pre-commit security hooks** -- `.pre-commit-config.yaml` with gitleaks, shellcheck, trivy.
9. **CI security checks** -- `ci.yml` runs security scans (gitleaks, trivy, semgrep).
10. **SHA-256 verification** -- Community addon downloads are verified against manifest hashes.
