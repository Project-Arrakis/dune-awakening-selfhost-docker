**Scope:** Full repository -- JavaScript (Node.js), Python, Bash, Docker Compose, Dockerfiles
**Files Scanned:** 90+ source files across all directories

## Executive Summary

**REVISION 2:** The original executive summary characterized all
findings, including architectural observations and defense-in-depth
items, as active vulnerabilities with a unified "any authenticated web
admin user" exploit framing. That framing has been removed. See each
finding's Classification line for what is actually demonstrated versus
what describes trust-boundary architecture or hardening opportunity.

This audit identified 13 security findings across the codebase, now
reclassified as: 2 verified vulnerabilities with a demonstrated or
directly-confirmable exploit path (CRIT-02's local/internal-network
credential exposure, downgraded from unauthenticated-remote; HIGH-04's
session-revocation gap), 3 architectural risks without a demonstrated
exploit (CRIT-01, CRIT-03, HIGH-03's supply-chain amplification), 1
already-remediated finding (the original HIGH-02 `curl | sh` pattern
for the Docker installer and SteamCMD download), 1 partially-remediated
finding (HIGH-05, file permissions already correct; the environment-
variable exposure part remains a defense-in-depth item), 1 finding
downgraded to informational (MED-04, CSRF-on-GET), and the remainder
are defense-in-depth recommendations (MED-01, MED-02, MED-03, MED-05,
and the improvable-but-not-broken parts of HIGH-01).

The project has a good baseline with input validation, audit logging,
rate limiting, security headers, and (verified in this revision)
consistent use of argument-array process spawning with `shell: false`
and an allowlisted, non-attacker-controlled operation-name dispatch
model for every Console API route that reaches process execution.

### CRIT-01: Docker Socket Exposed to Web Container with Host Networking

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#121`

**Severity:** CRITICAL (architecture) -- **REVISION 2:** the exploit
scenario originally described here is not demonstrated; see below.

**Classification:** Architectural risk without a demonstrated exploit.
The trust-boundary observation is verified against current upstream.
The specific exploit chain from "authenticated Console session" to
"attacker crafts an API request that creates a privileged container"
is not.

**CWE:** CWE-250 (Execution with Unnecessary Privileges), CWE-284 (Improper Access Control)

**Affected Files (line numbers re-verified against upstream `4d13321`):**
- `docker-compose.web.yml` -- Docker socket volume mount (`- /var/run/docker.sock:/var/run/docker.sock`, near end of the `volumes:` block; exact line has shifted since the original audit and should not be cited by number without re-checking)
- `docker-compose.web.yml` -- `network_mode: host`
- `docker-compose.yml` -- `network_mode: host` on orchestrator

**Description:**

The web administration console container (`redblink-dune-docker-console`) mounts the host's Docker socket (`/var/run/docker.sock`) as a volume and uses `network_mode: host`. Verified directly in upstream `4d13321`:

1. The web container runs on the host network stack, bypassing Docker network isolation.
2. The Docker socket provides API access to the Docker daemon, which runs as root.
3. A process inside the container with unrestricted access to the socket could create, start, and execute arbitrary containers -- including privileged containers.

This part of the finding is real and verified: **compromise of the
Console process should be treated as potentially host-root-equivalent**,
because the Console is intentionally Docker-control-plane privileged by
design (it manages connected local services, dynamic map/partition
containers, updates, logs, backups, and lifecycle operations that
require this access).

**REVISION 2 -- what is NOT demonstrated:** The original exploit
scenario stated that "an attacker can craft API calls that leverage the
Docker socket to run a privileged container." This report traced every
reachable path from an HTTP route to Docker/process execution in
`console/api/src/server.js`, `runner.js`, and `tasks.js` as of upstream
`4d13321` and found:

- Every route handler passes a hardcoded literal `operation` string (or
  chooses between exactly two hardcoded literals via a boolean, e.g.
  `body.enabled ? "backupAutoEnable" : "backupAutoDisable"`, or looks a
  client-supplied string up in a fixed object map with an explicit
  rejection for unmapped values, e.g. `sietchesUpdateRoute`'s
  `operationByAction` table) to `buildDuneArgs(operation, payload)`.
  No route was found where a client-supplied string becomes the
  operation name itself.
- `buildDuneArgs()` (`runner.js`) resolves each operation through a
  fixed `simpleOperations` map or an explicit `switch` statement, with
  payload fields passed through named validator functions
  (`validateServiceName`, `validateNumber`, `validateServerTitle`,
  etc.) before use.
- All process execution (`runner.js`, `tasks.js`) uses
  `spawn(command, args, { shell: false })` -- argument arrays, not
  shell strings. No `shell: true` or string-concatenated shell command
  was found in these files.
- The self-update helper (`tasks.js`'s `buildSelfUpdateHelperDockerArgs`)
  constructs its Docker `run` invocation from a fixed argument array; the
  only variable, freeform part is the inner `command` string, which is
  itself built from `buildDuneArgs()`'s already-validated `args`, passed
  through a real shell-quoting function (`shellQuote()`, single-quote
  escaping with `'` -> `'\''`), not raw interpolation.

No authenticated route was found that accepts arbitrary Docker CLI
arguments, an arbitrary shell command, or a caller-controlled
executable path. To substantiate a Critical, directly-exploitable
rating (rather than an architectural-risk rating), this report would
need one of:

1. A specific authenticated route allowing arbitrary Docker arguments.
2. A shell-injection path through a documented request field.
3. A path-traversal or arbitrary-write primitive that leads to execution.
4. A demonstrated Console RCE independent of already having host-level access.

None of these were found during this revision's review. The accurate,
verified finding is:

> A code-execution vulnerability inside the trusted Console (e.g. an
> unrelated dependency CVE, a path-traversal bug not yet found, or a
> future regression) would have a high-impact path to host compromise,
> because the Console is intentionally Docker-control-plane privileged.
> This is a serious architectural risk that raises the stakes of any
> future Console-side bug significantly above a typical web
> application. It is not the same as proving that any authenticated
> administrator, today, can execute arbitrary host commands through a
> documented API surface.

**Remediation (updated):**

Removing host networking or the Docker socket immediately is **not** a
safe standalone remediation -- the Console's legitimate, documented
functionality (managing connected local services, dynamic containers,
updates, logs, and lifecycle operations) depends on this access today.
A redesign to a restricted, operation-level privileged broker or socket
proxy is worth investigating, but needs its own operation-level API
design and compatibility tests before any default changes.

The most actionable current mitigation is reducing Console network
exposure, not removing its Docker privileges:

1. Default the Console's bind address to loopback or an explicitly
   selected LAN interface (see HIGH-01/MED-02 below).
2. Require a deliberate operator choice for public exposure.
3. Document `ADMIN_ALLOWED_IPS` (if present) or add it if not.
4. Provide a supported TLS reverse-proxy configuration.
5. Add explicit documentation that the Console is a trusted,
   root-equivalent management plane and should be treated with the
   same care as SSH/root access to the host.

**Verification:**

```bash
docker inspect redblink-dune-docker-console --format '{{.HostConfig.NetworkMode}}'
docker inspect redblink-dune-docker-console --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' | grep docker.sock
```

### CRIT-02: Hardcoded Default Database Password

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#122`

**Severity:** HIGH -- **REVISION 2: downgraded from CRITICAL.** The
underlying weak-credential finding is real and verified, but the
original "remote exploit" framing does not match the verified network
exposure.

**Classification:** Verified against current upstream, with corrected
network-exposure preconditions.

**CWE:** CWE-798 (Use of Hard-coded Credentials), CWE-259 (Use of Hard-coded Password)

**Affected Files:**
- `console/api/src/db.js` -- `password: env.DUNE_DB_PASSWORD || env.PGPASSWORD || "dune"` (default `dune` role password)
- `console/api/src/duneDb.js` -- `usesDefaultPassword` detection
- `docker-compose.metrics.yml` -- `DATA_SOURCE_PASS: ${DUNE_DB_PASSWORD:-dune}`
- `.env.example` -- `# DUNE_DB_PASSWORD=dune` (documented, commented out)
- `runtime/scripts/start-postgres.sh` -- **REVISION 2, newly identified:** `-e POSTGRES_PASSWORD=postgres` (the internal PostgreSQL superuser bootstrap credential, separate from and more privileged than the `dune` application role, not covered by the original finding at all)

**Description:**

The database connection module (`db.js`) falls back to a hardcoded
password of `"dune"` when no environment variable is set, and
`duneDb.js` explicitly detects this condition
(`usesDefaultPassword: process.env.DUNE_DB_PASSWORD ? process.env.DUNE_DB_PASSWORD === "dune" : true`).
Both are verified unchanged in current upstream `4d13321`. The metrics
stack's Postgres exporter also defaults to the same password.

**REVISION 2 -- network exposure, corrected:** The original finding
stated this was reachable at "`localhost:15432`" and implied broad
remote reachability once combined with `network_mode: host`. Verified
directly in `runtime/scripts/start-postgres.sh`:

```
-p "127.0.0.1:${POSTGRES_PORT}:5432"
```

PostgreSQL is published on `127.0.0.1` specifically, not `0.0.0.0` or
all interfaces. Because the Console itself runs with
`network_mode: host` (see CRIT-01), "127.0.0.1" here is the *host's*
loopback, not just a container-network-local address -- so any process
running on the host (not only inside the same Docker network) can
reach it. This is a real and non-trivial exposure surface given the
architecture, but it is materially different from an unauthenticated
*remote* database exposure, which is what "Critical, minimal
preconditions" implies under this report's own severity definitions.
Exploitation requires local-host access, a compromised host-network
container, or another service already able to reach the host's
loopback interface.

**REVISION 2 -- missing credential, added:** The original finding
covered only the `dune` application role. `runtime/scripts/start-postgres.sh`
also bootstraps the PostgreSQL superuser with a separate, even more
privileged, hardcoded credential: `POSTGRES_PASSWORD=postgres`. This
report did not independently re-verify that credential's own
`pg_hba.conf` reachability rules beyond confirming the same
`127.0.0.1`-only port publication applies to the whole Postgres
container (both roles are served by the same `dune-postgres` container
on the same published port) -- a full remediation must evaluate and fix
both credentials together, not just the `dune` role.

**Exploit Scenario (corrected):**

1. An attacker who already has local-host access, or who has
   compromised any container/service reachable to the host's loopback
   interface (for example, via CRIT-01's Console compromise, or an
   unrelated host-network container), can connect to PostgreSQL on
   `127.0.0.1:15432`.
2. With the default `dune`/`dune` credential (or the default
   `postgres`/`postgres` superuser credential) unrotated, they gain
   full read/write access to the game database.

**Remediation (updated per maintainer feedback):**

The remediation cannot safely consist of generating a value and writing
it only to `.env`. It must handle the actual, live database role and
every consumer of it together:

1. Generate strong credentials for new installations, for both the
   `dune` role and the `POSTGRES_PASSWORD` superuser bootstrap value.
2. Set the initial PostgreSQL and `dune` role passwords consistently at
   first-init time (not just written to `.env` after the database
   already exists with the default).
3. Preserve existing deployments -- do not break installs that already
   have the default password set and are relying on it.
4. Provide a transactional password-rotation procedure for existing
   deployments who want to rotate later.
5. Update every consumer together in the same change: Console, Director,
   Gateway, TextRouter, metrics exporter, backup tooling, and any other
   database client -- a partial rotation will desynchronize consumers.
6. Roll back automatically if any dependent service cannot reconnect
   after a rotation.
7. Test the rotation with passwords containing quotes, spaces, shell
   metacharacters, and URL-sensitive characters, since several
   consumers build connection strings via shell interpolation.
8. Never print or log generated credentials.

Changing `.env` without changing the live PostgreSQL role would cause
an outage (the application would try the new password against the
still-old role). Changing the database role first without updating
every consumer would do the same in the other direction. This needs to
ship as one coordinated, tested change -- see "Proposed Focused PRs"
at the end of this report.

**Verification:**

```bash
grep -r "dune" .env | grep DUNE_DB_PASSWORD
PGPASSWORD=dune psql -h 127.0.0.1 -p 15432 -U dune -d dune -c "SELECT 1"
docker inspect dune-postgres --format '{{range .Config.Env}}{{println .}}{{end}}' | grep POSTGRES_PASSWORD
```

### CRIT-03: Privileged cAdvisor Container with Host Filesystem Mounts

**Tracking:** `yacketrj/dune-awakening-selfhost-docker#123`

**Severity:** HIGH -- **REVISION 2: downgraded from CRITICAL.** The
privileged configuration is real and verified, but the deployment
context significantly narrows who can be affected, and no reachable
exploit path is demonstrated.

**Classification:** Architectural risk without a demonstrated exploit.

**CWE:** CWE-250 (Execution with Unnecessary Privileges)

**Affected Files:**
- `docker-compose.metrics.yml` -- `dune-cadvisor` service definition

**Description:**

The metrics stack runs cAdvisor with `privileged: true` and mounts
multiple host paths read-only:

```yaml
privileged: true
volumes:
  - /:/rootfs:ro
  - /var/run:/var/run:ro
  - /sys:/sys:ro
  - /var/lib/docker:/var/lib/docker:ro
  - /dev/disk:/dev/disk:ro
```

This is verified unchanged in upstream `4d13321`. `privileged: true`
disables seccomp/AppArmor/SELinux confinement and grants access to all
host devices regardless of the `:ro` mount flags on the volumes
themselves.

**REVISION 2 -- missing context, added.** All of the following are
verified directly against `docker-compose.metrics.yml` and
`runtime/scripts/dune`/`start-all.sh`/`install.sh` in upstream
`4d13321`:

- The metrics stack is opt-in: `docker-compose.metrics.yml` is not
  referenced anywhere in `start-all.sh` or `install.sh`. It only starts
  via an explicit `dune metrics start` subcommand.
- It does not start with the normal game stack.
- `dune-cadvisor` has **no `ports:` block at all** in
  `docker-compose.metrics.yml` -- unlike `dune-prometheus`, which
  explicitly publishes `127.0.0.1:9090:9090`, cAdvisor is not published
  to any host port and is reachable only via the internal `dune-net`
  Docker network.
- Prometheus reaches cAdvisor over that internal network, not a
  published port.
- The project's own compose file and prior commit history already
  document this as a privileged metrics collector (the `privileged: true`
  line is not hidden or unexplained in context).

A compromised, privileged cAdvisor container could still have severe
host impact if compromised -- that is a real consequence of the
`privileged: true` flag and is not in dispute. What is not demonstrated
is a reachable cAdvisor vulnerability or external attack path: there is
no CVE cited against the pinned cAdvisor version
(`gcr.io/cadvisor/cadvisor:v0.52.1`), and the container is not directly
reachable from outside the host's Docker network under the default,
opt-in configuration. The original Critical rating described
post-compromise impact, which is real, rather than demonstrated
exploitability, which is not shown here.

**Remediation (updated per maintainer feedback):**

The originally-proposed capability list (`SYS_PTRACE`, `no-new-privileges`,
etc.) must not be adopted without testing -- cAdvisor's actual required
privileges vary across Docker versions, cgroups v1 vs v2, SELinux
systems, WSL, and distribution-specific configurations, and an untested
capability set could simply break metrics collection rather than
improve security.

1. Test cAdvisor without `privileged: true` and determine the exact
   devices, mounts, capabilities, and namespaces actually required for
   this project's supported deployment targets.
2. Test on the supported Linux distributions, SELinux-enforcing
   systems, and WSL2/Docker Desktop, since metrics is documented as
   usable there.
3. Keep the metrics endpoint internal-only (already true -- preserve
   this property in any change).
4. Keep the cAdvisor image version pinned (already true -- preserve
   this property).
5. Document the expanded trust boundary explicitly in the metrics
   opt-in documentation, so operators enabling metrics understand what
   they are adding.
6. Consider a reduced-metrics mode that omits cAdvisor entirely for
   operators who want Prometheus/node_exporter metrics without the
   privileged container.

**Verification:**

```bash
docker inspect dune-cadvisor --format '{{.HostConfig.Privileged}}'
docker inspect dune-cadvisor --format '{{range .Mounts}}{{.Source}} -> {{.Destination}} ({{.Mode}}){{"\n"}}{{end}}'
docker port dune-cadvisor   # expected: no output, confirming no published host port
```

### HIGH-01: No HTTPS/TLS on Web Admin Panel

**Severity:** HIGH (unchanged)

**Classification:** Verified against current upstream. This and MED-02
are, per the maintainer's own assessment, the strongest and most
directly actionable findings in this report.

**CWE:** CWE-319 (Cleartext Transmission of Sensitive Information), CWE-311 (Missing Encryption of Sensitive Data)

**Affected Files:**
- `docker-compose.web.yml` -- `ADMIN_BIND_HOST` defaults, plain HTTP
- `.env.example` -- `ADMIN_SECURE_COOKIES=0`, `ADMIN_BIND_PORT=8088`
- `console/api/src/auth.js` -- `setSessionCookie` uses `Secure` only when `config.secureCookies` is true
- `console/api/src/server.js` -- entire API over HTTP

**Description:**

Verified unchanged in upstream `4d13321`: the web administration panel
serves all traffic over plain HTTP by default, session cookies are not
marked `Secure` by default, and there is no TLS termination anywhere in
the stack itself. A Docker-control-plane management service (see
CRIT-01) should not be casually exposed over plain HTTP to any network
an attacker might occupy -- passwords and session cookies can be
intercepted with a suitable network position, and the impact of a
stolen Console session is significant on its own, independent of
whether CRIT-01's arbitrary-Docker-execution scenario can be proven.

**Remediation (updated to preserve LAN usability, per maintainer feedback):**

1. Default the Console's bind address to `127.0.0.1` or a detected
   private/LAN address -- do not silently bind to every interface (see
   MED-02, which covers the same underlying default).
2. Make binding to a public-reachable address an explicit, deliberate
   choice, not a default.
3. Provide tested nginx and Caddy reverse-proxy example
   configurations, including WebSocket/SSE support (the Console's task
   log streaming depends on this).
4. Enable `Secure` cookies automatically when TLS is actually
   configured/detected, not just via a manually-set flag.
5. Trust `X-Forwarded-Proto` only when it comes from a configured,
   trusted proxy -- not unconditionally.
6. Add HSTS only when HTTPS is actually authoritative for the current
   deployment; do not enable HSTS on plain LAN/HTTP deployments, where
   it would be actively harmful.
7. Add startup diagnostics that show the bind address, secure-cookie
   state, and whether the configuration appears to be publicly
   reachable, so operators get direct feedback about their exposure.
8. Document VPN/Tailscale access as a supported alternative to public
   port exposure.

**Verification:**

```bash
curl -sI http://127.0.0.1:8088/api/health
curl -sI http://127.0.0.1:8088/api/health | grep -i set-cookie
```

### HIGH-02: `curl | sh` Anti-Pattern in Install Script

**Severity:** MEDIUM -- **REVISION 2: downgraded from HIGH and largely
reclassified as already remediated.** The specific patterns originally
cited no longer exist in current upstream code.

**Classification:** Already remediated upstream (Docker installer,
SteamCMD download). Verified against current upstream (README one-line
bootstrap still streams a downloaded archive into `tar`, a related but
different and lower-severity pattern).

**CWE:** CWE-494 (Download of Code Without Integrity Check)

**Affected Files (re-verified against upstream `4d13321`):**
- `install.sh` -- Docker installer download (**REMEDIATED**, see below)
- `orchestrator/dune_orchestrator.py` -- SteamCMD download (**REMEDIATED**, see below)
- `README.md` -- one-line bootstrap install command (**not remediated**, see below)

**Description (updated):**

**REVISION 2 -- `install.sh`, remediated.** The original finding cited
`install.sh:86` piping `curl` directly into `sh`. Verified in upstream
`4d13321`, this is no longer the case:

```bash
get_docker_script="${TMPDIR:-/tmp}/dune-get-docker-$$.sh"
trap 'rm -f "$get_docker_script"' 0

if ! curl -fsSL https://get.docker.com -o "$get_docker_script"; then
  echo "Could not download the Docker install script from get.docker.com." >&2
  exit 1
fi

if ! error=$(need_sudo sh "$get_docker_script" 2>&1); then
  echo "$error" >&2
  exit 1
fi
```

The script is downloaded to a temporary file first, the download's
success is checked explicitly, and only then is it executed -- with a
`trap` cleaning up the temp file afterward. A partial or interrupted
download can no longer result in partial-script execution, because the
whole file is written before `sh` ever runs it. This does **not**
authenticate the publisher beyond TLS (no independent signature or
checksum is verified) -- that remaining supply-chain gap is real and
covered in the remediation below -- but the specific "stream into a
running shell" anti-pattern this finding was named for is gone.

**REVISION 2 -- SteamCMD download, remediated.** The original finding
cited `dune_orchestrator.py:218` piping `curl` into `tar`. Verified in
upstream `4d13321`, `orchestrator/dune_orchestrator.py`'s
`ensure_steamcmd()` also downloads to a file first
(`curl -fsSL <url> -o str(tmp)`) and only then extracts it
(`tar -xzf str(tmp) -C str(STEAM_DIR)`) as a separate step -- not a
pipe. The remaining gap here is the same as the installer: no checksum
is verified against the downloaded archive before extraction, and
Valve can replace this installer archive's contents at their CDN URL at
any time without any project-side release, which needs special
handling (checksum pinning here cannot simply be "pin to the last known
release," since there is no project release involved in this download
at all).

**REVISION 2 -- README one-line install, not remediated, verified
still present.** `README.md`'s quick-start one-liner does still stream
a downloaded GitHub release archive directly into `tar -xz`:

```
_download_progress "https://github.com/Red-Blink/dune-awakening-selfhost-docker/archive/refs/tags/${version}.tar.gz" | tar -xz --strip-components=1
```

This is a different risk shape than the original finding's "partial
script executes as root" scenario -- it is a pipe into an archive
extractor, not into a shell interpreter, so a truncated stream fails
extraction rather than executing a truncated command. It still has no
integrity verification (no checksum or signature check) before
extraction, and is a real, currently-live instance of the general
"download without integrity check" class this finding is about.

**Remediation (updated):**

1. For the README one-liner: consider downloading to a file first (as
   `install.sh` now does) so a failed/truncated download can be
   detected explicitly before extraction, even though the risk here is
   lower than the original shell-execution framing.
2. Add SHA-256 checksum verification for the SteamCMD archive after
   download, sourced from a location independent of the download URL
   itself where possible.
3. Longer-term supply-chain controls worth pursuing project-wide:
   signed release metadata, build attestations, published SHA-256 files
   for project releases, or a project signing key. SteamCMD checksum
   pinning specifically needs to handle the fact that Valve can update
   that installer archive's contents at any time, independent of this
   project's own release cycle.

**Verification:**

```bash
grep -rn 'curl.*|.*sh\|curl.*|.*sudo\|curl.*|.*bash\|curl.*|.*tar' -- '*.sh' '*.py' 'README.md'
```

### HIGH-03: Self-Update Spawns Privileged Docker Containers

**Severity:** HIGH -- **REVISION 2: terminology corrected.** The helper
does not use Docker's `--privileged` flag; the original description
conflated "has Docker socket access" (true, and already root-equivalent
via CRIT-01's trust boundary) with "runs `--privileged`" (not true).

**Classification:** Architectural risk without a demonstrated exploit
independent of an already-compromised release/update channel.

**CWE:** CWE-250 (Execution with Unnecessary Privileges) -- **REVISION 2:** CWE-94 (Code Injection) removed; no injection path into the helper's command construction was found.

**Affected Files:**
- `console/api/src/tasks.js` -- `buildSelfUpdateHelperDockerArgs()`
- `runtime/scripts/self-update.sh` -- `rebuild_web_console_with_helper()`
- `runtime/scripts/update.sh` -- `install_auto_units_via_docker_host()`

**Description (corrected):**

Verified directly in upstream `4d13321`'s `buildSelfUpdateHelperDockerArgs()`:

```javascript
[
  "run", "--rm", "-d",
  "--name", helperName,
  "--user", `${hostUid}:${hostGid}`,
  "--group-add", dockerSocketGid,
  "--network", "host",
  "-v", `${hostRepoRoot}:/repo`,
  "-v", "/var/run/docker.sock:/var/run/docker.sock",
  ...
  helperImage,
  "sh", "-lc", command
]
```

**REVISION 2 -- what is verified:**

- The helper runs with a configured numeric `--user` UID/GID, not root
  by default.
- It receives Docker socket **group** access via `--group-add`, not
  the `--privileged` flag. No `--privileged` flag appears anywhere in
  this function or its shell-script equivalent.
- It mounts the repository and the Docker socket, and uses host
  networking -- this is genuinely root-equivalent in effect (Docker
  socket access always is, with or without `--privileged`), but it is
  a different and more precisely-scoped mechanism than "privileged
  containers" implies.
- The `command` string passed to `sh -lc` is constructed from
  `args = buildDuneArgs(task.operation, payload)` -- the same
  allowlisted, non-attacker-controlled operation system verified under
  CRIT-01 -- with each argument passed through `shellQuote()`
  (single-quote escaping) before interpolation into the command string.
  No caller-supplied, unvalidated shell content was found reaching this
  helper.

The supply-chain concern the original finding was pointing at remains
real and valid: **if a trusted update artifact (a GitHub release
tarball) is compromised, the update process will execute that
compromised code with access to the Docker control plane.** However,
this is true of any self-update mechanism by construction -- any
updater that applies new code must eventually run that new code. The
Docker-socket-accessible helper does not create this supply-chain
exposure; it increases the *impact* of an already-existing supply-chain
compromise from "arbitrary code as the update process's own user" to
"arbitrary code with Docker-control-plane access." That distinction
matters for prioritizing the fix: the highest-leverage remediation here
is artifact authentication (verifying what gets run), not further
restricting the helper's own already-narrow, already-allowlisted
command construction.

**Remediation (updated):**

1. Sign releases or publish independently verifiable attestations for
   release tarballs.
2. Verify checksums before extraction, sourced independently of the
   download URL where feasible.
3. Prevent downgrade to an older version unless explicitly requested by
   the operator.
4. Preserve rollback state so a bad update can be reverted.
5. Validate archive paths and file types during extraction (defends
   against path-traversal in a compromised or corrupted archive).
6. Keep update-helper inputs non-user-controlled -- this property is
   already true today (verified above) and should be preserved as a
   hard invariant in any future change to this code path.
7. Consider a host-side updater service with a narrow, well-defined
   request interface as a longer-term alternative to the
   Docker-socket-accessible helper container, if that interface can be
   designed without losing the helper's current functionality.

**Verification:**

```bash
grep -rn 'docker run.*docker\.sock\|docker run.*privileged\|docker run.*network.*host.*docker\.sock' -- '*.sh' '*.js'
docker inspect <helper-container-name> --format '{{.HostConfig.Privileged}}'   # expected: false
```

### HIGH-04: In-Memory Session Store with No Revocation

**Severity:** HIGH (unchanged) -- **REVISION 2: the underlying finding
is real and the maintainer agrees it should be fixed; several specific
technical claims within it were corrected.**

**Classification:** Verified against current upstream, with one
factual correction (this is not session fixation).

**CWE:** CWE-613 (Insufficient Session Expiration) -- **REVISION 2:** CWE-384 (Session Fixation) removed; see correction below.

**Affected Files:**
- `console/api/src/auth.js` -- `const sessions = new Map()`
- `console/api/src/auth.js` -- `makeSession()` with 12-hour expiry
- `console/api/src/auth.js` -- `readSession()` with no additional validation
- `console/api/src/server.js` -- `/api/auth/logout` route
- `console/api/src/server.js` -- `adminPasswordRoute()`

**Description (corrected):**

Sessions are stored exclusively in a JavaScript `Map` in memory,
verified unchanged in upstream `4d13321`.

**REVISION 2 -- session fixation claim, corrected.** The original
finding stated "session fixation possible" and cited CWE-384. Verified
directly: `makeSession()` generates a fresh, cryptographically random
session ID on every login --
`const id = randomBytes(32).toString("base64url")` -- with no code path
that accepts or adopts a client-supplied session identifier. Session
fixation (CWE-384) specifically requires the server to accept an
attacker-*chosen* identifier and treat it as authenticated after
victim login; that is not possible here. This claim is removed.

**REVISION 2 -- the real, verified issues, confirmed individually:**

- **Logout does not remove the server-side session.** Verified in
  `server.js`'s `/api/auth/logout` handler: it calls
  `clearSessionCookie(res, config)` (clears the browser cookie) but
  never calls `sessions.delete(session.id)`. The server-side `Map`
  entry remains valid until its own `expiresAt` elapses naturally.
- **Password changes do not invalidate existing sessions.** Verified in
  `adminPasswordRoute()`: it updates the password file and
  `config.adminPassword`, but never touches the `sessions` map. An
  attacker who obtained a session before a password change retains
  access after the change.
- **No "log out all sessions" capability** -- consistent with the
  above two findings; there is no code path that iterates and
  invalidates multiple sessions at once.
- **The expiration is a sliding window set once at session creation,
  with no separate absolute lifetime** -- verified in `makeSession()`.
- **Multiple sessions cannot be reviewed or revoked individually** --
  no endpoint was found that lists or targets individual session IDs
  for an operator to review.

**Remediation (updated per maintainer feedback):**

A persistent store (PostgreSQL, SQLite, file-based) is not automatically
necessary or safer here, and should not be treated as the only correct
fix. Restarting the Console and invalidating all sessions as a side
effect is an acceptable behavior for this application's threat model.
A simple in-memory model can remain if it supports:

1. `sessions.delete(session.id)` on logout -- the specific, minimal fix
   for the most concrete gap found.
2. A password/session generation counter, so all sessions created
   before a password change can be invalidated without tracking every
   session ID individually.
3. Revocation of all sessions on password change, using that counter.
4. An idle expiration (already present as the sliding window).
5. A separate absolute expiration, independent of activity.
6. Periodic cleanup of expired entries from the in-memory map.
7. Optional display of the current active-session count to the
   operator, for visibility without needing full multi-session
   management UI.

**REVISION 2 -- rejected remediations, per maintainer feedback:**
Binding sessions to IP address is likely to break VPN, reverse-proxy,
mobile, IPv6/privacy-address, and changing-NAT users, and should not be
a mandatory control. User-agent binding provides limited protection
because the User-Agent header is entirely attacker-controlled and
trivially replayed. Neither should be required; if offered at all, they
should be optional, clearly-labeled hardening toggles, not defaults.

**Verification:**

```bash
grep -n "sessions\s*=" console/api/src/auth.js
grep -n "sessions.delete" console/api/src/server.js   # currently expected: no output for the logout route
```

### HIGH-05: Funcom Token Exposed via Process Environment

**Severity:** MEDIUM -- **REVISION 2: downgraded from HIGH.** The file-
permissions claim in the original finding is factually incorrect for
current upstream code; the environment-variable exposure claim is real
but is a defense-in-depth concern, not equivalent to command-line
exposure.

**Classification:** Verified against current upstream for the
environment-variable exposure path (defense-in-depth). Already
remediated upstream for the file-permissions claim.

**CWE:** CWE-214 (Information Exposure Through Process Environment)

**Affected Files:**
- `runtime/scripts/init.sh` -- token passed via environment variable to a Python subprocess, and file write with `chmod 600`
- `runtime/scripts/db.sh` -- token/key passed via environment variable to a Python subprocess
- `console/api/src/config.js` -- token file location

**Description (corrected):**

**REVISION 2 -- file permissions, corrected.** The original finding
stated: "`config.js` stores the token in a plain text file at
`runtime/secrets/funcom-token.txt` with permissions `0o644`
(world-readable)." This is not accurate for current upstream code.
Verified directly in `runtime/scripts/init.sh`:

```bash
printf '%s' "$FUNCOM_TOKEN" > runtime/secrets/funcom-token.txt
chmod 600 runtime/secrets/funcom-token.txt
```

The token file is created with mode `0600` (owner read/write only), not
`0644`. Separately, `console/api/src/config.js` does use `0o644` for a
different file -- `.env` -- via its `updateEnvFileValue()` function;
`0o644` for `.env` (which is not exclusively secret content) is a
different, unrelated code path from the Funcom token's own `0o600`
write in `init.sh`. The original finding conflated the two. This part
of the finding is corrected and reclassified as already remediated
(or, more precisely, never actually broken as originally described).

**REVISION 2 -- environment-variable exposure, retained with corrected
severity framing.** Verified: `runtime/scripts/init.sh` and
`runtime/scripts/db.sh` do pass the Funcom token to Python subprocesses
via an environment variable (`TOKEN="$FUNCOM_TOKEN" python3 ...`).
Environment variables of a running process are visible via
`/proc/<pid>/environ`, but that path is readable only by the same UID
and root, subject to the host's normal `/proc` and `ptrace`
restrictions (e.g. `yama.ptrace_scope`). This is a real defense-in-depth
concern -- it is not equivalent to the token appearing in the process
*command line* (`/proc/<pid>/cmdline`), which is readable more broadly
in some configurations and shows up in tools like `ps aux` by default,
or to the token persisting in shell history, which does not apply here
since it is not typed as a literal command-line argument by a human.

**REVISION 2 -- the original remediation itself was wrong.** The
original finding's suggested fix --
`python3 script.py "$FUNCOM_TOKEN"` -- would make this **worse**, not
better: command-line arguments are visible via `/proc/<pid>/cmdline`
and standard process-inspection tools (`ps`, `/proc` browsing) more
readily than environment variables in many common configurations. This
remediation must not be implemented as originally written.

**Remediation (corrected):**

1. Prefer reading the token directly from the already-`0600` token file
   inside the subprocess, rather than passing it through the parent
   shell's environment at all, where the subprocess supports it.
2. Where inter-process handoff is required, prefer stdin or an
   inherited file descriptor over both environment variables and
   command-line arguments.
3. Avoid exporting the token into long-lived container environments
   unless required by an official upstream (Funcom) image that only
   accepts it that way.
4. Ensure all backup copies of the token file retain `0600` (verify
   this holds through `self-update.sh`'s backup/restore paths, which
   also reference this file).
5. Redact token-derived values from logs and diagnostics (verified:
   `logs.sh` already redacts this specific file path from log output).
6. Never print the token directly.

**Verification:**

```bash
ls -la runtime/secrets/funcom-token.txt   # expected: -rw------- (0600)
grep -rn 'TOKEN=.*python3\|TOKEN=.*python' -- '*.sh'
```

### MED-03: Database Connection Without TLS (sslmode=disable)

**Severity:** LOW -- **REVISION 2: downgraded from MEDIUM.** Verified
as defense-in-depth given the actual network path, not a priority
vulnerability.

**Classification:** Defense-in-depth recommendation.

**CWE:** CWE-311 (Missing Encryption of Sensitive Data)

**Affected Files:**
- `docker-compose.metrics.yml` -- `sslmode=disable` on the Postgres exporter connection
- `console/api/src/db.js` -- no SSL options in connection config

**Description (corrected):**

Verified unchanged in upstream `4d13321`. **REVISION 2 -- context
added, per maintainer feedback:** the exporter's connection occurs
entirely on the internal `dune-net` Docker network, and the Console's
own database connection is host-local (`127.0.0.1`). An attacker
capable of sniffing either of these paths would already need to control
the host, the Docker network namespace, or another privileged container
on that network -- at which point they very likely already have direct

defense-in-depth gap, not a priority vulnerability given the actual
verified network topology.

connection string, as the original finding suggested, **will fail
outright** unless PostgreSQL is separately configured to speak TLS at
all. Additionally, `sslmode=require` encrypts the transport but does
not verify server identity -- it does not protect against an
active on-path attacker who can also intercept and re-terminate the
connection. A complete implementation needs, together:

1. PostgreSQL server certificates.
2. A managed CA or a pinned certificate.
3. Correct hostname/SAN validation on the client side.
4. A certificate rotation plan.
5. `sslmode=verify-full` where practical, not just `require`.
6. Compatibility testing against the official PostgreSQL image and
   every actual client (Console, exporter, backup tooling, and any
   other consumer).

Do not ship a connection-string-only change for this finding.

**Verification:**

### MED-04: CSRF Token Bypass on GET Requests

**Severity:** INFORMATIONAL -- **REVISION 2: downgraded from MEDIUM.**
This describes a correct, standard security invariant that already
holds, not a vulnerability.

**Classification:** Already remediated upstream / not a vulnerability
as originally framed -- reclassified as an invariant to protect with a
regression test.

**CWE:** CWE-352 (Cross-Site Request Forgery) -- kept for reference; not asserting this CWE currently applies.

**Affected Files:**
- `console/api/src/auth.js` -- `requireAuth()` CSRF check

**Description (corrected):**

Verified unchanged in upstream `4d13321`: the CSRF token check is only
enforced for non-`GET`/`HEAD`/`OPTIONS` methods. **REVISION 2 -- this
is the correct behavior, not a weakness.** Standard CSRF protection is
specifically required for state-changing methods; `GET`, `HEAD`, and
`OPTIONS` are defined by RFC 7231 and OWASP ASVS guidance as expected
to remain safe and read-only, and requiring a CSRF token on every `GET`
would be non-standard and would make normal navigation, downloads, and
browser caching meaningfully harder for no security benefit, provided
the invariant that no `GET` route mutates state actually holds.

This report reviewed the `GET`-method route handlers in `server.js`
(downloads, exports, list/read endpoints) and found no route that
mutates state under `GET`, consistent with the report's own
acknowledgment that "the current API uses non-GET methods for
mutations." No code change is warranted here; this is now classified
as an invariant worth protecting with a regression test rather than a
finding to remediate.

**Remediation (corrected -- protect the invariant, don't add
unnecessary controls):**

1. Add a regression test that asserts no `GET`/`HEAD` route in
   `server.js` performs a database write, file write, or process
   spawn, so a future regression is caught automatically.
2. Continue enforcing CSRF for `POST`/`PUT`/`PATCH`/`DELETE` as today.
3. Keep `HttpOnly` on session cookies (already true).
4. Keep or explicitly re-review the existing `SameSite=Lax` setting on
   its own merits, rather than as part of this finding.
5. A Content-Security-Policy header is a reasonable future addition,
   but only after an explicit audit of the current frontend's inline
   scripts/styles, workers, images, and the addon execution model,
   since a strict `script-src 'self'` cannot be safely added without
   that review -- do not add this blindly as part of closing this
   finding.

**Verification:**

```bash
grep -n "req.method.*GET\|path.*===.*&&.*req.method" console/api/src/server.js | grep -v "auth\|health\|static"
```

### MED-05: Sensitive Values Passed via Shell Command Arguments

**Severity:** LOW -- **REVISION 2: downgraded from MEDIUM, and
significantly narrowed in scope.** As originally written, this grouped
many unrelated shell operations together and asserted each was
independently exploitable, which is not demonstrated.

**Classification:** Defense-in-depth recommendation. Needs
case-by-case re-analysis rather than a blanket rule, per maintainer
feedback.

**CWE:** CWE-214 (Information Exposure Through Process Environment)

**Affected Files:**
- `install.sh` -- password handling around `echo`/`printf`
- `runtime/scripts/config.sh` -- `sed -i` for `.env` values
- `runtime/scripts/ensure-public-ip.sh` -- `awk -v`
- `console/api/src/tasks.js` -- `shellQuote(command)` in the self-update helper (see HIGH-03 -- this is the already-reviewed, already-allowlisted command construction, not a separate exploitable instance)

**Description (corrected):**

**REVISION 2 -- per maintainer feedback, this finding should identify
exact values and actual exposure paths instead of grouping unrelated
shell operations together as if they were uniformly risky.** Some of

instance originally listed; doing so is the concrete next step before
any code change here, since a mechanical "never use `sed`/`awk -v`/env
vars for secrets" rule is not itself a safe or complete fix, and could
introduce new regressions the way the original HIGH-05 remediation
would have.

**Remediation (narrowed):**

1. Atomic file replacement (write to a temp file, then `mv`) and
   `umask 077` are useful, low-risk improvements where compatible with
   existing behavior, and can be applied without the full
   per-instance analysis above.
2. Do not treat every `sed`, `awk -v`, or Docker environment-variable
   use in this codebase as an independently exploitable Medium
   finding -- that overstates the case for most of them without the
   analysis above.
3. Complete the seven-point analysis per instance before proposing
   specific code changes, and handle official-image environment-variable
   requirements as a hard constraint, not an oversight to "fix" away.

**Verification:**

```bash
grep -rn 'sed -i.*password\|sed -i.*token\|sed -i.*secret' -- '*.sh'
```

## Positive Security Observations

The project demonstrates several good security practices, several of
which were directly confirmed (not just asserted) during this
revision's re-verification:

1. **Input validation** -- confirmed: named validator functions
   (`validateServiceName`, `validateNumber`, `validateServerTitle`, and
   others) are used throughout `runner.js` before values reach process
   execution.
2. **Allowlisted operation dispatch** -- **newly confirmed in this
   revision:** every traced HTTP route reaching `buildDuneArgs()` uses
   a hardcoded literal operation name, a boolean choice between two
   hardcoded literals, or a client-supplied key validated against a
   fixed map with explicit rejection of unmapped values. No route was
   found where client input becomes the operation name itself.
3. **`shell: false` process spawning** -- **newly confirmed in this
   revision:** all `spawn()` calls reviewed in `runner.js` and
   `tasks.js` use argument arrays with `shell: false`, not
   shell-string concatenation.

   `web-admin-audit.jsonl` via `audit.js`.
5. **Rate limiting** -- login attempts are rate-limited via
   `rateLimit.js`.
6. **Security headers** -- `nosniff`, `DENY` framing, `no-referrer`,
   restrictive permissions policy.
7. **Secret redaction** -- stdout/stderr output is sanitized via
   `redact.js`; confirmed this also covers the Funcom token file path
   specifically in `logs.sh`.
8. **SQL injection protection** -- parameterized queries throughout
   `duneDb.js`.
9. **Path traversal protection** -- `safeAddonRelativePath()` and
   `installedAddonContentPath()` validate paths.
10. **Cryptographically random session IDs** -- **newly confirmed in
    this revision:** `randomBytes(32)` per session, refuting the
    original session-fixation claim under HIGH-04.
11. **Pre-commit security hooks** -- `.pre-commit-config.yaml` with
    gitleaks, shellcheck, trivy.
12. **CI security checks** -- `ci.yml` runs security scans (gitleaks,
    trivy, semgrep).
13. **SHA-256 verification** -- community addon downloads are verified
    against manifest hashes.

## Command-Auth-Token Report (Companion Document)

**REVISION 2, added in this pass:** This audit's Critical/High findings
above are about the Console's own web-facing surface. A related,
separate report,
`docs/security/command-auth-token-vulnerability-and-failed-remediation.md`,
covers a different mechanism: the RabbitMQ server-command envelope's
`AuthToken` field. The maintainer's response also addressed that report
directly; the key corrections, verified in this revision, are:

- **The core technical conclusion is correct and verified:** the
  command envelope's `AuthToken` is validated by the Funcom
  Director/game consumer independently of RabbitMQ itself. Verified in
  `console/api/src/rmq.js`'s `publishServerCommand()`/`commandAuthToken()`
  and confirmed against the actual revert history:
  `runtime/scripts/admin-tools.sh` and `console/api/src/rmq.js` both
  still contain a built-in fallback constant
  (`BUILTIN_COMMAND_AUTH_TOKEN = "Nu6VmPWUMvdPMeB7qErr"`), and this was
  deliberately restored by the upstream maintainer in commit `52008a7`
  ("Restore built-in command auth token fallback," 2026-07-07, verified
  as an ancestor of current upstream `main`) after an earlier
  generated-token change broke command channels for deployments whose
  game-server side still expected the original built-in value.
- **Do not reintroduce automatic random token generation** without a
  synchronized mechanism to update the Director/game-server side at the
  same time -- this is exactly what caused the prior revert.
- **"Live vulnerability" was insufficiently qualified.** Verified in
  this revision: `publishServerCommand()` does not publish via a normal
  RabbitMQ producer connection reachable over the network -- it invokes
  `rabbitmqctl eval` *inside the RabbitMQ container itself* via
  `docker exec` (`dockerExec()` in `rmq.js`, using
  `spawn("docker", args, { shell: false })`). This means using this
  specific code path already requires Docker-exec access to the
  RabbitMQ container -- the same trusted, Console-level access CRIT-01
  covers -- not merely knowledge of the `AuthToken` value. A remote
  attacker without that access would need a separate path: reach
  RabbitMQ's own network-facing ports, authenticate through RabbitMQ's
  configured auth backend (verified elsewhere in this codebase as
  `rabbitmq_auth_backend_http`, not a default guest account --
  `loopback_users.guest = false` is set), obtain permission to publish
  to the relevant exchange, and construct a message the Funcom consumer
  accepts. This report should demonstrate that full chain or describe
  it explicitly as a plausible residual risk rather than an
  already-demonstrated "live vulnerability."
- **The firewall mitigation needs qualification, not blanket
  application.** RabbitMQ's game/service ports may need to remain
  externally reachable depending on the specific public/NAT deployment
  topology and the addresses advertised to Funcom's own services.
  Binding them to localhost or restricting them by guessed source IP
  without first observing and documenting real connection sources could
  break game services outright.
- **The stale documentation issue is confirmed and should be corrected
  immediately, separately from any functional token change.**
  `docs/security/generated-command-auth-token.md` describes the
  reverted generated-token architecture ("Architecture After") as
  though it were the currently active, safe state. It is not: the
  built-in fallback constant is present and active in current upstream
  `main` today (verified above). This document should be corrected to
  state plainly: the generated-token implementation was reverted, the
  project currently retains the built-in compatibility token by
  deliberate maintainer decision, producer-only token rotation breaks
  command handling for the reasons in commit `52008a7`, and local token
  generation must not be restored without a corresponding
  consumer-side synchronization mechanism.

The safe path forward proposed by the maintainer, agreed with here:

1. Determine whether the Director or world-server image supports any
   undocumented expected-token override mechanism.
2. Inspect configuration, symbols, environment-variable naming
   conventions, and startup arguments for such a mechanism.
3. Test a synchronized value on a disposable, non-production
   deployment.
4. Publish a harmless test command through the normal path.
5. Verify the actual expected game/database/log side effect occurred
   -- not merely that RabbitMQ reported a successful publish.
6. Restart all affected components and retest for persistence across a
   restart.
7. Revert immediately if any command channel stops functioning.
