# Discord Sign-In Setup Wizard: Guided App Creation + Hard HTTPS Gate — L1 Design

**Date:** 2026-08-30
**Status:** L1 design, revision 2. Revision 1 received a full Eight Hats Layer 1 audit (8 independent dispatches) — see §6 for the findings register and what changed in this revision.
**Tracking issue:** `dune-awakening-selfhost-docker#641`.
**Originated from:** live-testing feedback during PROMPT 2 validation of the layered-auth upstream PRs. Distinct, separate feature from #634 (the IAM Visual Editor) — this document only concerns the Discord OAuth **setup** wizard (`DiscordSetupWizard.tsx`'s "connect" step), not Access Control.

---

## 1. Why

Live operator testing of the guided Discord sign-in setup wizard surfaced two real gaps in its very first "connect" step (reached before any Discord OAuth configuration exists at all):

1. **The step tells the operator to SSH into the host and hand-edit `.env`**, even though the wizard's own *later* step (role mapping) already automates `.env` writes and a full restart-and-reconnect cycle, and a *separate* part of the console (`SettingsPanel.tsx`, reachable only after this initial setup is already done) already has a working form for the exact same Client ID/Secret values, calling the exact same backend routes. The automation already exists; it's just not present at the one point in the flow where an operator most needs it.
2. **The HTTPS requirement is a small warning paragraph, not a hard gate.** An operator can click "Continue with Discord" over plain HTTP and get a confusing, unrelated-looking downstream failure ("invalid or expired") instead of a clear reason.

Two clarifications, verified directly, shape this design's scope (§3):
- **Discord OAuth does not require the console to be reachable by Discord's own servers for the redirect** — the browser-facing part of the flow is entirely browser-redirect-based. It does, separately, require the console's **own backend** to make an *outbound* call to `discord.com` for the token exchange and identity/guild lookup (confirmed in `console/api/src/integrations/discord/oauth.js`/`config.js` — `DISCORD_OAUTH_BASE_URL`) — an operator with locked-down egress would still see this fail. (Corrected in this revision — see §6, Network finding #3.)
- **TOTP (Tier 3) has no network dependency at all** — irrelevant to this design, noted only for context.

## 2. Verified current state — two baselines (2026-08-30)

**On `main`@`c4b248ad`:**
- `console/api/src/server.js` already has `POST /api/setup/write-oauth-config` and `POST /api/setup/save-oauth-secret` (lines 993-994, handlers `writeOAuthConfig`/`saveOAuthClientSecret`), both redacting the secret in their audit log entries.
- `console/web/src/features/settings/SettingsPanel.tsx` already has a working `saveDiscordOAuth()` calling both routes.
- **`DiscordSetupWizard.tsx` does not exist on `main` at all** — the guided setup wizard is `tier1-upstream`-only.

**On `tier1-upstream`@`291f71fc`:**
- `DiscordSetupWizard.tsx` (185 lines) implements a 4-step flow (`connect` → `authorize` → `map` → `done`), derived live from server state on every mount/refresh — no frozen client-side step tracking, by deliberate design (the component's own header comment), so a refresh always resumes correctly.
- The `connect` step (shown when `!app?.configured`) currently renders two separate HTTPS-related paragraphs: one **conditional** on `!isHttps` (line 127), and one **unconditional**, always shown regardless of protocol (line 128), which also references "the console sign-in guide for standing up a reverse proxy or tunnel" — **confirmed this session that no such document exists anywhere in this repo** (checked `docs/`, `README.md`, `docs/operator-guide.md`, `docs/rfc-console-auth.md` — a dangling reference; see §6, GRC finding). Both paragraphs are superseded by this design (§4.2).
- The redirect URI shown (`` `${window.location.origin}/api/auth/discord/callback` ``, line 19) is computed dynamically, not hardcoded.
- **`SettingsPanel.tsx`'s real `saveDiscordOAuth()` (lines 260-276) sends *seven* keys** to `write-oauth-config` (`DISCORD_OAUTH_CLIENT_ID`, `DISCORD_OAUTH_REDIRECT_URI`, `DISCORD_HOME_GUILD_ID`, and four role/MFA fields), always populated from its own fully-hydrated local state — this is broader than what the wizard's `connect` step has state for (only Client ID + Secret; the guild/role fields belong to the wizard's later `map` step, a *different* endpoint, `discord-finalize`). **This matters directly**: `writeOAuthConfig`'s own partial-update safety (`if (body[key] === undefined) continue;`) is safe only if a caller omits untouched keys entirely, not if it sends them as blank strings — and this codebase has already hit and fixed exactly this bug once. `discordSetupFinalize`'s own comment (server.js, `tier1-upstream`) records it verbatim: *"`DISCORD_OAUTH_ALLOW_OWNER_BOOTSTRAP` is deliberately NOT written here... unconditionally forcing it... on every run silently clobbered an operator's already-configured bootstrap allowlist... The sibling manual path (`writeOAuthConfig`) already gets this right by only writing keys the request body actually includes — match it."* §4.1 now states this constraint explicitly, citing this exact precedent (Eight Hats Architect finding, §6).
- The `map` step already POSTs to `/api/setup/discord-finalize`, and `done` already has a full restart-and-reconnect flow (`restartNow()`, polling `/api/auth/state` for up to 3 minutes) — the automation §4.1 reuses.

**Implementation depends on `tier1-upstream` (the whole branch — `DiscordSetupWizard.tsx` only exists there), same explicit merge-gate discipline as #634:** confirm directly (`git grep DiscordSetupWizard main`) before beginning implementation, don't assume.

## 3. Scope

**In scope:**
1. Replace the `connect` step's static "SSH in and hand-edit `.env`" instructions with a guided flow: ask whether the operator already has a Discord application; branch to either a direct form or an assisted app-creation path; either way, land on the same Client ID/Secret form, reusing the existing `write-oauth-config`/`save-oauth-secret` routes — **sending only the two keys this step actually manages, as genuinely omitted fields, never blank strings** (§4.1; resolves Architect HIGH, §6).
2. For the "I need to create one" branch: link to Discord's Developer Portal, opened in a new tab via the **same safe `<a target="_blank" rel="noreferrer">` pattern already used everywhere else in this exact component and codebase** (not a raw `window.open()` call — resolves Security Architect MEDIUM, §6), with an independent `visibilitychange`/`focus` listener providing a soft, non-blocking "welcome back" nudge — never a hard gate on detecting the other tab closed.
3. Replace the HTTPS warning paragraphs with an **unconditional blocking panel** when `!isHttps`, shown before any of item 1's content, self-sufficient (no dangling reference to a non-existent guide — the in-panel guidance *is* the guidance): three free options (Cloudflare Tunnel, Tailscale, ngrok), each with a real, actionable next step and an honest statement of its own limitations (§4.2).
4. Keep the "you must also add this exact redirect URI to the application's OAuth2 redirect list" instruction, and the existing "use a dedicated application, not your bot's" warning, prominent and co-located with the input fields in **both** branches of item 1 — not left in a separate paragraph that could be scrolled past (resolves UI/UX HIGH re: wrong-application risk, §6).
5. A minimal test suite for the parts of this design that are mechanically testable (§4.3) — this design's own review found it had specified none at all in revision 1 (QA HIGH, §6).

**Explicitly out of scope:**
- **Automating tunnel provisioning itself.** A separate, larger, security-sensitive feature (a new trust boundary — a process exposing the host to the public internet, triggered from a web UI) deserving its own L1 design.
- **Verifying the redirect URI is actually registered in Discord's portal**, or **detecting a self-signed vs. real certificate** (the HTTPS check remains protocol-only, `window.location.protocol === "https:"`, unchanged from today — Discord itself never validates the console's certificate; only the signing-in browser does, at the redirect step, which is why this is a UX-level check, not a security boundary — see §4.2's explicit reframing, resolving Security Architect LOW, §6).
- **Verifying which Discord application a pasted Client ID/Secret actually belongs to.** Discord's API doesn't support introspecting a Client ID's ownership from just the credentials themselves; §4.1's prominent, co-located warning (item 4 above) is the achievable mitigation, not a technical verification.
- **Changing `SettingsPanel.tsx`.** It already works and remains the correction path if an operator needs to fix a mistake after this wizard's `connect` step has already advanced past the form (§6, DBA finding — a real but low-severity gap: the wizard itself has no "go back" affordance once configured, but the operator is never stuck, since they remain authenticated and `SettingsPanel.tsx` reaches the identical routes).

## 4. Design

### 4.1 Guided app-creation flow

Replaces the current static instructional block. New local component state: `appPath: "unset" | "have-app" | "need-app"`.

**This is a deliberate, narrow exception to the component's own "never freeze step state client-side" principle** (Architect + UI/UX both independently flagged this, §6) — acknowledged explicitly rather than silently introduced. Impact is bounded: a same-session refresh while away creating the application resets `appPath` to `"unset"`, costing one redundant click (both values converge on the identical form; no data loss, since an unsubmitted form is lost on refresh regardless).

**Initial sub-step (`appPath === "unset"`):** two buttons, "I already have a Discord application" / "I need to create one."

**Both sub-steps render the same Client ID/Secret form.** Save calls `POST /api/setup/write-oauth-config` with **exactly** `{ DISCORD_OAUTH_CLIENT_ID, DISCORD_OAUTH_REDIRECT_URI }` — no other key present in the body at all (see §2/§3 above for why) — then `POST /api/setup/save-oauth-secret` with `{ secret, overwrite }` when a secret was entered, matching `SettingsPanel.tsx`'s existing call shape for exactly these two routes. On success, re-run `probe()` (the wizard's existing state-refresh function) so the step machine advances naturally once the server reports `discordOAuthAppConfigured`.

**Both sub-steps also show, immediately adjacent to the input fields (not only in a separate paragraph):**
- The redirect URI + "must also be added to the application's OAuth2 redirect list" instruction (existing content, unchanged).
- **"Use a dedicated application for the console, not your bot's — the application's name and icon are what people see on Discord's sign-in screen."** (Retained verbatim from the existing static text, now co-located with the form in both branches rather than only in the pre-redesign instructional block, since this is the design's only real mitigation against the wrong-application risk the UI/UX hat identified — §6.)

**`appPath === "need-app"` additionally** shows a short, numbered checklist for what to do on Discord's site (resolves UI/UX MEDIUM re: no in-wizard guidance, §6): "1. Click New Application. 2. Name it for your server/console (not your bot). 3. Open the OAuth2 tab. 4. Copy the Client ID and generate/copy a Client Secret. 5. Add the redirect URI shown here to the Redirects list." The link itself is the existing safe anchor pattern (§3 item 2) pointing at `https://discord.com/developers/applications` (the general list — Discord has no documented stable deep-link to the creation flow; confirm at implementation time, don't assume otherwise, per §5 Q1). The focus/visibility listener sets a `returnedFromDiscord` flag on first return-to-tab, rendering a small "Welcome back — paste your new application's Client ID and Secret below" note; the form is fully usable in both sub-steps regardless of whether this listener ever fires.

### 4.2 Hard HTTPS gate

Computed identically to today (`isHttps = window.location.protocol === "https:"`), checked before rendering any step-specific content, including before §4.1's `appPath` branch — but **explicitly scoped as a UX-level control, not a security boundary** (revision from "no way to bypass" framing — resolves Security Architect LOW, §6): reaching this step already requires an authenticated owner session, so this gate's purpose is preventing a confusing, wasted round-trip, not enforcing a privilege boundary. This scope note is now stated directly in the design rather than implied.

**Placement clarified (resolves Architect/UI/UX LOW re: ambiguous scope, §6): this check gates only the `connect` step's content** (before Discord OAuth is configured at all) — it does not re-run on every step, so it cannot discard in-progress state in the later `authorize`/`map`/`done` steps (reaching those already implies a completed HTTPS round-trip).

When `!isHttps`, render a blocking panel:
- A clear statement that Discord sign-in requires HTTPS and this page isn't currently loaded over it.
- **Three free options, each with a concrete next step and an honest limitation** (resolves UI/UX MEDIUM "options may not be self-sufficient," and Network's two MEDIUM findings about specific option accuracy, §6):
  - **Cloudflare Tunnel** — a "quick tunnel" (`cloudflared tunnel --url http://localhost:<console-port>`) needs no account and gives an instant `*.trycloudflare.com` HTTPS address; fine for completing this setup, but **its address changes on every restart** — for day-to-day reliability, move to a named tunnel (needs a Cloudflare account + a domain in their DNS) afterward. (Not described as "this project's own pattern" — an earlier draft of this design made that claim, which this project's own `docs/rfc-console-auth.md` directly contradicts: *"this project has a large, globally-distributed self-hosted operator base, most of whom do not run Cloudflare Tunnel/Access at all"* — corrected, GRC HIGH, §6.)
  - **Tailscale HTTPS certificate** (`tailscale cert`) — if the console is already reached over Tailscale, this issues a real HTTPS cert scoped to the tailnet-only address, with **no public exposure at all**; the right choice if only tailnet members need to sign in. **Tailscale Funnel** (a different feature, public exposure) is only needed if someone outside the tailnet must complete the OAuth round-trip too — listed as a secondary option, not the default recommendation (revised from recommending Funnel outright — Network MEDIUM, §6).
  - **ngrok** — free tier works; requires creating an ngrok account and configuring a personal authtoken before first use (not mentioned in revision 1 — Cloud Security LOW, §6); the URL changes on restart unless paid.
  - A one-line disclaimer beneath all three: "These are independent third-party services; this project doesn't operate, endorse, or provide support for them." (Resolves GRC's open question about a disclaimer, §5 revision 1 Q3 — now answered, not left open, §6.)
- **A persistent "still not working after trying one of these?" note** pointing at the same three options and reminding the operator a page reload re-checks — not a dead end after a failed first attempt (resolves UI/UX HIGH, §6). No separate written troubleshooting guide is introduced; this panel's own content is the authoritative in-product guidance, replacing the dangling "see the console sign-in guide" reference that pointed at a document that was never written (GRC finding, §6).

### 4.3 Testing plan (absent from revision 1 — QA HIGH, §6)

- **Unit test for the `write-oauth-config` payload shape**: assert the connect-step form's save call includes *only* `DISCORD_OAUTH_CLIENT_ID`/`DISCORD_OAUTH_REDIRECT_URI` — no other key present, not even as `""` — directly regression-pinning the Architect finding (§2/§4.1). This is the highest-value test in this plan, since it protects against a bug class this codebase has already shipped and fixed once.
- **Unit test for `envFile.js`'s `updateEnvFileValue` under this exact call pattern**: a fresh/near-empty `.env` with sequential single-key writes (mirroring `writeOAuthConfig`'s `for (const [key, value] of Object.entries(fields))` loop) — this design routes the coldest possible `.env` state through that exact loop shape for the first time at real scale; the blank-line bug this function was fixed for earlier this session should have an explicit regression test covering this specific trigger, not just the general case (DBA LOW, §6).
- **Unit test for the HTTPS gate**: renders/blocks under a mocked `http:` protocol, does not under `https:` (QA MEDIUM, §6) — this line of code ships today with zero test coverage even in its current warning-only form; raising it to a hard, no-escape-hatch gate raises the cost of a misclassification enough to warrant a first test.
- **`window.open`/focus-nudge mechanism (§4.1): split into a testable and an accepted-manual-QA-only part** (QA HIGH, §6 — jsdom's `visibilitychange` doesn't reflect real tab-switching behavior, and no test anywhere in this codebase exercises this browser-API class, confirmed by a full-suite grep). The *link* itself uses the existing `<a href=... target="_blank" rel="noreferrer">` pattern (§4.1/§3), which is trivially testable the same way every other external link in this codebase already could be (assert the `href`) — write that test. The *focus-nudge rendering* (dispatching a synthetic `visibilitychange` and asserting the "welcome back" note appears) is accepted as manual-QA-only for this revision, stated explicitly here as a declared limitation rather than a silent gap, consistent with how §3's other non-goals are handled.

## 5. Open questions for Layer 2 review

1. Does Discord in fact have an undocumented-but-stable deep-link URL to open the "create new application" flow directly? Check at implementation time; §4.1 falls back to the bare applications-list URL if not.
2. Is a protocol-only HTTPS check sufficient long-term, given a self-signed certificate satisfies it while Discord's own redirect works fine regardless (§4.2's own reframing as a UX-level, not security, control)? Left as a genuine, lower-priority follow-up rather than blocking this design.
3. Should a real, written HTTPS/reverse-proxy setup guide eventually be written (Requirement 14), superseding the inline three-option panel (§4.2) as the single source of truth once this project's documentation has more capacity — or is the inline panel the project's deliberate, permanent answer? Not decided here; §4.2 is written to be self-sufficient either way.
