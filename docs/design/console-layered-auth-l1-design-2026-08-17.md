## 1. Why this is a third draft, and what's different

Two real, independent problems, each caught by a different Layer 1 audit pass, forced this redesign:

1. **Draft 1 (#327)** made Discord OAuth the sole primary login and depended on Cloudflare Access to solve "several admins, one identity source." The Cloud Security hat found Cloudflare Access sits in front of the tunnel and gates reachability *before* the console's own login ever runs — a new admin added only via a Discord role change still hits Cloudflare's own edge gate first, so the "one identity source" goal was not achieved, only relabeled. Separately, the Security hat found `oauth.js`'s `resolveOAuthTier()` falls open to a static, env-configured owner allowlist whenever the bot's role-resolution handoff is unreachable — a real, already-shipped availability-attack-to-privilege-escalation bug, made worse by making Discord OAuth the sole primary.
2. **Draft 2 (#329)** replaced Discord OAuth with WebAuthn/passkeys as the sole primary, specifically to remove both the Cloudflare dependency and the Discord-availability dependency. The Network hat found this doesn't work at all for this project's own recommended deployment pattern: WebAuthn requires a "secure context" (HTTPS or literal `localhost`), and this project's own `r740-dune-deployment-kit/docs/02-network-setup.md` explicitly recommends reaching the console over **plain HTTP through a VPN tunnel**, with no port-forward and no reverse proxy — an access pattern where `navigator.credentials.create()`/`.get()` are simply unavailable in the browser, full stop, regardless of anything the console's own code does. The Cloud Security and UI hats also independently found that draft never actually specified how a *second* admin gets onboarded — only the very first owner's setup flow was designed.

**This document's actual change, in one sentence:** stop trying to pick one login mechanism to be "the" primary, and instead layer three independently-optional mechanisms so each operator's real deployment determines which one they actually get, with the weakest one (shared password) reduced to pure break-glass and the two stronger ones each remaining available exactly when they're actually usable:

- **Tier 1 — Discord OAuth, fixed, the realistic default for most operators.** No new requirement over what exists today. The only change is closing the fail-open bug (§4.1) — this is a small, surgical fix to already-shipped code, not a rearchitecture.
- **Tier 2 — Passkeys, opt-in, only reachable when the operator has TLS somewhere in the path.** Off by default (an unset config value, not an auto-detected one — see §4.2 for why auto-detection is explicitly rejected). Once on, any already-authenticated admin can add a passkey to their *own* identity from the settings panel — this is what actually resolves the "how does a second admin get onboarded" gap, at no extra design cost, because the primary onboarding mechanism (Discord role assignment) already handles "who is an admin," and passkey registration becomes a self-service *add-on* an existing admin does for themselves, never a separate invite flow that needed inventing.
- **Tier 3 — Password + mandatory TOTP + recovery codes, universal, always available.** Unchanged in spirit from earlier drafts' break-glass framing, kept genuinely tertiary.

## 2. Verified current state (2026-08-17, checked against `main`@`f81399e7`)

- **The fail-open bug, precisely characterized** (correcting this document's own predecessor's imprecise paraphrase, per the Security hat's finding on draft 2): `resolveBootstrapTier()` (`oauth.js:158-183`, quoted verbatim, not paraphrased, since a design document making a security claim about existing code should show the real function):
  ```js
  export function resolveBootstrapTier({ userId, guildIds, allowOwnerBootstrap, homeGuildId, ownerAllowlist = [] }) {
    if (!allowOwnerBootstrap) return "";
    if (!homeGuildId) return "";
    if (!guildIds.includes(homeGuildId)) return "";
    if (!ownerAllowlist.includes(userId)) return "";
    return "owner";
  }
  ```
  This requires **four** simultaneous conditions, not "any Discord user": bootstrap must be explicitly enabled (`DISCORD_OAUTH_ALLOW_OWNER_BOOTSTRAP=1`, default unset/false), a home guild must be configured, the caller must still be a member of that guild, and the caller's snowflake must be in a static allowlist env var. The real bug is narrower than "wide open" but still genuine: `resolveOAuthTier()` (`oauth.js:166-183`) calls this function as a fallback **whenever `handoff.resolveTier()` returns an empty string for any reason** — network timeout, bot down, malformed response, stale timestamp, signature mismatch (`handoff.js:75-117`, confirmed exhaustively: every failure branch returns `""`, with no distinction between "Discord/bot is unreachable" and "this specific user's tier is genuinely empty/denied"). An operator who runs with bootstrap enabled (a real, supported, documented configuration — not a misconfiguration) and later revokes someone's Discord role, but doesn't also remember to prune the static allowlist env var (no UI, no reminder, an easy miss), has that person's access silently restored to owner the moment the bot handoff has any hiccup at all — a bot restart, a network blip, a deliberate DoS against the bot.
- **The fix does not require any new persistence, caching, or grace window** — this document's immediate predecessor (draft 2, §4.3) proposed caching "the last successfully-resolved tier... for a grace window," which both the Security hat (introduces a new stale-privilege-during-active-demotion window, not closing the bug so much as narrowing its trigger condition) and the QA hat (requires a `now()`-injection seam that doesn't exist yet in `oauth.js`, unlike the sibling `isFresh()` check in `handoff.js` which already has one) found genuinely problematic. Verified: `createOAuthTierResolver`, `resolveBootstrapTier`, and `resolveOAuthTier` are **pure, stateless functions** — `resolveOAuthTier` takes only `{userId, guildIds}` per call and has no notion of "an identity was previously resolved." The actual, simpler fix (§4.1) needs zero new state: it's a one-line change to *when* the bootstrap fallback is consulted at all, not a caching layer.
- **Two existing tests currently assert the exact behavior being removed** (a gap the QA hat found draft 2 never mentioned): `console/api/test/handoff.test.js`, two tests — `"createOAuthTierResolver falls back to bootstrap when handoff returns empty"` (line 299) and `"createOAuthTierResolver falls back to bootstrap when handoff is disabled"` (line 335) — both currently assert `tier === "owner"` for exactly the fall-through case this document removes for the *first* of those two tests (handoff configured but failing) while correctly leaving the *second* (handoff never configured at all) as still-valid, unchanged behavior — see §4.1 for why these are different cases and why only one test needs to change, not both.
- **No WebAuthn-capable code, dependency, or database exists anywhere in this repo** (unchanged finding from draft 2's audit, still accurate): `grep -rln "webauthn\|WebAuthn\|passkey"` across `console/api/src` and `console/web/src` returns zero matches; `console/api/package.json`'s only dependency is `pg`; `console/web/package.json` has no QR/crypto/auth-adjacent dependency.
- **No admin-console-specific local identity concept exists today** (unchanged from draft 2's audit): every `grep` hit for `adminAccount`/`AdminUser`/`admin_user` resolves to the unrelated in-game player-account domain (`duneDb.js`, `carePackage.js`, `systemPersonas.js`).
- **This console has no TLS anywhere in its own code** (the Network hat's key finding against draft 2, independently re-verified here): `console/api/src/server.js` uses plain `node:http`'s `createServer` — confirmed via grep, zero `https.createServer`/`tls.createServer`/certificate-loading code exists anywhere in `console/api/src`. `docs/security/audit-2026-07-04.md`'s HIGH-01 finding ("No HTTPS/TLS on Web Admin Panel") is still open/unremediated at the app layer; TLS, where it exists at all in any real deployment of this console, is added by the *operator*, not the app (a reverse proxy, or a VPN client that happens to terminate HTTPS locally) — this document does not change that, it only makes passkey availability conditional on the operator having done so.

## 3. Scope

**In scope:**
1. Fix the fail-open bug in `resolveOAuthTier`/`resolveBootstrapTier` (§4.1) — small, surgical, no new state.
2. Add opt-in passkey support, gated by an explicit, operator-set config value (never auto-detected) confirming a secure context exists (§4.2).
3. Self-service passkey registration for any already-authenticated admin, onto their own identity — this is what replaces "invite flow" as the second-admin-onboarding mechanism (§4.2).
4. Make the password fallback (Tier 3) genuinely tertiary: mandatory TOTP, real recovery codes, correctly-scoped session invalidation on rotation (§4.3).
5. Naming the recovery-code hash function explicitly (a gap both prior audits found unresolved) (§4.3).
6. Explicit backup/restore guidance covering the new failure modes this design introduces: stale-recovery-code resurrection, and passkey signature-counter rollback risking a false-positive cloning-lockout (§4.3, §6 — the DBA hat's CRITICAL finding against draft 2).

**Explicitly out of scope, and why (several of these are deliberate corrections from draft 2's overreach, not new deferrals):**
- **A local admin-identity record with its own credential-linking schema, as draft 2 proposed (`admin-identities.json`).** This document does not need one: Discord OAuth remains the primary identity source (as it already is today), and a passkey is registered *onto an existing, already-Discord-authenticated session* rather than onto a new, parallel local-identity concept. This removes an entire category of findings from both prior audits (the DBA hat's signCount-race and mixed-sensitivity-storage findings, the Architect hat's "does this fit existing patterns" finding, the GRC hat's "first-ever local identity system" framing) not by resolving them, but by not needing the mechanism that created them. See §4.2 for the concrete, much smaller schema this actually requires.
- **Any Cloudflare-specific mechanism of any kind** — unchanged from draft 2's correct decision on this point.
- **Solving the shared-rate-limit-bucket-behind-a-reverse-proxy problem generically** — still deferred (unchanged from draft 2), but see §7 for the Network hat's finding (against draft 2) that this project's own recommended access pattern (VPN, not an HTTP-terminating proxy) mostly avoids this problem in practice, which narrows the real-world urgency of the deferral.
- **Multi-instance/clustered console deployment** — unchanged, still out of scope, still consistent with this console's actual single-process architecture (re-verified: `server.js`'s single `createServer(...).listen(...)` call, no clustering anywhere).

## 4. Design

### 4.1 Tier 1 fix: Discord OAuth's fail-open bug, closed with no new state

**The actual fix**: `resolveOAuthTier` currently falls through to `resolveBootstrapTier` whenever `handoff.resolveTier()` returns `""`, for *any* reason. The fix is to only consult the bootstrap fallback when the handoff is **not configured at all** (`handoff.enabled === false`) — never when it's configured but the specific call failed:

```js
// oauth.js — createOAuthTierResolver, current shape:
export function createOAuthTierResolver({ bootstrap = {}, handoff = null } = {}) {
  return async function resolveOAuthTier(identity) {
    const { userId, guildIds } = identity;
    if (handoff && handoff.enabled) {
      const tier = await handoff.resolveTier({ userId, username: identity.username });
      if (tier) return tier;
    }
    return resolveBootstrapTier({ userId, guildIds, ...bootstrap });
  };
}

// Fixed:
export function createOAuthTierResolver({ bootstrap = {}, handoff = null } = {}) {
  return async function resolveOAuthTier(identity) {
    const { userId, guildIds } = identity;
    if (handoff && handoff.enabled) {
      // Handoff is configured: its result is authoritative. An empty
      // result means "deny" (bot unreachable, or bot said no), not
      // "fall through to the static allowlist" — the allowlist exists
      // only to bootstrap the very first owner on an install that has
      // never configured a handoff at all, not to survive an outage
      // once one is configured. See issue history: resolveBootstrapTier
      // used to also run here on handoff failure, which meant a stale
      // or unpruned DISCORD_OAUTH_OWNER_ALLOWLIST silently restored
      // owner access the moment the bot handoff had any outage,
      // regardless of the person's current, real Discord role.
      return handoff.resolveTier({ userId, username: identity.username });
    }
    return resolveBootstrapTier({ userId, guildIds, ...bootstrap });
  };
}
```

- **This is the entire fix.** No cache, no grace window, no new persisted state, no `now()`-injection seam needed anywhere — `handoff.enabled` is already a static, boot-time-computed boolean (`handoff.js:27-33`: `disabledHandoff()` vs `liveHandoff()`, chosen once at `createHandoff()` call time based on whether `secret`/`botUrl` are configured, `server.js:88-92`).
- **Operator-facing consequence, stated explicitly**: once an operator configures the bot handoff (`DISCORD_BOT_HANDOFF_SECRET`/`DISCORD_BOT_HANDOFF_URL`), the static owner-allowlist bootstrap (`DISCORD_OAUTH_OWNER_ALLOWLIST`) stops being consulted at all for that operator, permanently, as long as the handoff stays configured — including during a bot outage, which now means "no one can get a *new* Discord-tiered session until the bot is back," not "anyone on the allowlist gets owner regardless of their real current role." This is the correct, intended trade — availability drops (temporarily, during an outage) instead of security dropping (permanently, until someone notices and prunes the allowlist) — and should be stated plainly in the operator-facing docs for this change (`docs/security/console-rbac-implementation-and-testing.md` needs updating in the same PR, per Requirement 14) so an operator who *wants* the old degraded-but-available behavior understands the trade being made on their behalf and why.
- **Residual availability note, added per a targeted second-pass audit finding**: this fix makes every *new* Tier-1 login fully dependent on a live, successful handoff call within its existing 5-second timeout (`handoff.js:23,82`) — a single dropped packet, slow DNS resolution, or brief bot restart now denies all new Discord-tiered logins for anyone, not just the previously over-privileged bootstrap-allowlist case, with zero retry and no distinction between "transient blip" and "bot genuinely down." **This does not affect already-active sessions** — session cookies are validated against the in-memory `sessions` Map (`auth.js:48-61`) on every request, never re-checked against the handoff, so an admin already logged in before an outage begins stays logged in through it; only *new* logins during the outage window are affected. This should be stated in the same operator-facing doc update as the point above, so an operator experiencing "I can't log in with Discord right now" during a bot restart understands why and knows to wait or use Tier 3, rather than assuming something is broken.
- **Existing test impact, addressed explicitly** (the QA hat's finding against draft 2 — this section exists specifically because that finding does not get to be silently true a second time): `handoff.test.js`'s `"createOAuthTierResolver falls back to bootstrap when handoff returns empty"` (line 299) constructs a `handoff` that is **configured but failing** (`fetchImpl: mockFetchError()`, `botUrl` set) — this test's assertion (`tier === "owner"`) is exactly the old, removed behavior and **must be rewritten** to assert `tier === ""` instead, with an updated test name (e.g. `"createOAuthTierResolver denies, does not fall back to bootstrap, when a configured handoff fails"`). `handoff.test.js`'s `"createOAuthTierResolver falls back to bootstrap when handoff is disabled"` (line 335) constructs a `handoff` with `secret: "", botUrl: ""` — i.e., **never configured at all** — this is exactly the case the fix still correctly falls through for, and this test's assertion (`tier === "owner"`) remains correct, unchanged, and should be kept as-is (perhaps with a comment noting it was independently re-verified as still-valid during this change, not just untouched by accident).

### 4.2 Tier 2: opt-in passkeys, gated on an explicit, operator-set secure-context confirmation

**The gate, and why it's a config value, not auto-detection:**

```
WEBAUTHN_RP_ID=console.example.com
```

Unset by default (byte-identical behavior to today — no passkey routes are even registered if this is unset, matching this codebase's existing convention for other fully-optional features like Discord OAuth itself, `server.js:234-237`'s warning pattern). When set, this string becomes the WebAuthn Relying Party ID, and — critically — **the operator setting it is itself the confirmation that a secure context exists**, rather than the console trying to infer this from request headers (which would reintroduce exactly the "trust a header" problem draft 1's Cloudflare-specific rate-limit mechanism had, per that audit's Security and Network hat findings — this design deliberately does not repeat that pattern here). An operator who sets `WEBAUTHN_RP_ID` without actually having TLS anywhere in the path will simply find that passkey registration fails in the browser (`navigator.credentials.create()` throws or is `undefined`) — a clear, immediate, client-side failure with no security consequence (nothing server-side trusted a false claim), not a silent vulnerability.

**What "TLS somewhere in the path" concretely means for this project's real operators, stated explicitly since the previous draft's Network-hat audit found this needed spelling out:** the console itself never needs to terminate TLS — an operator can put a reverse proxy (nginx, Caddy — this project's own `docs/security/audit-2026-07-04.md` HIGH-01 remediation already recommends providing example configs for exactly this) in front of it with a real or self-signed certificate, or use a VPN client that happens to expose a local HTTPS endpoint, or (for the narrowest case) access the console via literal `localhost`/`127.0.0.1` if it's running on the same machine the browser is on. **The plain-HTTP-over-VPN pattern this project's own docs currently recommend as the primary hardening guidance does not, on its own, satisfy this** — an operator following that exact guidance today gets Tier 1 (Discord) and Tier 3 (password/TOTP) available, and Tier 2 (passkeys) unavailable until they additionally add a TLS-terminating layer. This is stated as a real, permanent limitation of this deployment pattern for this specific feature, not a bug to fix later.

**Self-service registration — the actual second-admin-onboarding answer:**
- New route, `/api/settings/passkeys/register-start` + `/register-finish`, reachable from **any already-authenticated session, regardless of tier** — this is a deliberate, precedented authorization shape, not an ad hoc bypass of the RBAC model (a targeted second-pass audit correctly flagged the first version of this section as an unprecedented "any tier can call a settings route" pattern with no stated enforcement mechanism, since every existing `/api/settings/*` route requires owner — `policy.js:217-221` explicitly `Deny`s `settings:*` for admin, and never grants it to moderator/player/observer at all, confirmed via `policy.js:181-287`).
- **The correct, already-established precedent for this exact shape already exists in this codebase, just on the Discord-adapter side, not the console-session side**: `console/api/src/integrations/discord/policy.js`'s `SELF_SCOPED_CAPABILITIES` (`PLAYER_LINK_WRITE`, `ACCOUNT_LINK_WRITE`) are capabilities explicitly carved out of the normal tier-ladder (`CAPABILITY_BY_TIER`) specifically because "every route that checks it always passes `discordUserId = actor.userId`, never a separate target... gating it by role tier either over-restricts... or over-grants" (verbatim rationale, `policy.js:24-32`), checked via a separate function (`requireSelfScopedCapability()`) that "only requires the actor to be a recognized... principal... and always operates on that actor's own identity."
- **This design applies the identical pattern to the console's own session-based policy engine** (`console/api/src/policy.js`, the AWS-IAM-style Deny>Allow>default-Deny engine, not the Discord-adapter one — a parallel but structurally similar system): a new, distinct action namespace, `self:passkey-register` / `self:passkey-remove`, deliberately **outside** the `settings:*` namespace and **not evaluated through `evaluate()`/the tier-statement engine at all** — checked by a new, small, dedicated `requireSelfScopedAction(req, res)` helper (mirroring `requireSelfScopedCapability`'s exact shape) that only confirms `auth.requireAuth(req, res)` succeeds (i.e., any valid, non-expired session of any tier) before proceeding, and the route handler itself always operates on `req.authSession.userId`, never a caller-supplied target — closing the exact gap the audit found, using this codebase's own existing, precedented pattern rather than inventing a new one.
- **§6 updated accordingly**: since this is a new action type outside the existing tier-ladder rather than a change to any tier's default policy, no existing operator's `iam-policies.json` (if customized) needs migration, and no tier's default `Allow`/`Deny` statements change — the self-scoped check is a separate gate, run instead of (not in addition to or blended with) the normal `evaluate()` call, exactly as `requireSelfScopedCapability()` already does for the Discord adapter.
- **Registration is only reachable from an already-authenticated session** (any tier, any `authMethod`) — there is no separate "invite a new admin" flow to design, because admin*ship* itself is still governed entirely by Tier 1 (Discord role/handoff) or the Tier 3 bootstrap allowlist, exactly as today. Passkey registration only ever answers "how does an *already-recognized* admin get a stronger login for themselves" — it never answers "how does someone become an admin at all," which is correctly a question this document doesn't need to solve because Tier 1 already solves it.
- **Storage, deliberately minimal** — no new `admin-identities.json`, no new local-identity concept (per §3's scope decision). A passkey credential is stored keyed by the `userId` already present on every session (`auth.js:43`'s existing `{tier, userId, username, guildId}` shape) — a new, small file, `runtime/generated/webauthn-credentials.json`, written via the existing `writeJsonAtomic()` (`jsonStore.js:10`, same function `policy.js` already uses for `iam-policies.json`), shaped as:
  ```json
  {
    "version": 1,
    "credentials": [
      { "userId": "...", "credentialId": "...", "publicKey": "...", "signCount": 0, "label": "work laptop", "createdAt": "..." }
    ]
  }
  ```
  This is deliberately much smaller than draft 2's `admin-identities.json` — it has no `tier`, no `linkedDiscordUserId`, no recovery codes, no TOTP pointer — because tier/authorization is still Discord's job (Tier 1) or the shared break-glass credential's job (Tier 3), never the passkey record's job. A passkey login (`/api/auth/passkey/login-start`/`-finish`) authenticates *who* the person is (their `userId`, matched against a stored credential), then looks up their **current** tier the exact same way a fresh Discord login would (re-running `resolveOAuthTier` for that `userId`) — meaning a passkey login is always as fresh/correctly-tiered as a live Discord login would be, and a demoted admin's passkey does not grant a stale tier, closing the exact class of concern the Security hat raised against draft 2's cache design, without needing a cache at all.
- **Origin/RP-ID binding, addressed as a documented, permanent operator constraint, not a code-level problem to solve:** since `WEBAUTHN_RP_ID` is a single, operator-chosen, static value, an operator who wants passkeys usable from more than one access path (e.g. both a VPN-internal hostname and a public DNS name) must choose one canonical hostname and always use that one for passkey purposes — consistent with, and explicitly citing, this project's own existing documented preference (`r740-dune-deployment-kit/docs/04-post-standup-hardening.md`, item 3: "Alternatively, skip the public hostname entirely and only reach the console via the... VPN... simpler, one less moving part"). This document does not attempt the multi-origin-array trick draft 2's audit surfaced as a *possible* mitigation (`@simplewebauthn/server`'s `expectedOrigin` accepting an array) — it's a real option, deliberately not taken here, in favor of the simpler, single-canonical-hostname operator expectation this project already establishes elsewhere.

**Dependency, named concretely (not deferred, per the UI hat's finding that draft 2's "TBD" framing for supporting libraries wasn't sufficient rigor for an L1 document):**
- `@simplewebauthn/server` (npm, MIT, `13.3.2` at time of writing, 8 well-scoped transitive dependencies for CBOR/ASN.1/X.509 parsing — verified via `npm view`) + `@simplewebauthn/browser` (MIT, zero dependencies, verified via `npm view`) for the registration/authentication ceremonies. This pairing is the correct call specifically *because* it's genuinely small in scope now (no attestation-trust-anchor configuration, no FIDO Metadata Service integration — `attestationType: "none"` in the standard flow, which the Cloud Security hat's audit confirmed keeps the library's own network-capable code paths (`isCertRevoked`, `MetadataService`) entirely unreached; this document explicitly commits to never enabling either).
- QR-rendering for TOTP setup (Tier 3, §4.3) needs its own small library — named concretely here rather than deferred a third time (per the UI hat's repeated finding against draft 2 that "to be confirmed at L2" was not real L1 rigor): **`qrcode`** (npm, MIT, zero runtime dependencies in its browser bundle) for `console/web`.

### 4.3 Tier 3: password + mandatory TOTP + named-hash recovery codes, correctly-scoped session invalidation

This section is materially unchanged in intent from draft 2's §4.4, with the specific gaps both prior audits found now closed:

- **TOTP is mandatory on this path**, not optional — since this credential's only remaining job (once Tier 1/2 exist) is break-glass recovery, the cost of always requiring a second factor is negligible while the benefit (this being explicitly the highest-value, least-frequently-used target on the system) is unchanged from draft 2's reasoning.
- **Recovery codes: 10, single-use, and — closing a gap both the Security and DBA hats independently flagged against draft 2 as unresolved — hashed with `scrypt` (Node's built-in `crypto.scryptSync`, confirmed available on this project's actual Node floor, `engines.node: ">=18.19.0"`, and on the Node 20/22 versions this repo's own CI actually runs; no new dependency, consistent with this document's stated preference for hand-rolling narrow primitives from Node's stdlib over adding a dependency where one isn't needed), never a bare fast hash like SHA-256, since recovery codes are short, human-typed strings with much lower entropy than a passkey private key and would otherwise be offline-brute-forceable from a stolen file.**
  - **Explicit parameters, not Node's bare defaults** (a gap the targeted second-pass audit found: Node's `scryptSync(password, salt, keylen)` with no options defaults to `N=16384`, measurably below OWASP's current minimum recommendation of `N=131072, r=8, p=1` for this use case — and using OWASP-strength parameters requires an explicit `maxmem` override, confirmed directly: `scryptSync(..., {N:131072, r:8, p:1})` throws `ERR_CRYPTO_INVALID_SCRYPT_PARAMS` ("memory limit exceeded") against Node's default 32MiB `maxmem`, while `{N:131072, r:8, p:1, maxmem:256*1024*1024}` succeeds, confirmed working, ~430ms per hash — an acceptable one-time cost for a break-glass action that happens at most a handful of times per install's lifetime). This document specifies the exact parameters (`N=131072, r=8, p=1, maxmem=256MiB`) rather than "use scrypt" alone, precisely so an implementer following this document doesn't reach for the weaker, throwing-free default.
  - **A random, per-code salt** (16 bytes, `crypto.randomBytes(16)`, stored alongside each code's hash — recovery codes are generated in a batch of 10 per regeneration event, and each gets its own independent salt, not one shared salt for the batch, to prevent a single cracked salt from accelerating an attack against the other 9).
  Consuming a code triggers forced TOTP+password re-setup on that same login (closing the "what if you lose the TOTP device too" gap the very first draft's GRC audit found CRITICAL).
- **Session invalidation on break-glass credential rotation, re-scoped correctly** (the Security hat found draft 2's `authMethod`-scoped design was a real regression — a stolen passkey/Discord session could rotate the break-glass password without losing its own access, worse than draft 1's blunt global clear, which at least self-limited by killing the attacker's own session too). **Fixed design:** rotating the break-glass password/TOTP clears every session **except** the one performing the rotation, **and** requires that acting session to re-prove its own credential (re-enter the current password, or re-tap a passkey) immediately before the rotation is accepted — not just trusted from an existing cookie. This closes both problems at once: legitimate concurrent admins are logged out (as intended, a real credential-rotation event), and a session-hijacking attacker cannot use a stolen session alone to entrench a credential rotation, because the rotation itself demands fresh proof of possession, independent of session state.
- **`audit()` calls specified for every new state-changing action** (a gap the GRC hat found draft 2 left almost entirely unaddressed, calling out the dropped `auth.password-changed.sessions-revoked` call from draft 1 as an actual regression): `settings.totp-setup`, `settings.totp-regenerated`, `settings.recovery-codes-regenerated`, `auth.recovery-code-consumed`, `auth.password-changed.sessions-revoked`, `settings.passkey-registered`, `settings.passkey-removed` — each following the existing `audit(config, req, "<action>", {...})` pattern already used 126 times across `server.js`.
- **Backup/restore guidance, addressing the two new integrity-specific edge cases the DBA hat found draft 2 left entirely unaddressed** (both distinct from the generic "old secrets become live again" framing draft 2 already had):
  1. **Consumed recovery-code resurrection**: restoring `runtime/generated/` (where recovery-code consumption state lives) from a backup taken before a code was used silently un-consumes it. Documented, explicit operator guidance (added to `runtime/scripts/db.sh`'s own backup/restore help text, and the operator-facing security docs, in the same change): *after any restore, regenerate the entire recovery-code set, unconditionally* — not "if you suspect compromise," always, since a restore's very purpose is to roll back state, and consumption-state is exactly the kind of state a restore is expected to roll back whether the operator thinks about it that way or not.
  2. **Passkey signature-counter rollback risking a false cloning-lockout**: `@simplewebauthn/server`'s authentication verification correctly treats a `signCount` that isn't strictly increasing as a cloning signal (per the library's own documented behavior). Restoring an old `webauthn-credentials.json` after a passkey has since been used rolls the *server's* recorded counter backward relative to the *authenticator's* actual internal counter, risking a legitimate device's next login being flagged as cloned. **Documented mitigation, matching the WebAuthn ecosystem's own standard guidance for this exact, known, non-novel scenario:** after any restore, an owner-only settings action (`/api/settings/passkeys/reset-counters`) accepts the *next* successful assertion's counter as the new trusted baseline for that credential, rather than requiring full re-registration — this is a small, explicit, one-time recovery action, not a design-time-unsolved problem left to an operator's support thread.
- **Rate limiting on this path is unchanged, kept exactly as it exists today** — this document does not attempt the generic reverse-proxy-aware fix draft 1 tried and dropped (§3's scope decision), for the same reasons draft 2 already gave, now additionally supported by the Network hat's finding (§7) that this project's own recommended VPN-based access pattern mostly avoids the specific shared-bucket collision this gap describes in practice.

## 5. Data/persistence

- **No Postgres schema change** (confirmed, unchanged from both prior audits — `duneDb.js` has zero admin-identity/credential-related tables).
- **One new flat file** (`runtime/generated/webauthn-credentials.json`, §4.2), materially smaller in scope than either predecessor draft's persistence design, storing only what Tier 2 needs (credential ID, public key, sign count, label — no tier, no recovery codes, no TOTP secret, no linked-account concept). Written via the existing `writeJsonAtomic()`.
- **`signCount` read-modify-write safety**, the HIGH finding the DBA hat raised against draft 2 (an intra-process, cross-request race on a full-file rewrite): **addressed explicitly**, with the mechanism corrected after a targeted second-pass audit found this document's first attempt cited the wrong precedent (`addonJobs.js`'s `running` boolean guards whole background-job *executions*, seconds-to-minutes long, triggered by a single-threaded tick loop — not concurrent *HTTP requests* racing on one file's read-modify-write, a differently-shaped problem). The correct, closer precedent, confirmed by that same audit, is `server.js:2972-2980`'s base-delete-queue lock: **a synchronous placeholder-write reserved before the first `await`**, specifically closing a queue-then-check race for one resource across concurrent requests — the same shape this design needs.
  - **Concrete mechanism, specified explicitly** (the audit's other finding: the first draft of this section left "flag vs. queue, reject vs. block" unstated, which is not implementer-ready): a module-level `Promise` chain acts as a serializing queue, not a bare boolean. Each request appends its own read-modify-write operation to the tail of the chain (`writeQueue = writeQueue.then(() => doReadModifyWrite(...))`) and awaits its own link — this means concurrent requests are **queued and both eventually succeed, in arrival order**, never rejected outright and never silently dropped, which avoids the undisclosed "what does the second admin's browser see" UX gap the audit flagged for a reject-based design. Given passkey logins are infrequent, human-paced events (not a high-throughput path), a simple in-process queue adds negligible latency in the ordinary case and only actually serializes on genuine same-instant collisions.
- **TOTP secret and recovery-code hashes remain in `runtime/secrets/`**, following the existing `_FILE` convention (`discordBotHandoffSecret`'s pattern, `config.js:249`) for the live TOTP value, and the named `scrypt` hash (§4.3) for recovery codes — kept separate from the small `webauthn-credentials.json` file, since (per the Architect hat's finding against draft 2) this project's actual established convention is "credential material gets its own file regardless of comparison direction," not "only live-value secrets need separation" — this document's much smaller Tier-2-only file doesn't mix in any Tier 3 credential material at all, sidestepping that finding entirely rather than needing to argue around it.
- **Single-process safety**, re-confirmed unchanged (`server.js`'s single `createServer(...).listen(...)`, no clustering anywhere in the Dockerfile/compose file).
