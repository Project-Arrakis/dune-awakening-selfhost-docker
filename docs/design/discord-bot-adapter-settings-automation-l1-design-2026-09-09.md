# Discord Bot Adapter Setup Automation (Settings UI) — L1 Design

**Date:** 2026-09-09 (revised same day to incorporate Layer 1 Eight-Hats audit findings — see §7)
**Status:** L1 design, drafted through a direct brainstorming dialogue with the operator (architectural path, per this org's brainstorming process). A real, dispatched Eight-Hats audit (8 independent agent reviews, not a solo pass) has been run against the first draft of this document; every CRITICAL/HIGH finding has been resolved directly in the sections below, not deferred. See §7 for the full findings register, STRIDE table, and resolution status.
**Scope:** a new Settings UI section in Core that automates enabling the Discord bot adapter — token generation, `.env` writes, and applying the change — replacing the current fully-manual process. Applies identically regardless of whether the operator ends up connecting the hosted "Sahir Venn" bot (repos `mentat`/`mentat-link`) or a self-hosted instance of the same bot code; Core's side of this is unaware of which.
**Explicitly out of scope (v1):** automating the live-stats-sharing opt-in (a separate, lower-priority manual `.env` burden using the same underlying mechanism — deferred as a fast-follow once this path is proven); a live Discord role picker (would require Core to hold its own Discord OAuth scope for browsing an operator's server, a materially bigger feature); any change to `mentat`/`mentat-link` code (this design touches Core only — the two follow-up doc updates named in §7 are the only cross-repo surface); a tested, automated bot-side token-reconnection procedure (§7 Finding L — Core-side rotation is in scope, the bot re-paste step remains a manual, documented procedure, tracked as a named follow-up, not silently assumed solved).

---

## 1. Problem statement

Confirmed by direct investigation (not assumed): Core already has a full, real backend for the Discord bot adapter — ~40 routes under `/api/integrations/discord/*` (`console/api/src/integrations/discord/`), bearer-token auth, role-ID-based tier mapping — but **zero frontend UI for configuring any of it**. Enabling the adapter today, for *both* the hosted and self-hosted bot paths, requires an operator to:

1. Hand-edit Core's `.env` to set `DUNE_DISCORD_ADAPTER_ENABLED=true` and `DUNE_DISCORD_ADAPTER_TOKEN_FILE=...`
2. Generate the token file themselves (`openssl rand -hex 32 > runtime/secrets/discord-adapter-token.txt`)
3. `chmod 600` it
4. **Recreate** (not just restart) the console container
5. Copy the resulting token value into wherever the bot side needs it (mentat's hosted setup-portal form, or their own self-hosted bot's `.env`)

This is real, current friction confirmed against `mentat`'s own `docs/installation-guide.md` and `src/setupServer.js` (the hosted setup portal's own inline copy walks the operator through exactly these five steps before it can accept a token). Core has zero awareness that this friction exists on its own side — the burden is identical whether the operator is heading toward the hosted bot or self-hosting.

Core's Settings page (`console/web/src/features/settings/SettingsPanel.tsx`) already has a structurally similar section — "Discord OAuth" — for a *different* purpose (console admin login via Discord, not the bot adapter). That section is a useful template for **form/layout conventions only** — its actual save behavior (`saveDiscordOAuth()`: `POST /api/setup/write-oauth-config` → "Restart console for changes to take effect," no automated recreate) is exactly the manual-restart friction this design exists to eliminate, and must **not** be copied (Eight-Hats Architect finding, §7).

## 2. Why "real automation" is feasible without new risk

The blocking technical question for any UI-driven `.env` change is: **a running container never re-reads its own env vars**, so writing a new value has no effect until the container is recreated — and a process cannot cleanly recreate its own container from inside itself.

Confirmed directly: this exact problem is already solved in this codebase, for the "Updates" nav item. Core's console container has the Docker socket mounted (`docker-compose.web.yml`, with an explicit existing warning comment about the trust this implies), and `console/api/src/tasks.js`'s `buildSelfUpdateHelperDockerArgs()` launches a **detached, ephemeral sibling helper container** (`docker run -d --rm`, survives the console's own teardown) that runs `runtime/scripts/self-update.sh`.

**Correction from the original draft (Eight-Hats Architect + Network findings):** `self-update.sh`'s existing console-rebuild path (`rebuild_web_console_now()`) is **not** a bare recreate — it unconditionally runs a full `docker compose build` (with its own real npm-registry/Debian-mirror network dependency) before `up -d --force-recreate`. There is no existing buildless-recreate entry point to parameterize. This design does **not** propose modifying `self-update.sh` to add one (that script is load-bearing for every operator's real version updates; adding a new conditional branch to it is a materially riskier change than this feature needs). Instead:

**This design adds a new, small, additive script** (`runtime/scripts/apply-console-env.sh`, or equivalent — exact name is an implementation detail, not a design commitment) that:
- Shares the lock file with self-update (renamed `runtime/generated/console-recreate.lock`, acquired via the same `flock` pattern `self-update.sh` already uses) so the two mechanisms can never race against each other or interleave `.env` writes (Eight-Hats Architect finding — mutual exclusion).
- Runs **only** `docker compose -f docker-compose.web.yml up -d --force-recreate <service>` — no build step, no version check, no GitHub API calls.
- Writes status using the **same status-file writer logic** `self-update.sh` uses internally (`self_update_write_status`/`self_update_on_exit`), extracted into a small shared shell library (`runtime/scripts/lib/run-status.sh`) both scripts source — avoiding a second, drifting copy of that logic (Eight-Hats Architect finding).

The frontend side reuses more directly, but with one required extension (§7 Finding I): on "Apply Console Update," the UI persists the in-flight task to `localStorage` (`persistUpdateTask`) *before* polling begins, and recovers it on mount (`loadPersistedUpdateTask`) — this is what lets an operator reload the page or reopen Settings mid-recreate and see accurate progress instead of a stale "Disabled" toggle. **This design explicitly reuses that persistence-and-recovery mechanism, not just the polling/progress UI**, keyed under its own distinct `localStorage` key (e.g. `arrakis.discordAdapterEnableTask`).

**Completion detection is different from Updates and must not reuse its exact logic** (Eight-Hats Architect finding): Updates' polling loop decides "the recreated console is back" by comparing the reported version against an *expected new* version — that signal doesn't exist here, since this design deliberately doesn't change the image. Instead, this design's status-file schema includes an explicit `succeeded`/`failed` terminal state written by the helper script itself once `docker compose up -d --force-recreate` returns; the frontend's first `/api/auth/state` poll only begins after the status file reports `succeeded`, plus a short fixed settle delay (to let the new process finish its own startup sequence, including the schema-verification step described in §4).

No new trust boundary is introduced: the docker-socket access this relies on is the same one already shipped and accepted for self-update.

## 3. Proposed design

### 3.1 Frontend

A new "Discord Bot" section added to `SettingsPanel.tsx`, next to (not replacing) the existing unrelated "Discord OAuth" section, following that section's own form/layout conventions only (see §1's correction). A one-line disambiguation is shown under the section heading — "For bot commands and in-game data access — not console admin sign-in, see Discord OAuth below" — to prevent the two adjacent, similarly-named sections from being confused (Eight-Hats UI/UX finding).

**Before rendering any state below, the section always reads live state first** (§3.2's GET route) — never assumes "never configured" as a default. This is the fix for the most-converged finding across this audit (independently flagged by the UI/UX, GRC, and QA/Test hats): **an operator who already has the adapter manually configured must never see a false "Disabled" state, and must never have their existing, live-connected token silently overwritten.**

Concretely, the section now asks one up-front question and has four states, not three:

- **Read state on mount** — GET `/api/settings/discord-bot` returns the adapter's actual current configuration, read the same way the existing "Discord OAuth" section reads its config (via the module-level `loadConfig()` singleton already used elsewhere in `server.js`, not a new per-request `.env`-parsing path). If `DUNE_DISCORD_ADAPTER_ENABLED` is already `true` (however it got set — this UI or a manual edit before this feature existed), the section renders directly into the **Enabled** state below with the *existing* role-ID values populated into the inputs, never a blank/fresh form. The destructive "generate + write a new token" action is reachable **only** through the explicit "Regenerate Token" button in the Enabled state — never as a side effect of the page simply detecting an already-enabled adapter.
- **Disabled** (only when genuinely never configured) — an up-front choice, "Which are you using?" (Hosted bot / Self-hosting), then "Enable Discord Bot Integration." The choice tailors the copy shown throughout the rest of the flow (not just a link at the end — Eight-Hats UI/UX finding: a bare pair of post-generation links underserves the non-technical audience `mentat`'s own installation guide already goes to real lengths for, with a comparison table, a decision helper, and a QR code).
- **Enabling** — confirm dialog. If this is the operator's first-ever successful adapter enable (detected via the same one-time legacy-schema-migration marker described in §4), the dialog copy includes a one-time note recommending a database backup first, since this specific transition can trigger a real data migration (see §4). Otherwise, a plain yes/no (no player-aware check needed — this never touches the game server). On confirm: the same persisted-task + status-file-polling progress UI Updates already presents (see §2's extension).
- **Enabled** — the current token, masked with reveal/copy; a "Regenerate Token" action requiring a **typed confirmation** ("type REGENERATE to continue"), matching this codebase's own existing precedent for irreversible high-consequence actions (`saveAutoGame()`'s `"SAVE AUTO GAME UPDATES"` literal-string confirmation) rather than a plain dismissable warning dialog — a plain warning was judged too weak for an action with no undo (Eight-Hats UI/UX finding); plain-text role-ID inputs (Observer/Moderator/Admin, validated per §3.2 — no Owner field, matching `discordActorTier()`'s existing real-guild-ownership-only Owner rule); and the tailored next-step guidance from the up-front hosted/self-hosted choice.

### 3.2 Backend

New route(s) under `/api/settings/discord-bot` (`GET` current state; `POST` enable/configure; `POST .../regenerate-token`).

**IAM action (Eight-Hats finding, independently raised by three hats — Architect, Cloud Security, and Security Architect):** this route is **not** gated by the generic `settings:write` action. This codebase already has a precedent for exactly this situation — the self-update/apply-stack route uses its own distinct action, `updates:apply`, specifically because it triggers the same docker-socket detached-helper mechanism, separate from the broad `settings:write` bucket an operator might grant to a delegated admin for unrelated, lower-risk reasons (web port, public-directory info). This route is gated by `updates:apply` for the enable/regenerate actions (the ones that actually launch the helper); the read-only GET may use `settings:write` (or no elevated action at all beyond authenticated-session, matching how the read side of "Discord OAuth" is scoped) since it has no docker-socket-adjacent capability.

**Command-construction constraint (Eight-Hats CRITICAL finding, Security Architect):** a latent shell-quoting bug exists in the *existing* helper-launch code (`tasks.js`'s log-echo line nests an already-`shellQuote()`-wrapped value inside an outer double-quoted shell string, so `$(...)` command substitution would still be honored by the shell) — currently unexploitable only because today's sole caller (`selfUpdateApply`) passes hardcoded arguments. **This design's implementation must never route any admin-supplied value (role IDs, token contents, or anything else) into the helper's `args`/command string.** The helper is invoked with a fixed, non-parameterized argv whose only job is `docker compose up -d --force-recreate <service>` against a server-side-hardcoded service name. All admin-supplied values go **only** into `.env` via the existing, already-safe `updateEnvFileValue()` path (which correctly uses `JSON.stringify`-based quoting, not shell interpolation). The pre-existing `tasks.js` quoting bug itself should be fixed as part of this implementation regardless (it's a real, if currently dormant, defect in shared infrastructure) — tracked as part of this feature's implementation, not a separate deferred item, since this feature is what makes it reachable in principle.

**`.env` write scope and validation (Eight-Hats MEDIUM findings, Security Architect):**
- The route writes a server-side **hardcoded** set of keys only — `DUNE_DISCORD_ADAPTER_ENABLED`, `DUNE_DISCORD_ADAPTER_TOKEN_FILE`, `DISCORD_OBSERVER_ROLE_IDS`, `DISCORD_MODERATOR_ROLE_IDS`, `DISCORD_ADMIN_ROLE_IDS`. The env-key name is never derived from a request-body field name.
- Each submitted role ID is validated server-side against `/^\d{15,21}$/` (Discord snowflake format) before being written; invalid input is rejected with a clear error, not silently written.
- All keys for one save are written via a **staged-buffer-then-flush** pattern (build the full new key/value set in memory, then perform the writes as a tight sequence with no intervening async work, mirroring the pattern `self-update.sh`'s own `merge_env_keys_from_backup` already uses for multi-key `.env` updates) — the detached helper is only launched after every write in the batch has been confirmed, so a mid-batch process kill can't leave `.env` with only some of the new keys applied (Eight-Hats DBA finding).

**Token generation**: same convention the manual docs already describe (`crypto.randomBytes`-equivalent to `openssl rand -hex 32`), written to `runtime/secrets/discord-adapter-token.txt` at `0600`. "Enable" **always** overwrites with freshly generated random bytes — it never conditionally reuses pre-existing file content left over from an abandoned manual setup attempt (Eight-Hats finding — provenance of "new" token material must be unambiguous). `runtime/secrets/discord-adapter-token.txt` is added to `self-update.sh`'s existing secret preserve/chown lists (alongside `funcom-token.txt`, `public-directory.json`) so it isn't silently lost or mis-owned across a future, unrelated stack self-update (Eight-Hats Cloud Security finding).

**Token regeneration does *not* trigger a container recreate.** Verified directly: `readDiscordBotApiToken()` re-reads the token file fresh on every request — it is never cached in `process.env` or read only at startup, unlike `DUNE_DISCORD_ADAPTER_ENABLED` and the role-ID vars, which genuinely are read once at container start. Regenerating is therefore a plain file rewrite with no helper invocation, no recreate, and no downtime — this both matches reality and avoids unnecessarily exposing the docker-socket-privileged path for an operation that doesn't need it (Eight-Hats Cloud Security + Security Architect findings). Enabling the adapter for the first time, or changing role-ID values, still requires the full recreate flow described below, since those *are* only read at container start.

**Recreate trigger** (enable / role-ID changes only, not token regeneration): launches the new additive script described in §2, under the shared `console-recreate.lock`.

**Status polling and post-recreate health signal (Eight-Hats DBA finding):** reuses `selfUpdateStatus.js`'s status-file schema/polling under a distinct run type, extended with one additional field this feature specifically needs: whether the Discord adapter's own schema initialization and token read actually succeeded post-recreate, not just whether the container process is up. This matters because both of those steps are deliberately fail-soft at the container level today (`initializeDiscordAdapterSchema()`'s promise rejection is only logged as a warning; a missing/corrupt token file makes `readDiscordBotApiToken()` silently return an empty string) — a naive reuse of "the container responded to `/api/auth/state`" as the success signal would report "Enabled ✓" even when the adapter is actually non-functional. The backend performs one extra check after the recreate completes (does `GET /api/integrations/discord/health` succeed with the newly-configured token) and writes that result into the status file's terminal state; the frontend's success view checks this field, not just liveness.

**Audit trail (Eight-Hats GRC finding, Repudiation):** every comparable privileged Settings action in this codebase (web-port change, recovery-code regeneration, public-directory claim) calls the existing `audit()` mechanism. This route does the same: `audit(config, req, "settings.discord-bot.enable", {...})` and `"settings.discord-bot.token-regenerated"` on their respective actions, never logging the token value itself (matching the existing `redactValue()` convention).

### 3.3 Data flow

1. Operator opens the Discord Bot settings section → `GET /api/settings/discord-bot` → renders the correct state per §3.1 (never assumes "never configured").
2. If genuinely disabled: operator picks hosted/self-hosted, toggles "Enable Discord Bot Integration" → confirm dialog (with a one-time backup recommendation if this is a first-ever enable, per §4) → `POST /api/settings/discord-bot`.
3. Backend validates role IDs, generates the token, writes the secret file (`0600`), stages and flushes the hardcoded `.env` key set, then launches the additive recreate script under the shared lock, with a fixed non-parameterized argv.
4. Script runs `docker compose -f docker-compose.web.yml up -d --force-recreate <console-service>` (no build/pull step), writes `succeeded`/`failed` to the status file.
5. Frontend (task persisted to `localStorage` from step 2, survives a reload) polls the status file; once `succeeded`, waits a short settle delay, then polls `/api/auth/state` until back up, counts down, auto-reloads (manual "Refresh Now" always visible).
6. Post-reload, the Discord Bot section re-fetches state (step 1) and shows **Enabled** only if the post-recreate health check (§3.2) actually passed — otherwise shows the failure state from §4.
7. Regenerating a token skips steps 3-6's recreate machinery entirely: it's a direct file rewrite behind a typed confirmation, reflected immediately with no downtime.

## 4. Error handling

- Helper-launch failure (e.g., a Docker socket issue, or the `console-recreate.lock` already held by an in-flight self-update): surfaced inline before the dialog closes, with a clear "an update is already in progress, try again shortly" message for the lock-contention case specifically (Eight-Hats Architect finding — mutual exclusion).
- Recreate succeeds at the container level but the post-recreate adapter health check (§3.2) fails (e.g., a malformed token file write, or the schema migration's warning-only failure path): status file reports `failed` with the specific reason: the frontend shows this error instead of the success countdown, with a "Retry" action rather than a dead end — this is a genuinely new failure class this feature introduces visibility into that didn't exist as a distinct, surfaced state before.
- **Token regeneration risk**: an operator's bot (hosted or self-hosted) may already hold the old token. Regenerating disconnects it until the operator re-pastes the new value wherever their bot is configured — Core has no way to reach either bot type to update it automatically. This is why regeneration requires the typed confirmation described in §3.1, not just a warning.
- **First-time legacy-schema migration (Eight-Hats DBA CRITICAL finding — see §5 for why this exists at all):** enabling the adapter for the first time on an operator's install triggers `initializeDiscordAdapterSchema()`, a real (if already-tested and transactionally atomic) Postgres migration — including, for any operator upgrading from a version that used the pre-rename `dune.discord_*` tables, a one-time legacy-data copy into the new `console.discord_*` tables. This was previously gated behind a deliberate, docs-reading manual `.env` edit; this design gates the same trigger behind a single confirm-dialog click. The confirm dialog's copy includes a one-time backup recommendation specifically for this first-enable case (detected via whether `initializeDiscordAdapterSchema()` has ever previously reported success for this install — an existing marker this design reads, not a new one it invents). Subsequent enables/regenerates on an already-migrated install don't re-trigger this copy.

## 5. Testing

- Backend: unit tests for token generation, `.env` writing (including the staged-buffer/all-or-nothing behavior), role-ID validation (`/^\d{15,21}$/` acceptance/rejection), and the new script's argument construction — mirroring the existing self-update test suite's own real, non-tautological pattern (`tasks.test.js`'s `buildSelfUpdateHelperDockerArgs` test, which asserts against literal expected strings, not a value recomputed from the same constants).
- Backend: an explicit test for the **failure path** described in §4 — the status file correctly reports `failed` with the post-recreate health-check reason, mirroring `selfUpdateStatus.test.js`'s existing failed-state test coverage (Eight-Hats QA/Test finding — the original draft's test plan omitted this entirely despite §4 describing it in prose).
- Backend: explicit tests for the **read-current-state route** covering every real combination, not just the two obvious ones — enabled-flag-true-with-token-file, enabled-flag-true-without-token-file, enabled-flag-false-with-token-file-present (an abandoned manual attempt), and role-ID vars set independently of the enabled flag (Eight-Hats QA/Test finding — this is the state-detection logic three independent hats flagged as the highest-consequence gap in the original draft).
- Frontend: component tests for all four states from §3.1, including the **Failed** state (not just the original three), and the up-front hosted/self-hosted choice's effect on rendered copy.
- Frontend: an explicit test that mocks fetch/timers and drives the actual polling state machine (status-file poll → settle delay → `/api/auth/state` poll → success/failure) through a connection-drop-and-recover cycle — not a shallow render test. This mechanism currently has **no existing test precedent to mirror** in this codebase (`UpdatesPanel.test.ts` only unit-tests two pure helper functions, never exercises the real polling loop) — this design cannot simply claim to "mirror existing UI test patterns" for this specific piece, since no adequate pattern yet exists to mirror (Eight-Hats QA/Test finding).
- A real, non-mocked middle-ground test between "pure unit test" and "manual dune-dev pass" is added, following this repo's own existing precedent (`runtime/tests/test-compose-project-name-portability.sh`, which invokes the real `docker compose config` CLI against a disposable git worktree without launching a live container): a test that writes the new `.env` values and invokes real `docker compose -f docker-compose.web.yml config` to assert the resolved service definition actually picks up the new env vars and references the correct service/image — catching a wrong-compose-file-reference or malformed-generated-`.env`-line bug class at CI cost, before it would otherwise only be caught by a manual dune-dev pass (Eight-Hats QA/Test finding).
- Manual verification against a real environment (dune-dev) remains required before shipping, per Requirement 0 — but now specifically includes: an operator starting from a **pre-existing, manually-configured** adapter (confirms the state-detection fix); an operator with **legacy `dune.discord_*` table data** (confirms the migration path, not just a fresh install, per Requirement 0's "test the actual upgrade" and the DBA finding below); and triggering the lock-contention error path by starting a self-update and this feature's enable flow at the same time.
- **Requirement 26 does apply here** (correction from the original draft, which incorrectly claimed it didn't): this feature doesn't add a new migration, but it dramatically increases who (any Settings-authorized operator via one click, vs. previously an operator who read the manual docs closely enough to know a migration exists at all) and how often (routine adapter enables, vs. previously a rare, deliberate action) triggers an existing one. The migration itself is already transactionally atomic (`db.transaction(migrate)`) and has existing test coverage (`discordAdapterSchema`-adjacent tests) — confirmed, not assumed — so no new rollback SQL is needed; what's new is the upgrade-path testing scope named above. Separately, since "Regenerate Token" now makes container recreates routine, and the schema migration re-runs (safely, idempotently) on every process start regardless of whether anything changed, the implementation should confirm via timing/`EXPLAIN` against a realistic `dune.player_state` size that the migration's cross-table cleanup `DELETE`s are cheap enough to run this much more frequently than before — or skip the migration re-run when the schema is already known-current and only the token/role-ID values changed.

## 6. Requirement 0 / blast radius

Core is a public, multi-operator fork. This design is purely additive: a new Settings section, a new route, no change to any existing route or behavior — an operator who never opens this section sees zero difference. It reuses the exact trust boundary (docker-socket access from the console container) already shipped and accepted for self-update, rather than introducing a new one, and gates the docker-socket-adjacent actions behind the same narrowly-scoped `updates:apply` action self-update itself uses, rather than the broader `settings:write` bucket (§3.2).

**Documentation follow-ups named explicitly (Eight-Hats GRC finding — the original draft named none):** three real, currently-accurate docs become stale the moment this ships and must be updated in the same change or the same release, per Requirement 14:
- This repo's own `docs/security/secrets-management.md` — its credential inventory table currently lists the adapter token as `Manual` rotation with "no rotation mechanism"; both become false.
- This repo's own `docs/integrations/discord-control-bot/setup-guide.md` — currently walks an operator through the manual `chmod 600`/token-file steps this feature replaces.
- `mentat`'s `docs/discord-setup.md` ("Step 6: Enable the Discord Adapter on the Console") — currently a manual `.env`-edit-and-restart walkthrough, linked directly from `mentat`'s own `docs/installation-guide.md` for both self-hosted options. A `cc:` comment should be filed on the relevant `mentat` issue/PR when this ships, per this org's cross-repo doc-drift convention.

A `CHANGELOG.md` entry is required at merge time (this repo's own live convention — see its `## Unreleased` section's existing entries, which each name the docs they touched) naming the three doc updates above.

**Requirement 27 (credential rotation) scope, stated explicitly rather than left implicit:** this design makes Core-side token rotation instant, live, and requires no restart on Core's side (confirmed: the token file is read fresh per-request). It does **not** by itself satisfy Requirement 27's full "rotation possible without taking the bot offline" bar end-to-end, because the bot-side re-paste-and-reconnect step remains entirely manual on the `mentat`/`mentat-link` side, with no tested, documented cross-repo procedure. This is named here as a known, accepted v1 limitation (see the top-of-document scope note), not silently assumed solved — a follow-up issue tracking the cross-repo rotation runbook should be filed against `mentat` when this ships.
