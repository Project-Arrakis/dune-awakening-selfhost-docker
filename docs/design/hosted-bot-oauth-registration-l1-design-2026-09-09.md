# Hosted Bot Console-Initiated OAuth Registration — Layer 1 Design

**Status:** Draft, pre-audit
**Date:** 2026-09-09
**Repos affected:** `dune-awakening-selfhost-docker` (Core console), `mentat` (the hosted, multi-tenant bot backend), `mentat-link` (documentation only — no functional change)
**Supersedes:** the "live Discord role picker... a materially bigger feature" item explicitly deferred out of scope in `docs/design/discord-bot-adapter-settings-automation-l1-design-2026-09-09.md` §2 (the Settings → Discord Bot feature this design builds directly on top of).
**Tracking issue:** to be filed after this draft passes its Layer 1 Eight-Hats audit.

## 1. Problem Statement

`mentat` is a shared, multi-tenant Discord bot: one running bot process serves many operators' Dune Docker consoles, each hosting a different Discord guild. For the bot to route a command in guild X to the right console with the right credential, something has to register the mapping `{guildId → consoleUrl, adapterToken, roleMappings}` in mentat's own database.

Today that registration happens through a fully separate, standalone onboarding flow:

1. An operator invites `mentat` to their Discord server.
2. `mentat`'s `handleGuildCreate()` (`mentat/src/onboarding.js:265-330`) DMs the inviter (or, if unidentifiable, the guild owner) a link: `${SETUP_URL}/setup?guildId=<id>`.
3. That link is served by `mentat-link.darkdante.org/setup`, which is a transparent reverse proxy (`mentat-link/functions/setup/[[path]].js`) to `mentat`'s own Express server (`mentat/src/setupServer.js`) — the page, the Discord OAuth login it performs, and the registration handler all live in `mentat`, not `mentat-link`.
4. The operator signs in with Discord (proving they manage *some* guild Discord will show them), picks their guild from a dropdown, and manually fills in: a Console URL field, an Adapter Token field, and up to three Discord role-ID fields.
5. Submitting calls `POST /setup/register` (`setupServer.js:429-551`), which writes to mentat's own SQLite DB via `upsertGuild()`.

**What's wrong with this today, concretely:**

- **The Adapter Token field asks the operator to manually run a command.** The current hint text (`setupServer.js:349-359`) tells the operator to `openssl rand -hex 32 > runtime/secrets/discord-adapter-token.txt`, `chmod 600` it, recreate their console container, then paste the same value back into this form. As of the immediately-preceding Core feature (Settings → Discord Bot), Core *already generates and writes this token itself* with zero CLI — this instruction is now solving a problem Core has already solved, on the wrong side of the boundary.
- **A prior attempt to fix this the "obvious" way was shipped and reverted for being actively broken.** Issue `mentat#194` ("Setup portal Generate button mints an adapter token Core can never accept — guaranteed-broken onboarding"): a Generate button that minted a *browser-side* random token was found to produce values Core would never recognize, since Core only validates against whatever is already in its own token file — operators hit a silent, unexplained 401 on every bot command after "successfully" completing setup. It was removed; the current manual-`openssl` instructions (issue `mentat#214`'s own remediation) were the deliberate replacement.
- **The flow is split across two entirely separate systems the operator has to context-switch between**, with no way for either side to know what the other has already done.
- **The registration step (`upsertGuild`) has no way to be triggered except by visiting this one specific page after a DM**, which means an operator who wants to connect a *second* guild, or reconfigure an existing one, has no path back to it except waiting for another bot invite/DM or re-finding the URL from old documentation.

**What this design does:** moves guild registration for the hosted bot entirely into Core's console — the same place an operator already goes to manage everything else about their install — while *increasing*, not decreasing, the security assurance the current flow provides (Discord-OAuth-verified proof of guild ownership, independently re-checked by `mentat`, not a claim Core's console can spoof).

## 2. Why the #194 Failure Mode Doesn't Recur Here

This is worth stating explicitly, since the fix this design replaces (issue `mentat#214`'s manual-`openssl` instructions) exists specifically *because* of `mentat#194`, and any redesign of this area must be checked against that history before it ships.

`mentat#194`'s root cause: a token was **manufactured independently of Core**, on a page that had no way to make Core aware of it. The only two ways to close that gap are (a) make the independently-manufactured value flow into Core somehow (never designed, never shipped), or (b) never manufacture an independent value at all — always use the one value that already exists, generated by and known to Core.

This design does (b), twice over:

- The **adapter token** is never generated by this new flow. Core already generated it (Settings → Discord Bot → Enable/Regenerate, already shipped). This design's only job with that token is to read it from wherever Core already wrote it and hand the *same bytes* to mentat's new registration API — there is no new token-generation code path anywhere in this design.
- The **guild-ownership proof** is never asserted by Core on its own say-so. Core's browser-driven OAuth step produces a live, ~1-hour-lived Discord access token; that same token is forwarded to `mentat`'s backend, which makes its own call to Discord's API with it. `mentat` never trusts "Core says this operator owns guild X" — it always independently re-derives that fact from Discord directly, exactly as it does today via its own OAuth flow, just fed a token that arrived from a different origin.

## 3. Proposed Design

### 3.1 Frontend / operator-facing flow (Core console)

**Settings → Discord Bot** (already shipped) gains a new action, available once the adapter is enabled and a token exists: **"Connect to hosted bot."** This is distinct from, and additive to, the existing self-hosted-bot guidance — an operator running their own dedicated bot instance never needs this action at all (no multi-tenant registration exists for that case; the feature already shipped is their complete story).

Clicking "Connect to hosted bot":

1. Browser navigates to a new, purpose-specific OAuth start route on Core's own backend (`GET /api/integrations/discord/hosted-bot/oauth/start` — see §3.2). This is a full top-level navigation (matches the existing console-login OAuth's pattern exactly — no popup, no iframe), so the operator briefly leaves the console UI.
2. Core redirects to Discord's authorize page (same OAuth application already configured for console login — `DISCORD_OAUTH_CLIENT_ID`/`DISCORD_OAUTH_CLIENT_SECRET`, already present in every install that has console-login OAuth configured; **if OAuth isn't configured yet, this action is disabled with a tooltip pointing at the existing Discord OAuth settings section** — this feature does not introduce a second, independent Discord application).
3. Discord shows its standard consent screen (typically an instant pass-through if the operator already has an active session with this same app/scope from console login — not guaranteed, since Discord's re-consent behavior isn't something Core controls, but never a *new* scope prompt, since no new scope is requested).
4. Discord redirects back to Core's new callback route (`GET /api/integrations/discord/hosted-bot/oauth/callback`). Core's server verifies state/PKCE (mirroring the existing hardened pattern byte-for-byte — see §3.2), exchanges the code, and calls Discord's `/users/@me/guilds`.
5. **Unlike the existing console-login flow, this callback keeps the `owner` field from each guild in the response** and filters to guilds where `owner === true` for the authenticated user. (Scope note: Discord's `guilds` scope returns `owner: true` only for guilds the user *literally owns* — the Discord "Server Owner," not merely an admin. This matches the existing mentat portal's own current behavior, `setupServer.js:329-332`'s "guilds the user owns/manages," and is the most conservative, unambiguous starting filter. Widening to "has ADMINISTRATOR permission" is a real, separately-discussable follow-up, not part of this design — see §9.)
6. Core's server does **not** mint a session or change what the operator can do inside the console (this is not a login flow) — it renders a one-time, in-console page: "Which server is this for?" with a dropdown of the owned guilds from step 5.
7. Operator picks a guild, confirms via the existing `ConfirmDialog` pattern (danger: false — this is disruptive-but-safe, not destructive, matching the framing already used for Enable/Save Role IDs elsewhere in this same Settings section), and submits.
8. On submit, Core's *backend* (not the browser) makes the server-to-server registration call described in §3.3. The browser sees only a loading state, then success/error.
9. **Success:** the section shows "Connected to hosted bot for `<guild name>`," with a "Connect another guild" action available to repeat the flow (supports the realistic case of one console serving multiple guilds, addressed explicitly here since the old flow had no clean path for it either).
10. **Failure:** a specific, actionable error per failure mode (§3.5) — never a bare "something went wrong."

This flow is Core-console-only, end to end. Nothing links out to `mentat-link.darkdante.org`. No DM triggers it.

### 3.2 Core backend — new OAuth purpose

New file: `console/api/src/integrations/discord/hostedBotOAuth.js`. Reuses, rather than forks, the library-level primitives already in `console/api/src/integrations/discord/oauth.js`:

- `exchangeDiscordAuthCode()` — reused unchanged.
- `buildAuthorizeUrl()` — reused unchanged (same scope, `"identify guilds"` — **no new scope**).
- The PKCE + `state`-cookie CSRF machinery (`createPendingStateStore()`, `oauthStateCookie()`, `constantTimeStringEqual()`) — reused unchanged. This is a genuinely hardened, already-audited pattern (real constant-time state comparison against an HttpOnly, path-scoped, 10-minute cookie, plus PKCE S256) and this design does not relax any part of it.
- `fetchDiscordIdentity()` is **not** reused as-is — it currently reduces the guilds response to bare IDs (`oauth.js:147-149`), discarding `owner`. A new sibling function, `fetchOwnedDiscordGuilds({ accessToken })`, calls the same `/users/@me/guilds` endpoint and returns `{ userId, username, guilds: [{ id, name, owner }] }` without discarding the field this design needs. `fetchDiscordIdentity()` itself is untouched — console-login behavior does not change.

New routes in `console/api/src/server.js`, gated behind the console's own existing auth (an operator must already be logged into their own console to reach these — this is not a public, unauthenticated route the way mentat's `/setup` is):

- `GET /api/integrations/discord/hosted-bot/oauth/start` — issues a new pending-state entry (own `state`/PKCE pair, own cookie, distinct from console-login's so the two flows can never be confused mid-flight), 302s to Discord.
- `GET /api/integrations/discord/hosted-bot/oauth/callback` — verifies state, exchanges code, calls `fetchOwnedDiscordGuilds()`, and returns the owned-guilds list to the frontend (as a page that hands off to the SPA with the list embedded, mirroring the existing `oauthReturnPage()` handoff-to-SPA pattern already used for console login — not a raw JSON response the browser has to fetch separately).
- `POST /api/integrations/discord/hosted-bot/register` — the operator's confirmed selection lands here. This is the route that performs the server-to-server call in §3.3. **The Discord access token from step 4 must still be valid/in-scope at this point** — Core's server holds it only in server-side memory for the duration of a single request cycle (never written to a session, cookie, or database — matching the existing "used once, discarded" philosophy of `oauth.js`'s own header comment), so this route must be called before the token's ~1-hour lifetime elapses. If the operator takes too long between picking a guild and confirming, Core re-runs the OAuth round-trip transparently rather than surfacing a raw expiry error (implementation detail, not a design gap — flagged here so it isn't missed as an edge case in Layer 2).

**IAM gating:** these three routes require the operator's own console session (any authenticated tier can *reach* the flow, since it doesn't grant any new console capability — but see §3.4 for the equivalent of the existing admin/owner distinction already established for the adjacent Settings → Discord Bot feature). Concretely: `hosted-bot/oauth/start` and `.../callback` require `settings:read` (matches the existing GET-state action for this section); `hosted-bot/register` requires `updates:apply` (matches `enable`/`role-ids`'s existing gating — this is the action that has a real external side effect).

### 3.3 The server-to-server registration call (Core → mentat)

Core's `POST /api/integrations/discord/hosted-bot/register` handler makes an outbound HTTPS call:

```
POST https://mentat-backend.darkdante.org/api/consoles/register
Content-Type: application/json

{
  "guildId": "<snowflake, from the operator's selection>",
  "discordAccessToken": "<the live, ~1hr-lived token from step 4, forwarded verbatim>",
  "consoleUrl": "<window.location.origin, confirmed/editable by the operator in the confirm step>",
  "adapterToken": "<read from Core's own token file/env, the same value Settings -> Discord Bot already generated>",
  "roleMappings": { "player": [...], "moderator": [...], "admin": [...] }
}
```

**On mentat's side** (new route in `mentat/src/setupServer.js` or a new sibling module — Layer 2 decides the exact file split):

1. Rate-limit this endpoint independently of `/setup/register` (it has a different caller population — arbitrary Core consoles on the internet, not browsers that already passed through mentat-link's own proxy).
2. Call Discord's `/users/@me/guilds` **itself**, using the forwarded `discordAccessToken` — **never trust the `guildId`/ownership claim in the request body without this independent check.** Confirm the token is valid (Discord will reject an expired/revoked token with its own 401) and that the returned guild list contains `guildId` with `owner: true` for the token's own user.
3. If verified: `upsertGuild()` (the existing function, `mentat/src/database.js:444-471`) with `consoleUrl`, `adapterToken` (encrypted at rest exactly as today, via `encryptColumn()` when `ACP_SECRETS_KEY` is configured — this design does not change that dependency), and the role mappings.
4. **Never persist `discordAccessToken`.** It is used for exactly one verification call and discarded in the same request — matching Core's own established "use once, discard" pattern for this same class of secret.
5. Respond with a normalized success/error shape Core's `register` handler translates into one of the specific UI states in §3.5 (not a passthrough of mentat's raw error body).

**Why this endpoint is a new, distinct kind of attack surface on mentat's backend, and what bounds it:** every other request mentat's backend accepts today either comes through mentat-link's proxy (gated by `MENTAT_PROXY_SHARED_SECRET`, an "obscurity, not access control" boundary per that code's own comments) or from the bot's own signed handoff mechanism (`handoff.js`, HMAC-signed, 30-second-lived). This new endpoint is deliberately reachable from **any** Core console on the internet with no pre-shared secret at all — that's the whole point (any operator, anywhere, should be able to connect their console without mentat's operators provisioning anything per-install). Its *only* gate is the live, independently-re-verified Discord OAuth token. This is an intentional, new trust boundary, not an oversight — but it must be named as one for the audit, not discovered by it.

**SSRF-adjacent note on `consoleUrl`:** mentat's bot already makes outbound calls to whatever `consoleUrl` an operator registers, today, via the existing manual/portal flow — accepting an operator-supplied URL and later connecting to it is not a new risk this design introduces, it's an existing, already-accepted shape of the system. This design does not change what mentat does with `consoleUrl` after registration, only how the registration itself is submitted.

### 3.4 Role-ID entry stays manual

Per explicit instruction: Discord role IDs (which roles map to player/moderator/admin bot-command tiers) are not derived from OAuth data — Discord's `guilds` scope doesn't expose a guild's role list at all (that needs the bot to already be a member and a separate, elevated API call), and this design does not add that. The operator continues to paste Discord role IDs into Core's Settings → Discord Bot fields (the pattern already shipped) exactly as today. This is the one explicitly-accepted remaining manual step.

### 3.5 Error handling

| Failure | UI treatment |
|---|---|
| Operator cancels/denies Discord's consent screen | Return to the Settings page with no error banner (this is a cancel, not a failure) — matches how browsers/Discord's own flow signal cancellation (an `error=access_denied` query param on the callback) |
| Operator owns zero Discord guilds | "No servers found where you're the owner. If you manage this server without owning it, [contact/see docs] — direct ownership is required for this step today." (see §9 for the ADMINISTRATOR-permission follow-up) |
| Access token expires between guild-pick and confirm | Transparent silent re-auth (§3.2), not a user-facing error, unless the SECOND attempt also fails, in which case: "Your Discord session expired — try again." |
| `mentat`'s registration API is unreachable (network/DNS/5xx) | "Couldn't reach the hosted bot service. Your console's own settings are unaffected — try again in a moment." (explicitly reassures the operator this failure has no effect on their local adapter config, since it doesn't) |
| `mentat` rejects: Discord re-verification fails (token invalid/expired by the time mentat calls Discord, or guild ownership mismatch) | "Could not verify you own that Discord server — please try connecting again." (deliberately does not say more — this is the one failure mode with a plausible malicious-actor interpretation, and the message should not help an attacker distinguish "token expired" from "you don't actually own this guild") |
| `mentat` rejects: malformed/missing adapter token on Core's side | Should be structurally unreachable — the "Connect to hosted bot" action is only shown once Settings → Discord Bot already has a token configured (§3.1) — Layer 2 should add a defensive check anyway |
| Re-registering an already-connected guild | Treated as an update, not an error — `upsertGuild()` already supports this (existing behavior, unchanged) |

### 3.6 What happens to the existing DM + portal flow

Per explicit instruction ("no setup link, no dm"): `mentat`'s `handleGuildCreate()` DM-on-invite behavior (`onboarding.js:265-330`) is **removed** as the default onboarding trigger once this ships. An operator who invites the bot going forward is expected to already know (from installation docs, updated as part of this design's own rollout) to go to their own console's Settings → Discord Bot page.

**The `/setup` page and `POST /setup/register` handler are not deleted.** They remain reachable (unlinked from any new DM, but still a real, working URL) as an escape hatch: for an operator troubleshooting a broken registration, for anyone who bookmarked the old link, and as a fallback if this new flow has an outage or a bug not caught before rollout. Its own stale instructions (the `openssl` hint, per the earlier conversation in this design's own history) still get corrected to point at Core's Settings page instead of a CLI command — that fix is real and worth keeping regardless of this larger design, and is a natural companion PR/commit in the `mentat` repo, done alongside this feature.

This is a deliberate, Requirement-0-driven choice: removing the *only* path to registration entirely, on day one of a new, unaudited flow, would leave zero recovery path if something is wrong. Fully retiring `/setup` (if ever desired) is a separate, later decision once this flow has real production track record — not part of this design.

## 4. Data Flow Summary

```
Operator's browser (Core console)
  -> GET /api/integrations/discord/hosted-bot/oauth/start   [Core backend]
  -> 302 to discord.com/oauth2/authorize                     [Discord]
  -> 302 back to /api/integrations/discord/hosted-bot/oauth/callback  [Core backend]
       - exchanges code for access token (server-side only)
       - calls Discord /users/@me/guilds, keeps owner=true guilds
       - hands owned-guilds list to the SPA
  <- operator picks a guild, confirms
  -> POST /api/integrations/discord/hosted-bot/register       [Core backend]
       -> POST https://mentat-backend.darkdante.org/api/consoles/register   [mentat backend]
            - re-calls Discord /users/@me/guilds with the forwarded token
            - verifies ownership independently
            - upsertGuild() into its own DB
            - discards the forwarded Discord token
       <- success/error
  <- Core translates into a specific UI state (§3.5)
```

The Discord access token exists in exactly two places, both server-side, both for the lifetime of a single request each: Core's `/callback` and `/register` handlers, and mentat's new registration handler. It never reaches the browser after the initial redirect chain, and it is never written to any database, session, or log on either side.

## 5. Testing

- Core: unit tests for `fetchOwnedDiscordGuilds()` (owner-filtering, empty-guild-list case) mirroring `oauth.js`'s existing test conventions; route-level tests for the 3 new endpoints following the same real-spawn-and-fetch integration pattern already established for the adjacent Settings → Discord Bot feature (`discordAdapterSettingsRoutes.integration.test.js`); a test proving the access token is never logged (reuse the existing `audit()`-redaction assertion pattern from that same feature).
- `mentat`: unit tests for the new registration endpoint's independent-reverification logic (valid token + matching guild → success; valid token + non-matching guild → rejected; expired/invalid token → rejected); confirm `discordAccessToken` never appears in any log line or DB write (mirroring this org's own Requirement 24 test conventions already used elsewhere in this codebase).
- Cross-repo: at minimum one documented manual end-to-end verification (Requirement 0's "test the actual upgrade/real flow, not just unit tests") — a real Core console, a real Discord OAuth app, a real guild, confirming the full round trip actually registers correctly and the bot subsequently authenticates against the registered console.

## 6. Requirement 0 / Blast Radius

- **No existing operator's working setup breaks.** Self-hosted-bot operators never see any part of this (§3.1). Existing hosted-bot operators who already registered via the old `/setup` flow keep working exactly as before — this design only changes how a *new* registration or *update* happens, not what's already stored in mentat's DB.
- **The old flow is not deleted**, precisely to avoid "the fix being riskier than the problem it fixes" (this org's own standing rule, given its history with the command-auth-token incident). It becomes a documented fallback, not a dead end.
- **No new Discord OAuth scope is requested.** Every operator who already has console-login OAuth configured already granted `identify guilds`; this design asks for nothing beyond that, so there is no new consent friction beyond triggering the flow itself.
- **mentat's backend gains one new public, non-preshared-secret-gated endpoint.** This is named explicitly as a new trust boundary in §3.3, not discovered later — it is the single largest blast-radius item in this design and the primary thing the Layer 1 audit should stress-test.

Remove or clearly mark stale the "Option B: Generate a new token from the portal" section (already confirmed, independently of this design, to describe a feature that was shipped, found broken, and reverted per `mentat#194` — this has been aspirational/wrong documentation since that revert and should be corrected regardless of this design's fate).

## 8. Open Design Decisions Deliberately Left for Layer 1 Audit / Layer 2

- Exact file/module split on `mentat`'s side for the new registration endpoint (new file vs. extending `setupServer.js`) — an implementation detail, not a design-level question.
- Whether "Connect another guild" (§3.1 step 9) needs its own dedicated UI list of currently-connected guilds (view/manage/disconnect), or whether "connect" is sufficient for this first iteration and "manage/disconnect" is a follow-up. **Recommendation: ship connect-only first; disconnect/manage is real, valuable, and explicitly out of scope for this design** to keep this change reviewable.
- Rate-limit thresholds for the new mentat endpoint (Layer 2 implementation detail, informed by whatever this codebase's existing rate-limiting middleware already supports).

## 9. Explicitly Out of Scope

- Widening guild eligibility from "Discord-verified owner" to "has ADMINISTRATOR permission" — a real, reasonable future request (many real operators run a shared server where they're not the literal owner), but it changes the verification semantics in a way that deserves its own explicit design/audit pass, not a drive-by inclusion here.
- Disconnecting/removing a previously-registered guild from Core's console.
- Any change to how the bot behaves once a guild is registered — this design is scoped entirely to the registration step itself.
- Deleting the `/setup` portal or the `mentat-link` proxy route in front of it.
