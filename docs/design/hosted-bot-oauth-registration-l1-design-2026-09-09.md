# Hosted Bot Console-Initiated OAuth Registration — Layer 1 Design

**Status:** Draft, pre-audit
**Date:** 2026-09-09
**Repos affected:** `dune-awakening-selfhost-docker` (Core console), `mentat` (the hosted, multi-tenant bot backend), `mentat-link` (documentation only — no functional change)
**Supersedes:** the "live Discord role picker... a materially bigger feature" item explicitly deferred out of scope in `docs/design/discord-bot-adapter-settings-automation-l1-design-2026-09-09.md` §2 (the Settings → Discord Bot feature this design builds directly on top of).
**Tracking issue:** to be filed after this draft passes its Layer 1 Eight-Hats audit.

## 1. Problem Statement

`mentat` is a shared, multi-tenant Discord bot: one running bot process serves many operators' Dune Docker consoles, each hosting a different Discord guild. For the bot to route a command in guild X to the right console with the right credential, something has to register the mapping `{guildId → consoleUrl, adapterToken, roleMappings}` in mentat's own database.

Today that registration happens through a fully separate, standalone onboarding flow:

1. An operator invites `mentat` to their Discord server.
2. `mentat`'s `handleGuildCreate()` (`mentat/src/onboarding.js:265-330`) DMs the inviter (or, if unidentifiable, the guild owner) a link: `${SETUP_URL}/setup?guildId=<id>`.
3. That link is served by `mentat-link.darkdante.org/setup`, which is a transparent reverse proxy (`mentat-link/functions/setup/[[path]].js`) to `mentat`'s own Express server (`mentat/src/setupServer.js`) — the page, the Discord OAuth login it performs, and the registration handler all live in `mentat`, not `mentat-link`.
4. The operator signs in with Discord (proving they manage *some* guild Discord will show them), picks their guild from a dropdown, and manually fills in: a Console URL field, an Adapter Token field, and up to three Discord role-ID fields.
5. Submitting calls `POST /setup/register` (`setupServer.js:429-551`), which writes to mentat's own SQLite DB via `upsertGuild()`.

**What's wrong with this today, concretely:**

- **The Adapter Token field asks the operator to manually run a command.** The current hint text (`setupServer.js:349-359`) tells the operator to `openssl rand -hex 32 > runtime/secrets/discord-adapter-token.txt`, `chmod 600` it, recreate their console container, then paste the same value back into this form. As of the immediately-preceding Core feature (Settings → Discord Bot), Core *already generates and writes this token itself* with zero CLI — this instruction is now solving a problem Core has already solved, on the wrong side of the boundary.
- **A prior attempt to fix this the "obvious" way was shipped and reverted for being actively broken.** Issue `mentat#194` ("Setup portal Generate button mints an adapter token Core can never accept — guaranteed-broken onboarding"): a Generate button that minted a *browser-side* random token was found to produce values Core would never recognize, since Core only validates against whatever is already in its own token file — operators hit a silent, unexplained 401 on every bot command after "successfully" completing setup. It was removed; the current manual-`openssl` instructions (issue `mentat#214`'s own remediation) were the deliberate replacement.
- **The flow is split across two entirely separate systems the operator has to context-switch between**, with no way for either side to know what the other has already done.
- **The registration step (`upsertGuild`) has no way to be triggered except by visiting this one specific page after a DM**, which means an operator who wants to connect a *second* guild, or reconfigure an existing one, has no path back to it except waiting for another bot invite/DM or re-finding the URL from old documentation.

**What this design does:** moves guild registration for the hosted bot entirely into Core's console — the same place an operator already goes to manage everything else about their install — while *increasing*, not decreasing, the security assurance the current flow provides (Discord-OAuth-verified proof of guild ownership, independently re-checked by `mentat`, not a claim Core's console can spoof).

## 2. Why the #194 Failure Mode Doesn't Recur Here

This is worth stating explicitly, since the fix this design replaces (issue `mentat#214`'s manual-`openssl` instructions) exists specifically *because* of `mentat#194`, and any redesign of this area must be checked against that history before it ships.

`mentat#194`'s root cause: a token was **manufactured independently of Core**, on a page that had no way to make Core aware of it. The only two ways to close that gap are (a) make the independently-manufactured value flow into Core somehow (never designed, never shipped), or (b) never manufacture an independent value at all — always use the one value that already exists, generated by and known to Core.

This design does (b), twice over:

- The **adapter token** is never generated by this new flow. Core already generated it (Settings → Discord Bot → Enable/Regenerate, already shipped). This design's only job with that token is to read it from wherever Core already wrote it and hand the *same bytes* to mentat's new registration API — there is no new token-generation code path anywhere in this design.
- The **guild-ownership proof** is never asserted by Core on its own say-so. Core's browser-driven OAuth step produces a live, ~1-hour-lived Discord access token; that same token is forwarded to `mentat`'s backend, which makes its own call to Discord's API with it. `mentat` never trusts "Core says this operator owns guild X" — it always independently re-derives that fact from Discord directly, exactly as it does today via its own OAuth flow, just fed a token that arrived from a different origin.

## 3. Proposed Design

### 3.1 Frontend / operator-facing flow (Core console)

**Settings → Discord Bot** (already shipped) gains a new action, available only when both are true: the adapter is enabled with a token configured, **and** the operator's earlier `choice` selection (the existing `hosted`/`self-hosted` state already in `DiscordBotSection.tsx`) is `"hosted"`. **This is a hard visibility/enablement gate, not just a claim that self-hosted operators "won't need it"** — a self-hosted operator (who runs their own dedicated bot instance, entirely outside mentat's multi-tenant registry) must never be able to reach this action at all, since mentat's registration has no way to know a guild is already served by a different, self-hosted bot process; registering it anyway would silently double-route that guild's commands through two live bots with no error surfaced to either operator. **[L1 finding, resolved]** The button is rendered only when `choice === "hosted"`; the 3 new backend routes in §3.2 independently re-check this same condition server-side (reading the persisted `choice` value, not trusting client-side hiding alone) before doing anything.

Clicking "Connect to hosted bot":

0. **If the operator has unsaved edits to the role-ID fields on this same page, they are prompted to save (or discard) those edits first**, via the existing save action, before the navigation in step 1 begins. **[L1 finding, resolved]** The step-1 navigation reloads the SPA on return; without this guard, in-progress typing would be silently lost with no warning.
1. Browser navigates to a new, purpose-specific OAuth start route on Core's own backend (`GET /api/integrations/discord/hosted-bot/oauth/start` — see §3.2). This is a full top-level navigation (matches the existing console-login OAuth's pattern exactly — no popup, no iframe), so the operator briefly leaves the console UI. **If Discord OAuth is not configured for this console at all, this route itself returns a Core-rendered error page** (a clear message plus a link back to the Discord OAuth settings section) **rather than attempting to build an authorize URL with empty credentials and redirecting to Discord's own generic error page.** **[L1 finding, resolved]** This is a server-side guard, not just a disabled-button-with-tooltip on the frontend — the frontend affordance (§3.1 original text) remains as the primary UX, but the route itself must fail safely if reached directly (a stale bookmark, a race with another admin session changing OAuth config, or a second tab).
2. Core redirects to Discord's authorize page (same OAuth application already configured for console login — `DISCORD_OAUTH_CLIENT_ID`/`DISCORD_OAUTH_CLIENT_SECRET`, already present in every install that has console-login OAuth configured; this feature does not introduce a second, independent Discord application). **The confirm step (step 7 below) discloses, in plain language, that this authorization will be forwarded to and verified by mentat's own service** — see the added disclosure text there. **[L1 finding, resolved: purpose-limitation/consent-transparency gap]**
3. Discord shows its standard consent screen (typically an instant pass-through if the operator already has an active session with this same app/scope from console login — not guaranteed, since Discord's re-consent behavior isn't something Core controls, but never a *new* scope prompt, since no new scope is requested).
4. Discord redirects back to Core's new callback route (`GET /api/integrations/discord/hosted-bot/oauth/callback`). Core's server verifies state/PKCE (mirroring the existing hardened pattern byte-for-byte — see §3.2), exchanges the code, and calls Discord's `/users/@me/guilds`.
5. **Unlike the existing console-login flow, this callback keeps the `owner` field from each guild in the response** and filters to guilds where `owner === true` for the authenticated user. (Scope note: Discord's `guilds` scope returns `owner: true` only for guilds the user *literally owns* — the Discord "Server Owner," not merely an admin. This matches the existing mentat portal's own current behavior, `setupServer.js:329-332`'s "guilds the user owns/manages," and is the most conservative, unambiguous starting filter. Widening to "has ADMINISTRATOR permission" is a real, separately-discussable follow-up, not part of this design — see §9.)
6. Core's server does **not** mint a session or change what the operator can do inside the console (this is not a login flow) — it renders a one-time, in-console page: "Which server is this for?" with a dropdown of the owned guilds from step 5. **The dropdown visually marks any guild that already has an active registration** (per §3.1 step 9's persisted-state requirement below), so the operator can tell, before submitting, whether they're connecting a new guild or updating an existing one. **[L1 finding, resolved]**
7. Operator picks a guild, confirms via the existing `ConfirmDialog` pattern (danger: false — this is disruptive-but-safe, not destructive, matching the framing already used for Enable/Save Role IDs elsewhere in this same Settings section). **The confirm dialog's message includes an explicit disclosure**, e.g.: *"Your Discord authorization will be used once to verify you own this server, then sent to and independently verified by the hosted bot service (mentat), and discarded — it is never stored."* **[L1 finding, resolved]** — then submits.
8. On submit, Core's *backend* (not the browser) makes the server-to-server registration call described in §3.3. The browser sees only a loading state, then success/error. **If the access token from step 4 has expired by this point** (real user think-time between steps 6 and 8 can exceed Discord's token lifetime in rare cases), Core does not silently redirect the operator back through Discord without warning — **it shows an explicit, brief message first** (*"Reconnecting to Discord to confirm this is still you…"*) **before** re-running the OAuth round-trip, so the second navigation doesn't read as a confusing, unexplained bounce. **[L1 finding, resolved: "transparent" re-auth wasn't actually transparent]** If that second attempt also fails, the operator sees the §3.5 "Your Discord session expired — try again" message instead of a further silent retry.
9. **Success:** the section shows "Connected to hosted bot for `<guild name>`," **and this status is real, persisted state — reflected from `readDiscordBotSettingsState()`'s response on every future page load, not an ephemeral post-action toast.** **[L1 finding, resolved]** A "Connect another guild" action is available to repeat the flow (supports the realistic case of one console serving multiple guilds, addressed explicitly here since the old flow had no clean path for it either); each previously-connected guild is listed by name (read-only — no manage/disconnect action yet, per §8).
10. **Failure:** a specific, actionable error per failure mode (§3.5) — never a bare "something went wrong."

This flow is Core-console-only, end to end. Nothing links out to `mentat-link.darkdante.org`. No DM triggers it.

**Discoverability, once the DM is removed (§3.6):** a brand-new operator who has never seen this feature needs more than "read the install docs once, weeks before inviting the bot" (see §3.6 for the full resolution of this — a Settings-page banner plus a required in-guild bot response for an unregistered guild).

### 3.2 Core backend — new OAuth purpose

New file: `console/api/src/integrations/discord/hostedBotOAuth.js`. Reuses, rather than forks, the library-level primitives already in `console/api/src/integrations/discord/oauth.js`:

- `exchangeDiscordAuthCode()` — reused unchanged.
- `buildAuthorizeUrl()` — reused unchanged (same scope, `"identify guilds"` — **no new scope**).
- The PKCE + `state`-cookie CSRF machinery (`createPendingStateStore()`, `oauthStateCookie()`, `constantTimeStringEqual()`) — reused unchanged. This is a genuinely hardened, already-audited pattern (real constant-time state comparison against an HttpOnly, path-scoped, 10-minute cookie, plus PKCE S256) and this design does not relax any part of it.
- `fetchDiscordIdentity()` is **not** reused as-is — it currently reduces the guilds response to bare IDs (`oauth.js:147-149`), discarding `owner`. A new sibling function, `fetchOwnedDiscordGuilds({ accessToken })`, calls the same `/users/@me/guilds` endpoint and returns `{ userId, username, guilds: [{ id, name, owner }] }` without discarding the field this design needs. `fetchDiscordIdentity()` itself is untouched — console-login behavior does not change.

**Token custody across the callback → confirm → register gap. [L1 CRITICAL finding, resolved — this section was rewritten; the original text asserted "held only in server-side memory for a single request cycle, never a session/cookie/DB" while also describing a flow where the token must survive from the OAuth callback (request 1) to a later, human-paced confirm/register call (request 3) — two claims that cannot both be true, independently flagged as Critical by two separate audit hats.]**

The real mechanism, modeled directly on this codebase's own `createPendingStateStore()` (`oauth.js:33-67`), which already solves an equivalent "state must survive across two separate requests" problem for CSRF/PKCE:

- A new `pendingHostedBotRegistrations` store (same shape as `createPendingStateStore()`: an in-memory map, a short TTL, a hard capacity cap, single-use/consumed-on-read) holds `{ accessToken, ownedGuildIds, userId }`, keyed by a fresh, random, server-generated **handle** (not the token itself).
- The callback (step 4) creates one entry, and sets a **new, dedicated, HttpOnly, `SameSite=Lax`, path-scoped cookie** (distinct from both the console's own session cookie and the OAuth state cookie) whose value is that handle. **This is the one honest correction to the original design's language: the handle is carried in a cookie. The token itself is not** — it never leaves server-side memory, is never logged, and is never written to any database, matching the properties that actually matter for this design's safety argument (§2, §4). "Never a cookie" was true of the token; it was never meant to (and cannot) be true of a correlator that lets a later request find server-side state belonging to this specific browser.
- The entry's TTL is bounded by Discord's own access-token lifetime (so an expired entry and an expired token fail at the same time, not separately) and the entry is consumed (deleted) the moment `/register` reads it — a second `/register` call with the same handle, or a stolen/replayed handle cookie, finds nothing.
- If the entry has expired (or was already consumed) when `/register` is called, this is exactly the "access token expires between guild-pick and confirm" case in §3.1 step 8 / §3.5 — Core re-runs the OAuth round-trip (with the explicit "Reconnecting…" message) rather than silently failing.

New routes in `console/api/src/server.js`, gated behind the console's own existing auth (an operator must already be logged into their own console to reach these — this is not a public, unauthenticated route the way mentat's `/setup` is):

- `GET /api/integrations/discord/hosted-bot/oauth/start` — checks Discord OAuth is configured at all (see §3.1 step 1's server-side guard); issues a new pending-state entry (own `state`/PKCE pair, own cookie, distinct from console-login's so the two flows can never be confused mid-flight), 302s to Discord.
- `GET /api/integrations/discord/hosted-bot/oauth/callback` — verifies state, exchanges code, calls `fetchOwnedDiscordGuilds()`, creates the pending-registration entry above, sets its handle cookie, and returns the owned-guilds list to the frontend (as a page that hands off to the SPA with the list embedded, mirroring the existing `oauthReturnPage()` handoff-to-SPA pattern already used for console login — not a raw JSON response the browser has to fetch separately, and never including the raw access token in that handoff payload).
- `POST /api/integrations/discord/hosted-bot/register` — the operator's confirmed selection lands here, reads and consumes the pending-registration entry via the handle cookie, and (if still valid) performs the server-to-server call in §3.3. Also independently re-checks `choice === "hosted"` server-side (§3.1) and re-validates the submitted `guildId` against the entry's own `ownedGuildIds` list **before forwarding anything to mentat** — a defense-in-depth check so a bug or tamper in the browser layer fails closed at Core too, not only at mentat's own (authoritative) re-verification. **[L1 finding, resolved: defense-in-depth guildId check]**

**IAM gating — corrected against this codebase's real, current policy engine, not an assumed parallel to the sibling feature. [L1 finding, resolved: the original text cited `settings:read`, which does not exist as a mapped action for this section at all — the real sibling precedent is `updates:read` — and cited bare `updates:apply` for `register` without accounting for this codebase's own established pattern of layering owner-only protection onto a sensitive sub-case of a coarser action.]**

- `hosted-bot/oauth/start` and `.../callback` require **`updates:read`** — this is the actual action the shipped sibling feature's own `GET /api/settings/discord-bot` route uses (verified directly against `console/api/src/actions.js`), granted to both admin and owner via the existing `updates:*` wildcard. Citing `settings:read` (denied to admin via the `settings:*` Deny wildcard) would have silently stranded every admin-tier operator the moment they clicked "Connect to hosted bot," despite that same tier already being able to fully enable and configure the adapter one step earlier.
- `hosted-bot/register` requires a **new, dedicated, owner-only action** — `settings:discord-bot-hosted-register` — rather than the coarse `updates:apply` the original draft cited. This mirrors the established precedent this codebase already applies to its own riskiest sub-cases: the sibling feature's `enable`/`role-ids` routes layer an explicit `session.tier !== "owner"` check specifically for changing the bot's "admin"-tier Discord role mapping (judged too sensitive for bare `updates:apply` alone), and token *regeneration* got its own bespoke, non-`updates:*` action for the same reason. This route is at least as sensitive as either of those: it forwards a live external OAuth credential and the local adapter secret across an organizational trust boundary to a third-party-operated service, provisioning a persistent third-party integration. A role scoped only to `updates:apply` (e.g. a future custom IAM policy meant to authorize "apply stack updates and tweak role IDs") must not, without separate explicit review, also gain the ability to do this.

### 3.3 The server-to-server registration call (Core → mentat)

Core's `POST /api/integrations/discord/hosted-bot/register` handler makes an outbound HTTPS call:

```
POST https://mentat-backend.darkdante.org/api/consoles/register
Content-Type: application/json

{
  "guildId": "<snowflake, from the operator's selection>",
  "discordAccessToken": "<the live, ~1hr-lived token from step 4, forwarded verbatim>",
  "consoleUrl": "<window.location.origin, confirmed/editable by the operator in the confirm step>",
  "adapterToken": "<read from Core's own token file/env, the same value Settings -> Discord Bot already generated>",
  "roleMappings": { "player": [...], "moderator": [...], "admin": [...] }
}
```

**On mentat's side** (new route in `mentat/src/setupServer.js` or a new sibling module — Layer 2 decides the exact file split):

0. **This endpoint must be added to `requireProxySecret()`'s `exemptPaths` list.** **[L1 CRITICAL finding, resolved — the original draft's claim that this endpoint is reachable "from any Core console on the internet with no pre-shared secret at all" was flatly contradicted by mentat's own, already-shipped code: `setupServer.js` applies `requireProxySecret({ exemptPaths: [...] })` as its *first* middleware, rejecting every request that doesn't carry `MENTAT_PROXY_SHARED_SECRET` — a secret known only to mentat-link's own proxy, never to a third-party Core install. As literally specified, every single call this design describes would 403 before reaching step 1 below.]** This is a deliberate, explicit widening of an existing boundary — `proxyAuth.js`'s own header comment already documents that boundary as "obscurity, not access control" (the hostname's TLS cert is public via Certificate Transparency regardless), so adding one precisely-scoped exemption does not weaken anything the shared secret was actually relied on to protect elsewhere; every other route keeps requiring it unchanged. This exemption is the concrete Layer 2 code change that makes the design's own stated trust model (§ below) actually true, rather than aspirational.
1. **Cheap, local validation before any outbound Discord call**: reject requests with a malformed/missing `discordAccessToken` (wrong shape/length, matching the existing length-check pattern already used in `exchangeDiscordAuthCode()`) or a `guildId` that isn't a valid snowflake, with no call to Discord at all. **[L1 HIGH finding, resolved — see the DoS note below.]**
2. **Rate-limit this endpoint independently of `/setup/register`**, mirroring the real, existing per-endpoint rate-limiter pattern already used elsewhere in this file (`steamLinkRateLimit.js`/`statsPushRateLimit.js` are the concrete precedent to follow, not a novel mechanism). **Key the limiter by the Discord user ID recovered in step 3 below, not source IP alone** — IP-based limiting doesn't protect the endpoint's real bottleneck (mentat's own shared, single-`client_id` Discord API rate-limit budget, serving every guild the bot has) and is weak against a distributed sender; **additionally apply a hard global ceiling on outbound-to-Discord calls originating from this route specifically**, independent of any per-caller limit, since even legitimate distinct callers could collectively exhaust the shared budget. **[L1 HIGH finding, resolved — a zero-pre-shared-secret endpoint that costs one outbound Discord API call per request, against a single shared rate-limit bucket serving every connected guild, is a real denial-of-service path for an attacker with no Discord credentials of their own; step 1's local pre-validation and this global ceiling together bound it.]**
3. Call Discord's `/users/@me/guilds` **itself**, using the forwarded `discordAccessToken` — **never trust the `guildId`/ownership claim in the request body without this independent check.** Confirm the token is valid (Discord will reject an expired/revoked token with its own 401) and that the returned guild list contains `guildId` with `owner: true` for the token's own user.
4. If verified: `upsertGuild()` (the existing function, `mentat/src/database.js:444-471`) with `consoleUrl`, `adapterToken` (encrypted at rest exactly as today, via `encryptColumn()` when `ACP_SECRETS_KEY` is configured — this design does not change that dependency), `guildName` (extracted from the same Discord response fetched in step 3 — the response already has it, no extra call needed), and `status: "active"` (matching the existing `/setup/register` flow's own semantics, not `upsertGuild()`'s bare default of `"pending"`). **[L1 finding, resolved: missing parameter specification]** **`roleMappings` is not part of this call at all** — role IDs are managed exclusively through Core's own Settings → Discord Bot section (§3.4) and this route never reads or writes them; the request payload below reflects this. **[L1 finding, resolved: §3.3's original payload example contradicted §3.4's own text]** Note this update path is *less* destructive than the existing `/setup/register` flow's own behavior: unlike that flow (which unconditionally resets `guild_settings` — `rbac_mode`/`default_ephemeral` — to hardcoded defaults on every registration via `updateGuildSettings()`), this new route calls only `upsertGuild()` and leaves any existing `guild_settings` customization untouched on re-registration. This asymmetry between the two paths is intentional and beneficial, not a bug — documented here so it isn't mistaken for one.
5. **Never persist `discordAccessToken`.** It is used for exactly one verification call and discarded in the same request — matching Core's own established "use once, discard" pattern for this same class of secret.
6. Respond with a normalized success/error shape Core's `register` handler translates into one of the specific UI states in §3.5 (not a passthrough of mentat's raw error body).

```
POST https://mentat-backend.darkdante.org/api/consoles/register
Content-Type: application/json

{
  "guildId": "<snowflake, from the operator's selection>",
  "discordAccessToken": "<the live, ~1hr-lived token, forwarded verbatim>",
  "consoleUrl": "<window.location.origin, confirmed/editable by the operator in the confirm step>",
  "adapterToken": "<read from Core's own token file/env, the same value Settings -> Discord Bot already generated>"
}
```

**Why this endpoint is a new, distinct kind of attack surface on mentat's backend, and what bounds it:** every other request mentat's backend accepts today either comes through mentat-link's proxy (gated by `MENTAT_PROXY_SHARED_SECRET`) or from the bot's own signed handoff mechanism (`handoff.js`, HMAC-signed, 30-second-lived). This new endpoint is, by deliberate design and the explicit `exemptPaths` change in step 0, reachable from **any caller that can present a live, `guilds`-scoped Discord OAuth access token** — not, precisely speaking, "any Core console": nothing cryptographically ties a caller to Core's own round-trip specifically, since a bearer token is portable to whoever holds it. **[L1 finding, resolved: caller-population framing corrected]** Core's browser/backend round-trip is the intended, convenient on-ramp to this endpoint, not a security boundary the endpoint itself relies on — the endpoint's *only* real gate is the live, independently-re-verified Discord OAuth token (steps 1-3 above), which is why those steps, and their DoS-resistance specifically, carry the actual weight of this trust boundary. This is an intentional, new trust boundary — the single largest blast-radius item in this whole design (§6) — not an oversight.

**Accountability:** `mentat`'s own operators are unambiguously responsible for this endpoint's abuse-monitoring and incident response, since it is their process and their egress; Core's operators have no visibility once a request leaves their own console. **[L1 finding, resolved — stated explicitly rather than left implicit.]**

**Resilience — timeout and retry for Core's outbound call:** Core's HTTPS request to `mentat-backend.darkdante.org` uses a bounded timeout (15 seconds — long enough for a real network round trip including mentat's own outbound Discord verification call, short enough that the operator isn't left waiting indefinitely on a hung backend) and exactly one retry on a 5xx or connection-level failure (no retry on 4xx, since a 4xx here means the request itself was rejected — retrying an already-rejected request wastes the shared rate-limit budget this design otherwise protects in §3.3 step 2). **[L1 finding, resolved — the original draft named this failure mode in §3.5 but specified no bound, risking an indefinitely-hanging request.]**

**Prerequisite: outbound internet access.** This entire feature requires Core's console to reach `mentat-backend.darkdante.org` over HTTPS, outbound. This is a materially weaker assumption than "reachable from the internet" (which many self-hosted operators deliberately avoid), but it is a real, new prerequisite this design introduces — named explicitly here and in §6, rather than left for an operator on a fully egress-restricted network to discover only when the feature silently fails. **[L1 finding, resolved]**

**SSRF-adjacent note on `consoleUrl`:** mentat's bot already makes outbound calls to whatever `consoleUrl` an operator registers, today, via the existing manual/portal flow — accepting an operator-supplied URL and later connecting to it is not a new *kind* of risk this design introduces. What this design does change is the *rate* at which new `consoleUrl` targets can be registered: today's manual, one-Discord-invite-per-attempt flow has soft friction this self-service flow removes. Step 2's Discord-user-keyed rate limiting is the mitigation for this dimension specifically, not just for the raw-request-volume DoS concern above. **[L1 finding, resolved]**

### 3.4 Role-ID entry stays manual

Per explicit instruction: Discord role IDs (which roles map to player/moderator/admin bot-command tiers) are not derived from OAuth data — Discord's `guilds` scope doesn't expose a guild's role list at all (that needs the bot to already be a member and a separate, elevated API call), and this design does not add that. The operator continues to paste Discord role IDs into Core's Settings → Discord Bot fields (the pattern already shipped) exactly as today. This is the one explicitly-accepted remaining manual step.

### 3.5 Error handling

| Failure | UI treatment |
|---|---|
| Operator cancels/denies Discord's consent screen | Return to the Settings page with no error banner (this is a cancel, not a failure) — matches how browsers/Discord's own flow signal cancellation (an `error=access_denied` query param on the callback) |
| Operator owns zero Discord guilds | "No servers found where you're the owner. If you manage a server without owning it, direct ownership is required for this step today — see [the installation guide's hosted-bot section](../integrations/discord-control-bot/setup-guide.md) for the manual `/setup` fallback in the meantime." (see §9 for the ADMINISTRATOR-permission follow-up; **[L1 finding, resolved: the original text had a literal, unresolved `[contact/see docs]` placeholder here]**) |
| Access token expires between guild-pick and confirm | An explicit "Reconnecting to Discord to confirm this is still you…" message, then a silent re-run of the OAuth round-trip (§3.1 step 8, §3.2's pending-registration store) — not a raw expiry error. If that second attempt also fails: "Your Discord session expired — try again." |
| `mentat`'s registration API is unreachable (network/DNS/timeout after the bounded retry+timeout policy in §3.3) | "Couldn't reach the hosted bot service. Your console's own settings are unaffected — try again in a moment." (explicitly reassures the operator this failure has no effect on their local adapter config, since it doesn't) |
| `mentat` rejects: Discord re-verification fails (token invalid/expired by the time mentat calls Discord, or guild ownership mismatch) | "Could not verify you own that Discord server — please try connecting again." (deliberately does not say more — this is the one failure mode with a plausible malicious-actor interpretation, and the message should not help an attacker distinguish "token expired" from "you don't actually own this guild") |
| `mentat` rejects: malformed/missing adapter token on Core's side | Structurally unreachable in the intended flow (the "Connect to hosted bot" action is only shown once Settings → Discord Bot already has a token configured, §3.1) — Core's `/register` handler adds a defensive check regardless (reads the token file itself immediately before forwarding; if empty, returns "Your console doesn't have an adapter token configured yet — enable the adapter first" without making any outbound call to mentat at all) |
| Operator's console has no outbound internet access to reach `mentat-backend.darkdante.org` at all | Same UI treatment as the generic "unreachable" row above — from the operator's perspective these are indistinguishable, but see §6 for why this is named as its own, separate blast-radius item (this is a real prerequisite, not just a transient blip) |
| Re-registering an already-connected guild | Treated as an update, not an error — `upsertGuild()` already supports this (existing behavior, unchanged); the guild dropdown (§3.1 step 6) marks it as already-connected beforehand so this is rarely a surprise |

### 3.6 What happens to the existing DM + portal flow

Per explicit instruction ("no setup link, no dm"): `mentat`'s `handleGuildCreate()` DM-on-invite behavior (`onboarding.js:265-330`) is **removed** as the default onboarding trigger once this ships. An operator who invites the bot going forward is expected to already know (from installation docs, updated as part of this design's own rollout) to go to their own console's Settings → Discord Bot page.

**Removing the DM without a replacement discovery signal was a real, unaddressed gap in the original draft — resolved with two concrete mechanisms, both in scope for this design, not deferred:** **[L1 finding, resolved]**

1. **In-guild bot response for an unregistered guild.** When any bot command is invoked in a guild that has never been registered (no row in mentat's `guilds` table, or one with `status !== "active"`), the bot's reply states plainly that the server isn't connected yet and names the exact next step: *"This server isn't connected to a console yet. A server admin should go to their Dune Docker console's Settings → Discord Bot page and click 'Connect to hosted bot.'"* This is the natural, self-service discovery path for exactly the population that used to rely on the DM — someone who invited the bot, tried a command, and needs to know what to do — and it requires no new infrastructure, since the bot already has to look up the guild's registration to route the command in the first place.
2. **Core-console-side banner.** Settings (or the Dashboard) shows a dismissible notice once the adapter is enabled with `choice === "hosted"` but no hosted-bot registration exists yet: *"You've enabled hosted-bot support but haven't connected a Discord server. Connect one in Settings → Discord Bot."* This drives the operator proactively, from Core's own side, rather than relying entirely on docs recall from before they ever invited the bot.

**The `/setup` page and `POST /setup/register` handler are not deleted.** They remain reachable (unlinked from any new DM, but still a real, working URL) as an escape hatch: for an operator troubleshooting a broken registration, for anyone who bookmarked the old link, and as a fallback if this new flow has an outage or a bug not caught before rollout. Its own stale instructions (the `openssl` hint, per the earlier conversation in this design's own history) still get corrected to point at Core's Settings page instead of a CLI command — that fix is real and worth keeping regardless of this larger design, and is a natural companion PR/commit in the `mentat` repo, done alongside this feature.

This is a deliberate, Requirement-0-driven choice: removing the *only* path to registration entirely, on day one of a new, unaudited flow, would leave zero recovery path if something is wrong. Fully retiring `/setup` (if ever desired) is a separate, later decision once this flow has real production track record — not part of this design.

**Existing invited-but-unregistered guilds are unaffected by this removal** — verified directly against `handleGuildCreate()` (`mentat/src/onboarding.js:265-330`): it fires once per real invite event and only skips guilds already `status === "active"`, so no currently-invited, not-yet-registered guild loses a path that already exists; their historical DM (already sent) still points at the still-functioning `/setup` fallback above. **The ongoing, ship-day-forward risk — a brand-new invite has no automated signal until the operator either tries a bot command (mechanism 1 above) or checks Core's console (mechanism 2)** — is the one accepted, residual risk of this section, named explicitly rather than left implicit. **[L1 finding, resolved]**

## 4. Data Flow Summary

```
Operator's browser (Core console)
  -> GET /api/integrations/discord/hosted-bot/oauth/start   [Core backend]
       - checks OAuth is configured; fails safe with a Core-rendered error if not
  -> 302 to discord.com/oauth2/authorize                     [Discord]
  -> 302 back to /api/integrations/discord/hosted-bot/oauth/callback  [Core backend]
       - exchanges code for access token (server-side only)
       - calls Discord /users/@me/guilds, keeps owner=true guilds
       - creates a pending-registration entry {accessToken, ownedGuildIds, userId},
         keyed by a fresh random handle; sets the handle in a new, dedicated cookie
       - hands the owned-guilds LIST (not the token, not the handle) to the SPA
  <- operator picks a guild, confirms (sees the disclosure text from §3.1 step 7)
  -> POST /api/integrations/discord/hosted-bot/register       [Core backend]
       - reads + consumes the pending-registration entry via the handle cookie
       - re-checks choice === "hosted" and the guildId against ownedGuildIds
       -> POST https://mentat-backend.darkdante.org/api/consoles/register   [mentat backend]
            - exempted from requireProxySecret specifically for this one path
            - local shape validation before any Discord call (DoS bound)
            - re-calls Discord /users/@me/guilds with the forwarded token
            - verifies ownership independently
            - upsertGuild() into its own DB (guildName + status:"active", no roleMappings)
            - discards the forwarded Discord token
       <- success/error (15s timeout, 1 retry on 5xx)
  <- Core translates into a specific UI state (§3.5), persists "Connected" status
```

The Discord access token itself exists in exactly two server-side places, each for the lifetime of a single request: Core's `/callback` handler (which creates it and stores it server-side, keyed by the handle) and mentat's registration handler (which receives it once, forwarded from Core's `/register` handler, and discards it after one verification call). **The token itself never reaches the browser.** What the browser does hold, between the callback and the confirm click, is an opaque, single-use, short-TTL *handle* in a dedicated cookie — a correlator, not a credential — matching the same "state must survive across two requests" pattern this codebase's own OAuth CSRF/PKCE machinery already uses. The token is never written to any database or log on either side.

## 5. Testing

**[L1 finding, resolved — the original §5 named only a handful of happy-path tests; the audit found 5 of 7 §3.5 error rows and several of §2/§3.3's own claimed security properties had no corresponding named test at all. Every scenario below is named explicitly so Layer 2 cannot silently ship an under-tested version of a safety-critical property.]**

**Core, unit-level:**
- `fetchOwnedDiscordGuilds()`: owner-filtering (mixed owned/not-owned guilds in the response → only `owner:true` ones returned), empty-guild-list case, malformed Discord response.
- The pending-registration store (§3.2): entry expires with the token's own TTL; a handle is single-use (a second read after `/register` already consumed it finds nothing); a handle from a different session/cookie cannot read another operator's entry; capacity cap behaves like `createPendingStateStore()`'s own tested cap.
- `/register`'s local defensive checks: empty/missing adapter-token-file read → blocks before any outbound call to mentat, returns the exact §3.5 message, and asserts no HTTP request was attempted; submitted `guildId` not present in the entry's `ownedGuildIds` → rejected locally, before any outbound call (the defense-in-depth check from §3.2).

**Core, route/integration-level** (real spawn-and-fetch pattern, matching `discordAdapterSettingsRoutes.integration.test.js`):
- IAM: a session with `updates:read` only (no `settings:discord-bot-hosted-register`) attempting `POST /register` → 403, and confirms `upsertGuild()`-equivalent forwarding never happens (mock mentat's endpoint and assert it was never called). A session with `choice !== "hosted"` attempting any of the 3 routes → 403/blocked, confirming the server-side re-check (not just frontend hiding) actually holds.
- `error=access_denied` on the callback → no error banner, clean return to Settings.
- A `/register` call with the pending-entry's TTL artificially expired → confirms the "Reconnecting…" message path fires and a fresh OAuth round-trip is initiated, not a raw error.
- Mock `mentat-backend.darkdante.org` to return a 5xx / hang past the 15s timeout → confirms exactly one retry occurs, then the "Couldn't reach the hosted bot service" message, and confirms no local Core state is mutated as a side effect.
- Mock mentat's endpoint to return the ownership-mismatch rejection shape → confirms Core surfaces the exact §3.5 row-5 message verbatim, with no additional detail leaked, and confirms no local Core state is mutated (this is the Core-side half of the design's single most important security property — mentat's own independent re-verification is tested on mentat's side below, but nothing previously verified that Core correctly *relays* that rejection rather than swallowing it into a false success or leaking extra detail).
- Calling `/register` twice with the same guild (simulating "connect another guild" re-run on an already-connected guild) → confirms idempotent-update behavior, not a duplicate-error.
- A test proving the access token never appears in any log line, any `Set-Cookie` header, any session-store write, or any database row for the lifetime of the whole flow (reuse the existing `audit()`-redaction assertion pattern from the adjacent feature, but broadened to check all four surfaces explicitly, not logging alone).

**`mentat`, unit-level:**
- The new endpoint's independent-reverification logic: valid token + matching guild → success; **valid token proving ownership of a *different*, unrelated guild the caller genuinely owns, submitted against a *different* target `guildId` → rejected** (this is the design's single most important negative test — an attacker with their own legitimately-owned, unrelated guild's token must not be able to register a victim's guildId; already correctly identified as necessary in this design and must stay explicit in Layer 2, not get quietly dropped); expired/invalid/revoked token → rejected.
- Local pre-validation (§3.3 step 1) rejects a malformed token/guildId shape with zero calls to Discord's API — a test that mocks Discord's endpoint and asserts it was never invoked for these inputs.
- Rate limiting: the new endpoint's limiter is independent of `/setup/register`'s own counter (a burst against one doesn't exhaust the other), and is keyed by the verified Discord user ID once known, not source IP alone.
- Confirm `discordAccessToken` never appears in any log line or DB write (mirroring this org's own Requirement 24 test conventions already used elsewhere in this codebase).
- `upsertGuild()` called via this new path: confirms `guild_settings` (rbac_mode/default_ephemeral) is left untouched on an update, unlike the existing `/setup/register` path's own destructive reset — a regression test for the beneficial asymmetry noted in §3.3.
- Regression tests for the DM removal itself: `guildCreate` no longer triggers a DM send (assert the send call is NOT made); `/setup` and `POST /setup/register` still return 200 and successfully upsert a guild after the `onboarding.js` edit (the surrounding code must not have been accidentally broken by removing the DM logic).

**`mentat`, middleware-level:**
- A direct request to `POST /api/consoles/register` with no `x-mentat-proxy-secret` header still succeeds (confirming the `exemptPaths` addition from §3.3 step 0 actually takes effect) — paired with a test confirming every *other* existing route on this Express app still correctly rejects a request missing that header (confirming the exemption is precisely scoped, not an accidental broadening).

**Cross-repo — stronger than a single one-time manual check.** **[L1 finding, resolved — the original text's "at minimum one documented manual end-to-end verification" was the *only* cross-repo safety net, with no recurring cadence and no shared contract, in a system where the two repos deploy and test entirely independently — exactly the "mocked test silently diverges from real production behavior" failure class this org's QA hat mandate exists to catch.]**
- A shared, versioned fixture for the `POST /api/consoles/register` request/response JSON shape, imported by both repos' own test suites, so a field rename or shape change on either side is caught by that side's own test run, not only by a later manual check.
- The manual end-to-end verification (real Core console, real Discord OAuth app, real guild, confirming the full round trip and that the bot subsequently authenticates against the registered console) is required **before initial rollout**, and again as a named checklist item in this org's own Requirement-20 Layer 3 pre-release gate for either repo, whenever a release touches this code path — not a one-time check that's never revisited.

## 6. Requirement 0 / Blast Radius

- **No existing operator's working setup breaks.** Self-hosted-bot operators never see any part of this (§3.1, hard-gated on `choice === "hosted"` both client- and server-side). Existing hosted-bot operators who already registered via the old `/setup` flow keep working exactly as before — this design only changes how a *new* registration or *update* happens, not what's already stored in mentat's DB.
- **The old flow is not deleted**, precisely to avoid "the fix being riskier than the problem it fixes" (this org's own standing rule, given its history with the command-auth-token incident). It becomes a documented fallback, not a dead end.
- **No new Discord OAuth scope is requested.** Every operator who already has console-login OAuth configured already granted `identify guilds`; this design asks for nothing beyond that, so there is no new consent friction beyond triggering the flow itself.
- **Real, required one-time operator action: a second redirect URI must be registered.** **[L1 finding, resolved]** Discord requires every distinct OAuth redirect URI to be pre-registered per application. This design's new callback (`/api/integrations/discord/hosted-bot/oauth/callback`) is a second, distinct path from the existing console-login callback, sharing the same Discord application — every existing operator who wants to use this feature must add this second redirect URI to their own Discord Developer Portal app configuration before it will work at all, or they'll see a `redirect_uri_mismatch` error from Discord directly. This is real, Requirement-0-relevant friction, not "no new friction" as an earlier draft of this section claimed — it must be called out explicitly in rollout communication and docs (§7), and Core's own UI should detect and surface a `redirect_uri_mismatch` response distinctly from the generic error cases in §3.5.
- **Outbound internet access from Core to `mentat-backend.darkdante.org` is a new, real prerequisite.** **[L1 finding, resolved]** Weaker than "reachable from the internet," but still a real assumption some self-hosted operators on egress-restricted networks won't satisfy; named explicitly per §3.3's Resilience note, rather than left to be discovered only as a silent failure.
- **Token custody is now multi-party, not just multi-hop.** **[L1 finding, resolved]** Today, only `mentat` ever handles a live Discord access token for this purpose (it's the direct OAuth recipient in the existing `/setup` flow). This design means *every* Core install that adopts this feature also transiently handles the same class of live token, server-side, for the duration of one request. Core is a public fork run independently by many operators with widely varying security postures — this is a real increase in the number of parties who transiently hold a live bearer token, distinct from (and in addition to) the token's own limited scope. Mitigated by: the token never touches a browser, is never logged (Requirement 24 discipline applied explicitly to the new `hostedBotOAuth.js` module, including confirming it's never placed in a URL/query string on either leg — URLs are logged far more casually than request bodies by generic infrastructure), and is discarded within the same request cycle on every hop.
- **mentat's backend gains one new endpoint, exempted from its own `requireProxySecret` middleware, whose only real gate is a live, independently-re-verified Discord OAuth token.** This is named explicitly as a new trust boundary in §3.3, not discovered later — it is the single largest blast-radius item in this design and the primary thing the Layer 1 audit stress-tested. Its caller population is, precisely, "anyone holding a valid `guilds`-scoped Discord access token" — not "Core consoles" specifically, since bearer tokens are portable (§3.3's corrected framing).
- **mentat-backend.darkdante.org's documented access model changes.** **[L1 finding, resolved]** This org's own master operating doc describes this hostname as "internal-only, never advertised to users." After this ships, that description is no longer accurate for this one path — it becomes reachable by any caller with a valid Discord token, not only by mentat-link's own proxy. §7 requires this doc be updated (Requirement 23) so a future reader isn't working from a stale, narrower threat model.
- **A dedicated owner-only IAM action gates the actual registration call** (`settings:discord-bot-hosted-register`, §3.2) — admin tier cannot trigger the server-to-server call, only owner, matching this codebase's own precedent for actions of this sensitivity.
