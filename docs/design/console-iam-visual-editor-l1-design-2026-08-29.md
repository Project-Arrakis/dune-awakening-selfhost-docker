# Console Access Control: AWS-IAM-Visual-Editor-style Permissions Tab — L1 Design

**Date:** 2026-08-29
**Status:** L1 design, revision 2. Revision 1 received a full Eight Hats Layer 1 audit (8 independent dispatches) — see §6 for the findings register and what changed in this revision. One CRITICAL finding from that audit (a crown-jewel save-guard bypass on the prerequisite branch) was fixed and deployed same-session; see #575, not repeated here since it isn't a defect in this document.
**Tracking issue:** `dune-awakening-selfhost-docker#634`.
**Originated from:** live-testing feedback during PROMPT 2 validation of the layered-auth upstream PRs (#577/#201 Tier 3, #578/#202 Tier 1) — see the Access Control UX findings and the crown-jewel-Deny hardening (commit `245aba25`, fixed further at `de0ed64b` on `tier1-upstream`) recorded on tracking issue #575. This document is a distinct, separate feature built on top of that hardening, not a continuation of the layered-auth PRs themselves.

---

## 1. Why

Live operator testing of the existing Access Control (IAM policy) editor surfaced a consistent pattern: individual action labels are frequently opaque jargon (`Mutate`, `Vehicles Read`) with no indication of what they grant or why a checkbox won't respond, and the flat, always-expanded, ungrouped-by-severity layout of ~150 actions across ~20 namespaces makes it hard to scan "what's safe to grant vs. what's dangerous" at a glance. The operator specifically referenced AWS IAM's Visual Editor (the create-policy UI: a collapsible list of AWS services, each expandable into actions grouped by access level — List / Read / Write / Permissions management / Tagging — with a header checkbox to grant an entire service or level at once) as the interaction model to mirror.

This is a real, validated usability gap, not a hypothetical one: three separate rounds of live-testing feedback in this same session (the "Mutate" label, the "Vehicles Read"/"Skill Catalog" namespace collision, and the admin-vs-moderator Deny asymmetry question) all trace back to the same root cause — the current grid exposes the raw policy-engine vocabulary directly to the operator with minimal translation.

## 2. Verified current state — two baselines, named explicitly (revised in response to Architect finding H1)

Revision 1 said it verified against `main`@`c4b248ad` but several names/fields it cited (`actionGrantedByStatements`, `actionLabel`, `lockReason`/🔒 lock UI, the catalog's `allActions` field, a `policy.js` comment about ownership-based scoping) only exist on `tier1-upstream`, not `main` — confirmed by direct grep against both branches. This feature's real dependency surface is `tier1-upstream` in full, not just the crown-jewel piece revision 1 flagged. Stated plainly this time:

**On `main`@`c4b248ad` (no dependency):**
- `console/web/src/features/settings/IamPolicyEditor.tsx` (327 lines) renders one flat, always-expanded card per namespace (`groupedActions`, keyed by a hardcoded `namespaceOrder` array), each listing every action as an individually-clickable checkbox with a mechanically-derived label (`humanLabel()`: title-case the raw action's suffix — named `humanLabel` on `main`, renamed `actionLabel` on `tier1-upstream`). No group-level select-all, no collapse/expand, no access-level sub-grouping, no lock/wildcard UI at all.
- `console/api/src/actions.js`'s three route tables (`ROUTE_ACTIONS`, `REGEX_ACTIONS`, `REGEX_ACTIONS_BY_METHOD`) are the real source of truth for what actions exist and how they're reached — present on both branches.
- `test/rbacParity.test.js` already statically parses `server.js`'s route dispatcher and fails CI if any route has no action assigned ("parity: every non-adapter route in handleApi has an IAM action") — the existing completeness-gate precedent §4.2's new test follows. Present on both branches.
- **The catalog on `main` is measurably incomplete for this feature's purposes** (Architect finding H2, verified by computing it directly): of 93 distinct real actions across all four action tables, 15 exist only in `REGEX_ACTIONS`/`REGEX_ACTIONS_BY_METHOD_PATTERN` and are absent from `GET /api/settings/iam/policies`'s `actions`/`actionMap` response on `main` — including `players:mutate`, `database:mutate`, and `carepackage:grant`, three of the highest-stakes actions in the whole catalog. This is exactly backwards from §1's goal.

**On `tier1-upstream`@`de0ed64b` (this feature's real prerequisite — the whole branch, not one commit):**
- `IamPolicyEditor.tsx` gained `lockReason()` and 🔒 lock UI (distinguishes an exact-literal Allow from a wildcard/Deny-blocked one — §4.1's select-all design depends on this existing), `actionGrantedByStatements` (the set-builder §4.1 assumes), `CROWN_JEWEL_DENY_ACTIONS` and the (now-fixed, see #575) `setPolicies()` save guard, and `ACTION_DESCRIPTIONS`/`ACTION_LABEL_OVERRIDES`.
- The catalog gained an `allActions` field (`server.js`, `[...allKnownActions()].sort()`) specifically to include the 15 actions missing from `main`'s narrower `ROUTE_ACTIONS`-only view — this closes the gap above, and is why this feature is workable at all.
- `policy.js` gained the "ownership-based access... tracked separately" comment §3 cites to justify dropping Resources/Conditions.

**Implementation of this feature must not begin until `tier1-upstream` (or whatever supersedes it) is confirmed merged to `main`** — not assumed, checked (`git grep CROWN_JEWEL_DENY_ACTIONS main` returning a hit is a sufficient gate check). This is now an explicit, named gate (GRC finding H1) rather than an implied "it will land eventually."

## 3. Scope

**In scope:**
1. Rework the Permissions tab's rendering into a two-level accordion: namespace groups (collapsed by default) → access-level sub-groups (Read / Write / Permissions Management) → individual action rows.
2. A tri-state "select all" checkbox at both the namespace level and each access-level sub-group level.
3. Derived access-level classification (§4.2) — no hand-maintained per-action map.
4. Search auto-expands any group/sub-group containing a match, and restores prior state when the query is cleared.
5. **(Added, GRC finding — co-requisite, tracked as a separate small fix, not blocking this feature's design):** `runtime/scripts/self-update.sh`'s local-state backup/restore allowlist (`backup_local_state()`/`restore_local_state_after_install()`) does not currently include `runtime/generated/iam-policies.json`, unlike ~30 sibling state files. This is a pre-existing gap this feature raises the stakes on (it makes broad, one-click policy customization easy and inviting, increasing how many operators have a real customized policy worth losing to a silent self-update revert). File as its own issue and fix before or alongside this feature ships — not part of this design's own implementation, since it's a one-line addition to an unrelated script.

**Explicitly out of scope:**
- **The JSON tab and Test tab.** Both are unchanged — this is a Permissions-tab-only rework. An operator who prefers raw JSON editing loses nothing.
- **AWS's "Resources" (ARN pattern) and "Conditions" dimensions.** This console's actions are tier-wide, not scoped to individual objects (a documented, existing follow-up in `policy.js`'s own comments on `tier1-upstream`: "ownership-based access... tracked separately"), and there is no request-context concept (time of day, source IP, tags) equivalent to AWS's Conditions. Both dimensions are dropped rather than stubbed with a UI that does nothing.
- **AWS's "List" and "Tagging" access levels.** Neither maps to anything in this catalog (no list-vs-get distinction; no tagging concept at all) — shipping either as an always-empty category would be worse than not having it.
- **Multi-statement policy documents.** Each tier's policy document here is small enough (one Allow, one Deny) that multiple independent visual "statements" would add UI complexity with no real benefit; the existing Allow/Deny-pair model is unchanged.
- **Save-level rollback/undo/version history for a policy document, and confirmation prompts on large bulk grants (DBA finding, MEDIUM).** Real gap — a "select all" can now grant a dozen-plus actions in one save, with no more safety net than today's single-checkbox model has (a single atomic overwrite, no retained prior version). Explicitly deferred: this is a `policy.js`/`setPolicies()`-level capability that would benefit every save path, not just this feature's, and belongs in its own design rather than being bolted onto an editor-UI-only change. Filed as a follow-up issue.

## 4. Design

### 4.1 Interaction model and save semantics

Each namespace card becomes a collapsible section (default collapsed) with a header row: `[tri-state checkbox] Namespace Name (N/M allowed) [chevron]`. Expanding it reveals up to three access-level sub-sections (only levels with at least one action in that namespace render at all), each with its own tri-state header checkbox, expanding further into the existing individual action rows (label, lock icon, tooltip — unchanged from `tier1-upstream`'s current grid).

**Tri-state semantics, corrected (UI/UX finding H1 — the denominator was wrong).** Revision 1 computed checked/indeterminate/unchecked over *every* action in the group, which meant a group containing any crown-jewel action could never show "checked" for a non-owner tier, no matter how completely the operator granted everything actually grantable — a permanently-stuck-indeterminate checkbox with no way to reach "done." Corrected: the denominator for a given tier is *grantable* actions in the group only — i.e., excluding whatever `CROWN_JEWEL_DENY_ACTIONS` (matched via `matchAction()`, see below) removes from that tier's reach. Checked = every grantable action in the group is granted; indeterminate = some but not all; unchecked = none. The "(N/M allowed)" header count uses the same corrected M.

**Checking a group-header box grants every ungranted, grantable action in that group as an individual, literal Allow entry** (decision, not a namespace/level wildcard) — every row stays individually toggleable afterward, exactly matching how a single-action checkbox behaves today. This was chosen over a wildcard (`namespace:*`) specifically because a wildcard-granted row shows as 🔒 locked under the grid's existing `lockReason()` logic, which would defeat the "drill in for fine-grained control" purpose immediately after using select-all.

**Crown-jewel exclusion — matching logic now specified explicitly (Security finding H1).** Revision 1 said exclusion applies "if a group contains a crown-jewel action (per `CROWN_JEWEL_DENY_ACTIONS`)" without saying how that's tested — and the only concrete code in the whole document (§4.2's `accessLevelForAction`) used naive array membership (`CROWN_JEWEL_DENY_ACTIONS.includes(action)`), which is the exact bug shape the Security hat found and fixed at the `setPolicies()` level this same session (`de0ed64b`): `CROWN_JEWEL_DENY_ACTIONS` contains a wildcard pattern (`settings:*`), so literal membership silently fails to exclude concrete actions like `settings:write`/`settings:read` that the pattern covers. **This design now mandates the same expand-then-match logic as the server-side fix**: a real action is crown-jewel-excluded for a non-owner tier if and only if `CROWN_JEWEL_DENY_ACTIONS.some(pattern => matchAction(pattern, action))` (the client-side `iamActionAllowed`/`matchAction` mirror already used for lock-detection, not a reimplementation). §4.4 adds a required test asserting `settings:write`/`settings:read` specifically are excluded from select-all for every non-owner tier — regression-pinning this exact class of bug at the design's own most novel piece of new logic.

If a group contains a crown-jewel action (by the matching above) for a non-owner tier, "select all" excludes it from the literal grant. **The exclusion note is now specified to always render in the collapsed header itself** (UI/UX finding H2 — revision 1 left this ambiguous, and the more natural reading risked the note only appearing after expansion, which an operator who clicks a collapsed header's checkbox and moves on would never see): the header's "(N/M allowed)" text gains a trailing note when the group has any excluded action, e.g. `(4/5 allowed — 1 owner-only)`, visible without expanding. The individual action row remains visible and 🔒-locked underneath if the operator does expand, same as today.

**Unchecking a group-header box revokes every currently-granted literal action in that group.** An action granted by a wildcard or Deny-blocked (already locked today) is left untouched and still shows its existing lock hint — group-level toggling only ever touches the same "exact Allow literal" actions an individual checkbox can already cleanly toggle.

### 4.2 Access-level classification (derived)

```ts
function accessLevelForAction(action: string, routeMethods: Set<string>): "read" | "write" | "permissions" {
  const ns = action.split(":")[0];
  if (CROWN_JEWEL_DENY_ACTIONS.some(pattern => matchAction(pattern, action)) || ns === "settings" || ns === "setup") return "permissions";
  const mutatingMethods = ["POST", "PUT", "PATCH", "DELETE"];
  if (mutatingMethods.some(m => routeMethods.has(m))) return "write";
  return "read";
}
```

(Corrected to use `matchAction()`, matching §4.1's fix — revision 1's `.includes()` here was the same bug shape, just not yet exploitable since the `ns === "settings"` override happened to catch every real `settings:*` action anyway. Fixed for consistency and so a future crown-jewel pattern addition doesn't silently rely on a coincidental override.)

`routeMethods` is a new field the catalog endpoint adds per action — computed server-side by walking `ROUTE_ACTIONS` + `REGEX_ACTIONS_BY_METHOD` (both are keyed or valued by an explicit HTTP method) and unioning the methods that reach each action. **`REGEX_ACTIONS` entries are genuinely method-agnostic by construction (Architect finding, confirmed: no method is recorded there at all)** — revision 1 didn't address what `routeMethods` means for an action reached only through that table. Resolved: an action with zero entries in `routeMethods` (reached only via `REGEX_ACTIONS`) is classified `"read"` unless its name matches an existing `-write`/`:write`/`-mutate`/`-delete`/`-ban`/`-kick`/`-teleport`/`-restart`/`-spawn`/`-despawn` convention (the same naming-convention fallback already used for other parameterized actions), giving every action *some* explicit rule rather than an implicit default. This is a heuristic, not a proof — see the required per-namespace review in §4.4's revised testing plan, which is the real correctness backstop, not the completeness test.

**Confirmed real, non-hypothetical edge cases (Architect finding, computed directly against both branches' `actions.js`):** `settings:read` (GET+POST) and `exchange:market` (GET+POST) both resolve correctly today only because an unrelated override (namespace/crown-jewel) runs first and wins — not because method-aggregation itself is reliable for mixed-method actions. `admin:map-chat` (GET+POST, `tier1-upstream` only) has no such override and resolves to `"write"` purely because a mutating method exists among its routes, which happens to be the conservative/safe outcome here but is an emergent side effect, not a tested rule. This is Open Question 1 (§5) — not resolved by this revision, since it needs an operator decision, but now stated as a confirmed real risk rather than a hypothetical.

### 4.3 Search

The existing search box (filters by action string or label substring) is extended to auto-expand any namespace card and access-level sub-section containing at least one match, and restore the prior collapse state when the query is cleared (`expandedBeforeSearch`, snapshotted on first keystroke, restored on clear). **Known limitation, not fixed in this revision (UI/UX finding, MEDIUM):** a manual expand/collapse made by the operator *while* a search is active is not part of the snapshot and will be reverted on clear — flagged as a real but low-severity rough edge (Open Question 4, §5), not blocking, since the alternative (continuously re-snapshotting on every manual interaction during search) adds meaningful complexity for a narrow case.

### 4.4 Testing plan (substantially revised — QA hat found the original plan had real gaps, not just missing detail)

- Unit tests for `accessLevelForAction()` covering all three levels, the parameterized/method-agnostic fallback, and the three confirmed mixed-method edge cases from §4.2 by name (`settings:read`, `exchange:market`, `admin:map-chat`) — these are genuine falsifiable per-input assertions, unaffected by the finding below.
- **The "completeness" test is redesigned, not just relocated (QA finding H1 — revision 1's version was a tautology).** `accessLevelForAction`'s TypeScript return type (`"read" | "write" | "permissions"`) already statically guarantees no unclassified bucket exists — a runtime test asserting the same property can never fail, whether it imports the real function or a reimplementation. Replaced with a **curated expected-level snapshot**: a checked-in table of every real action from `allKnownActions()` (imported from the real catalog, not reimplemented) mapped to its expected level, reviewed by a human at write time and updated by a human (not auto-generated) whenever a new action is added — this is what actually catches a *mis*classification (a future write-shaped action silently landing in "read"), which a completeness-only test structurally cannot. This is a real, ongoing maintenance cost §4.2's "self-updating, zero maintenance" framing (revision 1) overstated — a new action still requires one line added to this table, though the test failing loudly (a new action with no table entry) replaces the silent-miscategorization risk with a build failure, which is the actual goal.
- **Cross-package test-access is now specified (QA finding H2 — revision 1 didn't say how a web-package test reaches the real API-package catalog, and two of the three plausible ways are exactly the antipatterns this review is watching for).** `accessLevelForAction` and its expected-level table live in `console/web/src/features/settings/iamPolicy.ts`; `allKnownActions()`/the route tables live in `console/api/src`. These are two independent, unlinked npm packages. **Decision: the expected-level table test runs in the API package** (`console/api/test/`, alongside `rbacParity.test.js`, importing `allKnownActions()` directly with zero fixture) and asserts against a table that is duplicated by necessity into that test file — a comment cross-references the web package's copy so a reviewer changing one is prompted to check the other. This is the same shape as the classification logic itself living in two conceptually-linked places today (server-side truth, client-side mirror for the grid) and is preferred over a live HTTP integration test (heavier harness, untested-anywhere-else pattern) or a static fixture snapshot (drifts silently — see next bullet).
- **`routeMethods` gets its own dedicated API-side contract test (QA finding, addressing the previously-unnamed exception), not just a passing mention.** Asserts the real, computed `routeMethods` value for a representative action from each table (`ROUTE_ACTIONS`-only, `REGEX_ACTIONS_BY_METHOD`-only, and a `REGEX_ACTIONS`-only action to confirm the method-agnostic fallback in §4.2 fires correctly) — run against the real tables, not a hand-picked fixture value, closing the fixture-drift risk QA flagged.
- Contract/render tests for the web component, **correctly citing their real precedent (QA finding H3/Architect — `IamPolicyEditor.contract.test.tsx` doesn't exist on `main`; it exists on `tier1-upstream`, this feature's actual prerequisite)**: tri-state checkbox states at both levels (including the corrected excluding-crown-jewels-from-the-denominator semantics, §4.1); select-all writing literal actions, not a wildcard; crown-jewel exclusion-with-note on select-all for a non-owner tier, **and the complementary owner-tier case** (QA finding — revision 1 only named the non-owner-tier test, leaving the owner branch of the same conditional untested) confirming an owner's select-all is never excluded; search auto-expand and restore-on-clear. This explicitly reuses the real, shared helpers (`actionGrantedByStatements`, `matchAction`) rather than reimplementing them in the test file — the exact anti-pattern `IamPolicyEditor.grouping.test.ts`'s own header comment already records this codebase paying for once (QA finding, MEDIUM).
- No changes to `policy.js`'s evaluation semantics are needed for this feature itself — this is purely an editor-UI feature over the existing Allow/Deny model. (The crown-jewel *guard* fix at `de0ed64b` is a separate, already-shipped fix to existing code, not part of this feature's own test surface.)
- **Audit-log granularity gap, named but explicitly deferred (Security finding, MEDIUM).** `server.js`'s save-route audit log records only which tiers were touched, not which actions were added/removed or whether the change came from one checkbox or a namespace-wide select-all. This feature multiplies the practical consequence of that gap (one click can now add far more than one action) without itself proposing a fix — flagged as a real, pre-existing gap worth its own follow-up (Repudiation risk: an incident investigation has no record to distinguish an intentional bulk grant from an accidental one), out of scope for this UI-only feature to fix.

## 5. Open questions for Layer 2 review

1. Is deriving access level from HTTP method actually reliable enough, given the three confirmed mixed-method cases in §4.2 currently resolve correctly only via an unrelated override? Does `admin:map-chat` (and any future mixed-method action without an override) need an explicit per-action correctness review before this ships, not just the completeness table?
2. Is the "(N/M allowed — 1 owner-only)" header note (§4.1, now specified to render in the collapsed state) sufficient, or does excluding a crown-jewel action from a bulk grant warrant a stronger confirmation step?
3. Is there any real operator (not just this session's) for whom collapsed-by-default makes the *common* case (checking one already-known permission) slower, not faster?
4. Is losing a manual expand/collapse action made *during* an active search (§4.3, acknowledged rough edge) acceptable, or does it need the added complexity of continuous re-snapshotting?
